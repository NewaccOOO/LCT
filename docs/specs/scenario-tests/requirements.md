# Требования: сценарный прогон модели трассировки

Цели и границы — в [brief.md](brief.md), факты — в [research.md](research.md), решения — в [design.md](design.md), условия ТЗ — в [tz-inventory.md](tz-inventory.md). Все команды запускаются из корня репозитория; скрипты в `scripts/gates/` сами подключают `env.sh`.

## Истории и критерии приёмки

### US-1: Команда прогоняет детерминированные сценарии по каждому условию ТЗ, чтобы находить нарушения правил до жюри (P1, цель G-1)

- **AC-1.1** WHEN выполняется `bash scripts/gates/scenarios.sh` THE SYSTEM SHALL собрать jar из текущих исходников, прогнать pytest по `tests/scenarios` и напечатать `SCENARIOS OK passed=<n> failed=0 skipped=0` только если прошло не меньше 120 сценариев, ни один не упал, не пропущен и не помечен `xfail`; при запуске без фильтра `-k` скрипт записывает `data/scenarios/last-run.json` с временем прогона и результатом каждого сценария — проверка: `scripts/gates/scenarios.sh` печатает `SCENARIOS OK passed=<n> failed=0 skipped=0`, гейт требует `n` не меньше 120.
- **AC-1.2** THE SYSTEM SHALL для каждой позиции tz-inventory.md со скоупом «да» иметь не меньше двух сценариев, которые ссылаются на её ID и различаются хешем сцены; сценарий без объявленных ожиданий в покрытие не засчитывается — проверка: `uv run --project tools python -m heatscen.report --check` печатает `COVERAGE OK items=<n> uncovered=0`.
- **AC-1.3** THE SYSTEM SHALL для каждого сценария и каждого объявленного в нём ожидания изменить соответствующее поле в сохранённом выходе сервиса и получить отказ этого ожидания; сценарий без ожиданий считается непойманной мутацией — проверка: `uv run --project tools python -m heatscen.mutate` печатает `MUTATION OK scenarios=<n> expectations=<m> missed=0`, гейт требует `n` не меньше 120.

### US-2: Команда гоняет случайную синтетику с разным составом типов ограничений, чтобы ловить регресс на наборах другой структуры (P1, цель G-2)

- **AC-2.1** WHEN выполняется `bash scripts/gates/sweep.sh` THE SYSTEM SHALL для сидов 1–300 сгенерировать вход (`medium` для сидов, кратных 6, иначе `small`; одно из четырёх подмножеств `restriction_type` из D-6 по остатку `seed % 4`; префикс ID по сиду), прогнать CLI и `heatcheck.validate.run_all` по всем 15 правилам, и напечатать `SWEEP OK seeds=300 failed=0 special=<s> recon=<r>` только если каждый сид завершился кодом 0 без единого нарушения, а суммарно по прогону есть хотя бы один специальный участок и одна реконструкция; результат пишется в `data/scenarios/sweep.json` — проверка: скрипт печатает `SWEEP OK seeds=300 failed=0 special=<s> recon=<r>` с `s` и `r` больше нуля.
- **AC-2.2** WHEN генератор запускается с `--types <список>` и `--id-prefix <строка>` THE SYSTEM SHALL выдать файл, где ограничения только перечисленных типов, все `id` начинаются с префикса, `heatsynth.check` печатает `SYNTH SCHEMA OK`, а два запуска с одним сидом дают одинаковые байты — проверка: `bash scripts/gates/synth_types.sh` печатает `SYNTH TYPES OK subsets=4`.

### US-3: Сервис следует ТЗ там, где расходился, чтобы жюри не нашло расхождений с документами организатора (P1, цель G-3)

- **AC-3.1** THE SYSTEM SHALL записывать в `tie_in.required_diameter` диаметр нового участка, который начинается в этой врезке, и для врезки в трубу, и для врезки в камеру (ТП §10.2, R-10); валидатор проверяет то же; фикстура `tests/validator` пересчитана — проверка: `bash scripts/gates/scenarios.sh -k required_diameter` печатает `SCENARIOS OK passed=<n> failed=0 skipped=0` с `n` не меньше 4.
- **AC-3.2** THE SYSTEM SHALL держать в `rules/rules.json` типы `metro`, `railway`, `water_supply`, `sewer`, `power_line_support` и `_fallback` со значениями таблицы research.md, при этом сверка с CONSTRAINTS.md по десяти исходным типам не меняется — проверка: `uv run --project tools python -m heatscen.rules_ext docs/specs/scenario-tests/research.md rules/rules.json` печатает `RULES EXT MATCH`, затем `uv run --project tools python -m heatcheck.rules_check CONSTRAINTS.md rules/rules.json` печатает `RULES MATCH`.
- **AC-3.3** IF во входе есть ограничение с `restriction_type`, которого нет в `rules.json` THEN THE SYSTEM SHALL обработать его по правилу `_fallback` (запрет, отступ 1,0 м плюс половина ширины пары), завершить CLI кодом 0 и напечатать в stderr одну строку на тип: `ПРЕДУПРЕЖДЕНИЕ: restriction_type "<тип>" нет в справочнике, объектов: <n>, применено правило запрета с отступом 1,0 м` — проверка: `bash scripts/gates/scenarios.sh -k unknown_type` печатает `SCENARIOS OK passed=<n> failed=0 skipped=0` с `n` не меньше 2.
- **AC-3.4** THE SYSTEM SHALL применять к типам из AC-3.2 те же механизмы, что к исходным: буфер запрета с `clearance + width/2` для `forbid`, специальный участок с `margin_m`, `min_angle_deg` и `k_special` для `special`, геометрия Point, LineString, MultiLineString, Polygon, MultiPolygon; валидатор берёт правило типа из `rules.json` и `_fallback` для остальных — проверка: `bash scripts/gates/scenarios.sh -k S14` печатает `SCENARIOS OK passed=<n> failed=0 skipped=0` с `n` не меньше 8.

### US-4: Команда и жюри читают отчёт прогона, чтобы видеть покрытие условий ТЗ и историю дефектов (P2, цель G-4)

- **AC-4.1** WHEN выполняется `uv run --project tools python -m heatscen.report --check` THE SYSTEM SHALL пересобрать `docs/testing/scenario-report.md` из `data/scenarios/last-run.json`, `data/scenarios/sweep.json`, tz-inventory.md и `docs/testing/defects.md` и напечатать `REPORT OK` только если пересобранный текст совпадает с закоммиченным файлом байт в байт и в нём есть матрица со строкой на каждую позицию инвентаря со скоупом «да», итог случайного прогона и раздел дефектов; дата, хеш коммита и время прогона в отчёт не входят — проверка: команда печатает `REPORT OK`.
- **AC-4.2** THE SYSTEM SHALL вести `docs/testing/defects.md` как таблицу «сценарий, симптом, причина, коммит исправления», где каждая строка заполнена, а ID сценария существует в реестре — проверка: `uv run --project tools python -m heatscen.report --check` печатает `DEFECTS OK rows=<n>`.

### US-0: Что не должно измениться

- **AC-0.1** Все 31 гейт пакета backend-core зелёные после правок сервиса, валидатора и `rules.json` — проверка: `node ~/.claude/skills/unlazy/scripts/gate-check.mjs --cwd . --timeout 1800 --reverify docs/specs/backend-core/GATES.md` печатает `ALL MET`.
- **AC-0.2** CONSTRAINTS.md байт в байт совпадает с `main` — проверка: `bash scripts/gates/constraints_unchanged.sh` печатает `CONSTRAINTS UNCHANGED`.

## Нефункциональные требования

- **NFR-1** Полный прогон — сценарии AC-1.1 плюс случайный прогон AC-2.1 — занимает не больше 1500 секунд стенных часов на машине исполнителя — источник числа: Q-7, допущения A-1 и A-2; замер: `uv run --project tools python -m heatscen.report --check` печатает `TIME OK elapsed=<s>s`, где `s` — сумма времени из `last-run.json` и `sweep.json` в целых секундах, только если сумма не больше 1500.

## Ограничения

- **C-1** Прогон на Python 3.12 и новее в проекте `tools/` через `uv`; зависимости только уже объявленные в `tools/pyproject.toml` (shapely, pyproj, pytest); новый пакет `scenarios/heatscen` добавляется в `[tool.hatch.build.targets.wheel]`.
- **C-2** Работа в ветке `feature/scenario-tests`, созданной от `feature/backend-core`; пуш только этой ветки; merge в `main` делает человек. В сообщениях коммитов нет трейлера `Co-Authored-By`.
- **C-3** Числа кейса и новых типов живут только в `rules/rules.json`; сценарии берут пороги, цены и отступы оттуда, а не из литералов.
- **C-4** В сервисе нет координат, ID и структуры конкретного набора или сценария; правка по дефекту обязана держаться на правиле, а не на геометрии сцены.
- **C-5** Сцены строятся в метрах в EPSG:32637 от локального начала `413000, 6180000` (как в фикстуре валидатора, R-2) и пишутся в EPSG:4326 с девятью знаками.
- **C-6** Допуски сравнения фиксированы: длина 0,05 м, стоимость 1 руб., расход 0,001 т/ч, score 0,001; формульная проверка примера 10.8 (TZ-72) — 100 руб. (R-13); граница длины маршрута задаётся в каждом сценарии явно. Допуски валидатора не меняются.
- **C-7** Гейты запускаются из корня репозитория с `--timeout 1800`; вывод маркеров `SCENARIOS OK`, `SWEEP OK`, `SWEEP TYPES OK`, `SYNTH TYPES OK`, `MUTATION OK`, `COVERAGE OK`, `REPORT OK`, `DEFECTS OK`, `TIME OK`, `RULES EXT MATCH` печатают только Python-модули `heatscen` и скрипты `scripts/gates/*.sh` после всех своих проверок; скрипты начинаются с `set -euo pipefail` и не содержат `|| true`, `|| :` и `exit 0`.
- **C-8** Файлы `docs/specs/backend-core/**` и CONSTRAINTS.md не меняются.
- **C-9** Строки для пользователя (предупреждения CLI, сообщения об ошибках, текст отчёта) на русском; идентификаторы, ключи `rules.json` и имена сценариев на английском: ключи типов `metro`, `railway`, `water_supply`, `sewer`, `power_line_support`, `_fallback`; ID сценариев вида `S<семейство>-<номер>`, например `S01-03`.

## Допущения

Приняты без подтверждения. Если допущение окажется ложным, план меняется.

- **A-1** Один сценарий через CLI занимает около 3 секунд, 120 сценариев — не больше 8 минут подряд — если ложно: сценарии запускаются в три потока `concurrent.futures`, порог NFR-1 не меняется.
- **A-2** Три параллельных JVM для случайного прогона укладывают 250 `small` и 50 `medium` в 10 минут на 11-ядерной машине — если ложно: `--workers 2`, а при выходе за 1500 секунд NFR-1 фиксируется красным в отчёте.
- **A-3** Значения норм для новых типов подходят как поведение по умолчанию; жюри либо не даст этих типов, либо примет обоснование ссылками на СП — если ложно: правится только таблица research.md и `rules.json`.
- **A-4** Жюри назовёт новые типы английскими ключами вида `metro`, `railway`; другие строки попадут в `_fallback` — если ложно: ключи в `rules.json` переименовываются, код не меняется.
- **A-5** Сцену можно построить так, что задуманная врезка и маршрут дешевле любого другого допустимого не меньше чем на 10 % и ожидание однозначно — если ложно: сервис выбрал другой допустимый вариант, ожидание сценария неверно, исправляется сценарий, а не сервис; случай записывается в журнал.
- **A-6** Валидатор и `ObstacleSet` работают с ограничением-точкой через буфер так же, как с полигоном — если ложно: правка одной функции в `space.py` и в `ObstacleSet`.
