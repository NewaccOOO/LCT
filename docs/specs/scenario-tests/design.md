# Дизайн: сценарный прогон модели трассировки

## Контекст и масштаб

Сервис, валидатор и генератор из backend-core готовы. Валидатор проверяет любой выход по 15 правилам (R-3), но он не знает, какой ответ правильный для конкретной сцены: врезка в существующую камеру или новая камера рядом, реконструкция на 75 м или на 114 м. Генератор не умеет ставить объекты в заданные точки (R-4). Нужна своя библиотека сцен и ожиданий, прогон через CLI (R-1) и три вспомогательных инструмента: мутации, случайный прогон, отчёт. Плюс правки сервиса по R-10 и R-11. Оракул сценариев обоснован в [ADR-0001](adr/0001-scenario-oracle.md).

## Решение

Один Python-пакет `heatscen` в `tools/scenarios/` рядом с `heatsynth` и `heatcheck`. Сцена описывается в метрах и превращается в GeoJSON тем же способом, что фикстура валидатора. Ожидание сценария — набор решающих фактов о выходе, каждый сравнивается по своему правилу; поверх них к каждому выходу применяются все 15 правил валидатора. Сценарии живут в модулях по семействам, чтобы параллельные агенты не правили один файл. Мутационная проверка гарантирует, что ожидания не пустые, случайный прогон — что правки по дефектам не сломали общий случай, отчёт — что покрытие условий ТЗ видно без чтения кода.

- **D-1** Структура — закрывает C-1, AC-1.1.

  ```text
  tools/pyproject.toml                       packages += "scenarios/heatscen"
  tools/scenarios/heatscen/
    __init__.py
    scene.py          Scene: source, pipe, chamber, oks, existing_oks, restriction, to_geojson
    expect.py         Expect и функции сравнения, check(run, expect, rules) -> list[str]
    runner.py         run(scene) -> Run: CLI через subprocess, кэш в data/scenarios/<id>/
    registry.py       @scenario(id, tz, title), load_all() импортирует families/*
    families/         s01_tie_in.py … s14_types.py — по одному модулю на семейство
    mutate.py         python -m heatscen.mutate
    sweep.py          python -m heatscen.sweep --seeds 300 --workers 3
    report.py         python -m heatscen.report [--check]
    rules_ext.py      python -m heatscen.rules_ext <research.md> <rules.json>
  tests/scenarios/
    conftest.py       фиксация результатов в data/scenarios/results.json
    test_scenarios.py parametrize по load_all(), pytest id = "<id>-<slug>"
  scripts/gates/scenarios.sh, sweep.sh, synth_types.sh
  docs/testing/scenario-report.md, defects.md
  data/scenarios/    кэш прогонов, last-run.json, sweep.json (вне git: data/* уже в .gitignore)
  ```

- **D-2** Сцена (`scene.py`) — закрывает C-5, AC-1.2. Координаты в метрах от локального начала `413000, 6180000` (EPSG:32637), перевод в EPSG:4326 через `pyproj.Transformer`, девять знаков. Методы: `source(id, x, y)`, `pipe(id, points, dn, flow, upstream)` — LineString из двух и более точек, `chamber(id, x, y, dn, upstream)`, `oks(id, cp, flow, polygon=None, heat_load=None, away=None)` — по умолчанию квадрат 20 м, середина ближней стороны которого совпадает с точкой подключения, а сам квадрат лежит в направлении от источника сцены к точке подключения; `away=(dx, dy)` задаёт это направление явно; `polygon` принимает список колец для MultiPolygon, `existing_oks(id, polygon)`, `restriction(id, type, geom)` — Point, LineString, MultiLineString, Polygon, MultiPolygon, `raw(feature)` для сценариев на битый вход. `scene_hash()` — SHA-256 сериализованного GeoJSON, по нему AC-1.2 отличает сценарии. Числа (диаметры, пропускная способность, цены) сценарии берут из `rules/rules.json` через `heatscen.rules()`.

- **D-3** Ожидание (`expect.py`) — закрывает AC-1.1, AC-1.3. `Expect` — dataclass, все поля необязательные; сценарий обязан задать хотя бы одно. Сравнение идёт с вариантом `rank = 1`, если поле не говорит иначе.

  | Поле | Что проверяет | Допуск |
  |---|---|---|
  | `tie_ins` | список `{existing_object_id, existing_object_type, required_diameter?, existing_diameter?}`; число врезок равно длине списка | точное |
  | `new_chambers` | число новых камер или список их `diameter` | точное |
  | `segment_dn` | `{cp_id: dn}` — диаметр участка, который заканчивается в точке подключения | точное |
  | `dn_used` | множество диаметров новых участков | точное |
  | `special` | `{restriction_type: n}` — не меньше `n` участков `special`, лежащих в зоне объектов этого типа | точное |
  | `no_special` | все участки `base` | — |
  | `technical_nodes` | число технических узлов | точное |
  | `recon` | список `{existing_object_id, required_diameter, length, added_flow_tph}` | длина 0,05 м, расход 0,001 |
  | `no_recon` | реконструкций нет | — |
  | `chamber_recon` | список `{existing_object_id, required_diameter, cost}` | стоимость 1 руб. |
  | `unconnected`, `penalty` | список ID и штраф | штраф 1 руб. |
  | `variants` | `(min, max)` число вариантов; `distinct_tie_in_sets` — наборы `existing_object_id` попарно различны | — |
  | `max_new_length` | `new_network_length` варианта 1 не больше | — |
  | `summary` | `{поле: значение}` сводки варианта 1 | по C-6 |
  | `costs_by_formula` | `cost` каждого участка равен `length × new_rub_m(dn) × k` с `k` по зонам сцены | 1 руб. (100 руб. для TZ-72) |
  | `exit_code`, `diagnostics`, `stderr_contains`, `no_output` | для сценариев входа: код CLI, пары `(featureId, field)`, подстроки stderr, отсутствие файла | точное |

  `check()` возвращает список сообщений, каждое начинается с имени поля и двоеточия: `tie_ins: врезка в hc-2, ожидалась hc-1`. По этому префиксу `mutate.py` понимает, какое поле отвергло мутацию. Зоны специальных объектов для `special` и `costs_by_formula` сценарная библиотека считает сама из сцены: полигон — `buffer(margin_m)`, линия — круг радиуса `margin_m` вокруг точек пересечения оси с трассой; участок лежит в зоне, если его середина внутри зоны; `k` участка — наибольший `k_special` среди зон, в которых он лежит.

  Если `exit_code` не задан или равен 0, к выходу применяется `heatcheck.validate.run_all`, и любое нарушение любого правила — провал сценария. Отключить валидатор сценарий не может.

- **D-4** Прогон (`runner.py`, `test_scenarios.py`) — закрывает AC-1.1, NFR-1. `run(scene)` пишет `input.geojson`, запускает `java -jar target/heatnet.jar --cli` (путь jar из переменной `HEATNET_JAR`, по умолчанию `target/heatnet.jar`), сохраняет `output.geojson` и `run.json` (код, stdout, stderr, время, хеш сцены, mtime jar). Кэш действителен при совпадении хеша и mtime, так повторный `pytest -k` не гоняет всё заново. `test_scenarios.py` параметризован по `load_all()` с id `"<id>-<slug>"`, поэтому `-k S14`, `-k required_diameter`, `-k unknown_type` выбирают сценарии по ID и slug. `conftest.py` собирает статус и время каждого сценария в `data/scenarios/results.json`; `scripts/gates/scenarios.sh` подключает `env.sh`, вызывает `ensure_jar`, запускает pytest, и при запуске без аргументов переписывает `results.json` в `last-run.json` с общим временем. Маркер `SCENARIOS OK passed=<n> failed=0 skipped=0` печатается только при нуле упавших, пропущенных и `xfail`.

- **D-5** Мутации (`mutate.py`) — закрывает AC-1.3. Для каждого сценария берётся кэш `run.json` и `output.geojson`; для каждого заданного поля `Expect` применяется своя мутация, и ожидается, что `check()` вернёт сообщение с префиксом именно этого поля. Мутация меняет объект, на который ссылается ожидание; для нулевого или пустого ожидания она добавляет лишний объект:

  | Поле | Мутация при непустом ожидании | Мутация при нулевом или пустом |
  |---|---|---|
  | `tie_ins` | `existing_object_id` первой ожидаемой врезки заменяется на несуществующий | добавляется копия любой врезки с новым `id` |
  | `new_chambers` | удаляется одна новая камера | добавляется новая камера в точке первой врезки |
  | `segment_dn` | диаметр участка, который заканчивается в указанной точке подключения, поднимается на ступень | — |
  | `dn_used` | диаметр участка с наименьшим `dn` поднимается на ступень | — |
  | `special` | у первого участка в зоне указанного типа `laying_method` меняется на `base` | — |
  | `no_special` | — | `laying_method` первого участка меняется на `special` |
  | `technical_nodes` | удаляется один узел | добавляется узел в точке первой врезки |
  | `recon` | удаляется реконструкция первого ожидаемого `existing_object_id` | — |
  | `no_recon` | — | добавляется копия первого нового участка как реконструкция |
  | `chamber_recon` | `cost` первой ожидаемой записи + 5 | добавляется запись для камеры первой врезки |
  | `unconnected` | список очищается | в список добавляется ID первого ОКС сцены |
  | `penalty` | штраф обнуляется | штраф + 1 |
  | `variants` | удаляется вариант с наибольшим `rank`; при `max` — добавляется копия варианта 1 с новым `rank` | — |
  | `max_new_length` | `new_network_length` варианта 1 становится больше границы на 1 | — |
  | `summary` | каждое ожидаемое поле сводки + 5 | — |
  | `costs_by_formula` | `cost` первого участка + 5 | — |
  | `exit_code` | код меняется на 0, если ожидался ненулевой, иначе на 2 | — |
  | `diagnostics`, `stderr_contains` | stderr очищается | — |
  | `no_output` | — | создаётся пустой выходной файл |

  Сценарий без единого поля считается непойманным. Итог: `MUTATION OK scenarios=<n> expectations=<m> missed=0`.

- **D-6** Случайный прогон (`sweep.py`, `synth_types.sh`) — закрывает AC-2.1, AC-2.2. Генератор получает флаги `--types a,b,c` (какие `restriction_type` размещать; бюджет `restriction_budget` делится между перечисленными, типы вне списка не размещаются) и `--id-prefix p_` (все `id` и ссылки `oks_id`, `upstream_object_id` с префиксом). В списки типов генератора добавляются `metro` и `power_line_support` (полигон и точка, запрет), `railway` (полоса как трамвай, специальный проход), `water_supply` и `sewer` (линии как газопровод). Значения `--types` — только `restriction_type`; существующие ОКС и сеть генератор ставит всегда. Подмножество по сиду: `seed % 4 == 0` — все 13 типов; `1` — восемь исходных: `park, social_area, prohibited_site, water, road, tram_tracks, gas_pipeline, power_cable`; `2` — только запреты: `park, social_area, prohibited_site, water, metro, power_line_support`; `3` — только специальные проходы: `road, tram_tracks, gas_pipeline, power_cable, railway, water_supply, sewer`. Пресет `medium` для сидов, кратных 6, иначе `small`. `sweep.py` гонит сиды в `concurrent.futures.ThreadPoolExecutor(workers)`, для каждого: генератор, CLI, `run_all` по всем 15 правилам, подсчёт специальных участков и реконструкций; пишет `data/scenarios/sweep.json` и печатает `SWEEP TYPES OK subsets=4` и `SWEEP OK seeds=300 failed=0 special=<s> recon=<r>`. `synth_types.sh` за секунды проверяет только генератор: четыре подмножества, состав типов, префикс, детерминизм, `heatsynth.check` — маркер `SYNTH TYPES OK subsets=4`.

- **D-7** Отчёт (`report.py`) — закрывает AC-1.2, AC-4.1, AC-4.2, NFR-1. Входы: `tz-inventory.md` (парсинг таблицы, ID и скоуп), реестр сценариев (ID, TZ, хеш сцены, число полей `Expect`), `last-run.json`, `sweep.json`, `docs/testing/defects.md`. Выход `docs/testing/scenario-report.md`: матрица «TZ → условие → сценарии → вердикт»; сводка по семействам с числом сценариев и вердиктов; итог случайного прогона с разбивкой по подмножествам (число сидов, упавших, специальных участков, реконструкций); таблица дефектов. В отчёте нет даты, хеша коммита и времени прогона, иначе пересборка никогда не совпадёт с закоммиченным файлом. Строки инвентаря, у которых в первой колонке не один ID вида `TZ-n` (диапазон `TZ-73 … TZ-85`), парсер пропускает. `--check` пересобирает отчёт, сравнивает с файлом и печатает по одному маркеру на проверку: `COVERAGE OK items=<n> uncovered=0`, `DEFECTS OK rows=<n>`, `TIME OK elapsed=<s>s` (целые секунды, сумма времени из `last-run.json` и `sweep.json`, не из текста отчёта), `REPORT OK`. Любой провал — маркер `... FAILED` с причиной и код выхода 1.

- **D-8** Правки сервиса и валидатора — закрывает AC-3.1…AC-3.4, AC-0.1.
  - `rules/rules.json`: ключи `metro`, `railway`, `water_supply`, `sewer`, `power_line_support`, `_fallback` со значениями таблицы research.md; прочерк в таблице означает, что ключа у правила нет. У линейных `water_supply` и `sewer` `half_width_m: 0.0`, потому что габарит во входе не передаётся и отсчёт идёт от оси.
  - `Rules.restriction(type)` возвращает правило типа, а для неизвестного — `_fallback`; добавляется `isKnown(type)`. Код, который перебирает типы ограничений как справочник (валидатор, генератор, `rules_check`), пропускает ключи, начинающиеся с `_`.
  - `GeoJsonStreamReader`: неизвестный `restriction_type` больше не диагностика; объект читается с любой допустимой геометрией; `InputData` получает `warnings: List<String>` с одной готовой строкой на тип по формату AC-3.3. `CliRunner` печатает предупреждения в stderr перед расчётом; `JobWorker` пишет их в лог, задача идёт дальше.
  - `ObstacleSet` и сборка: правило берётся через `Rules.restriction`, точечные объекты буферизуются как полигоны.
  - `NetworkAssembler`: `tie_in.required_diameter` равен диаметру первого нового участка от врезки. `heatcheck/tree.py`: `chamber_required` и `pipe_required` заменяются на ту же величину. `docs/interpretation.md`: строка про `required_diameter` переписана, добавлен абзац про `_fallback` и новые типы. `tests/validator/build_fixture.py` и фикстуры пересчитаны, тесты `test_rules.py` поправлены.
  - `heatcheck/space.py`: правило типа берётся из `rules["restrictions"]` с `_fallback` для остальных; ограничение-точка буферизуется.

- **D-9** Триаж красного сценария — закрывает G-3, AC-4.2. Красный сценарий сначала перепроверяется руками: ожидание пересчитывается по ТЗ и `interpretation.md`. Если ожидание неверно (A-5) — правится сценарий, запись в журнал «Отклонения и находки». Если сервис нарушает правило ТЗ — правится сервис, строка в `docs/testing/defects.md` (сценарий, симптом, причина, коммит), после правки гоняются `scenarios.sh`, `sweep.sh` и гейты backend-core. Если ТЗ допускает оба прочтения — выбирается более строгое, записывается в `interpretation.md` и в журнал; валидатор и сценарий приводятся к нему.

- **D-10** Состав семейств — закрывает AC-1.2, G-1. Минимум по семействам — требование к леджеру листа, сумма минимумов 170; гейт пакета AC-1.1 требует 120 сценариев всего, это нижняя планка на случай, если семейство не добрало. ID сценариев `S<семейство>-<номер>`.

  | Семейство | Модуль | Что проверяет | TZ | Минимум |

## Альтернативы

- Golden-файлы (полный ожидаемый выход на сцену) — отклонены: любое допустимое изменение маршрута ломает все файлы, а ошибку в ожидании не отличить от ошибки сервиса.
- Только валидатор без собственных ожиданий — отклонён: валидатор пропускает решения, которые допустимы по правилам, но не те, что задумано сценой (новая камера вместо существующей, лишняя врезка).
- JUnit через `VariantEnumerator` — отклонён по Q-5: ожидания считались бы тем же кодом, что и сервис.
- `pytest-xdist` для параллельности — отклонён по NG-8, stdlib достаточно.
- Расширение генератора функциями размещения — отклонено: генератор устроен вокруг случайного размещения с проверками зазоров (R-4), сцена в 30 строк на Python проще.

## Выкатка, откат, наблюдаемость

- **Включение и выключение:** прогон запускается вручную скриптами гейтов; в непрерывную интеграцию этим пакетом не подключается.
- **Откат:** правки сервиса по D-8 — отдельные коммиты в `feature/scenario-tests`, откатываются `git revert`; `rules.json` без новых ключей продолжает работать с прежним кодом.
- **Сигналы отката:** красный `AC-0.1` после правки сервиса; рост времени `medium` в `perf.sh` выше 120 с.
- **Отказ зависимости:** без jar `scenarios.sh` собирает его через `ensure_jar`; без `uv`-окружения команды не запускаются, это фиксируется в отчёте как ошибка тулчейна.

## Где можно застрять

- Сервис выбирает допустимую, но не задуманную врезку → A-5: сцена перестраивается так, чтобы разрыв стоимости был не меньше 10 %, ожидание не ослабляется до «любая врезка».
- Мутация ловится валидатором, а не ожиданием сценария → `mutate.py` проверяет только поля `Expect`, валидатор при мутациях не запускается.
- Точечные ограничения в `ObstacleSet` и `space.py` → A-6, буфер точки.
- Кэш прогона переживает правку сервиса → ключ кэша включает mtime jar, `ensure_jar` пересобирает jar при изменении исходников.
- Один `medium`-сид в случайном прогоне зависает → таймаут CLI 300 с на сид, сид засчитывается как упавший.
