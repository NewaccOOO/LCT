# Задачи: сценарный прогон модели трассировки

Критерии — в [requirements.md](requirements.md), гейты — в [GATES.md](GATES.md), решения — в [design.md](design.md).

## Контракт исполнения

- **Режим:** параллельно, unlazy scope `scenario-tests`. Волна 0 и волны 2–4 выполняет драйвер, волну 1 — субагенты, не больше пяти одновременно; T-6 и T-7 стартуют, как только освобождается слот.
- **Тулчейн и команды:** из корня репозитория, всегда после `source scripts/gates/env.sh`. JDK 11, Maven 3.9, `uv run --project tools …`, Docker Desktop для гейтов backend-core. Все гейты пакета запускаются `node ~/.claude/skills/unlazy/scripts/gate-check.mjs --cwd . --timeout 1800 docs/specs/scenario-tests/GATES.md`.
- **Гейты:** `CHECK:` в GATES.md одобрил пользователь до запуска через `gate-check --approve`; исполнитель не одобряет проверки сам. Новый или изменённый гейт добавляется с `ABANDON: <id> нужно одобрение пользователя на новую проверку`, работа продолжается.
- **Ветка:** `feature/scenario-tests` от `feature/backend-core` (C-2). Субагенты работают в отдельных git worktree (`isolation: worktree`), первым действием делают `git merge --ff-only feature/scenario-tests`, коммитят только свои файлы без трейлеров атрибуции и не пушат; драйвер вливает ветку worktree и перепроверяет леджер листа в основном дереве.
- **Интерфейсы** (заполнены до параллельного запуска, менять только через журнал):
  - `heatscen.Scene`, `heatscen.Expect`, `heatscen.scenario` — сигнатуры и поля по D-2, D-3 и примеру в design.md; `heatscen.rules()` возвращает разобранный `rules/rules.json`; `heatscen.runner.run(scene, scenario_id) -> Run(exit_code, stdout, stderr, output, elapsed)`; `heatscen.expect.check(run, expect, rules) -> list[str]` — пустой список означает успех.
  - Модуль семейства `tools/scenarios/heatscen/families/s<NN>_<name>.py` регистрирует сценарии декоратором; ID `S<NN>-<номер>`, поле `tz` — список ID из tz-inventory.md, `title` на русском; slug pytest-id строится из имени функции, поэтому функции про `required_diameter` и `unknown_type` содержат эти слова в имени.
  - Леджер листа с семейством сценариев считает лист готовым, когда: сценариев не меньше минимума D-10, у каждого есть `tz` и не меньше одного поля `Expect`, `pytest -k S<NN>` не даёт ошибок сбора и исключений в сценариях, а каждый красный сценарий разобран по D-9 и либо исправлен, либо записан в `docs/testing/defects.md` с причиной «сервис». Зелёность всех сценариев — гейт пакета AC-1.1, он закрывается в T-9.
  - Скрипты гейтов: `scenarios.sh [аргументы pytest]`, `sweep.sh`, `synth_types.sh` по D-4 и D-6; правила скриптов по C-7.
  - Изменения сервиса и валидатора по D-8 принадлежат T-1; агенты семейств пишут ожидания сразу по ТЗ (например, `required_diameter` равен диаметру нового участка) и не подстраивают их под текущее поведение.

### Отклонения и находки

- 2026-09-15, T-0. Одобрение гейтов перед стартом прогнало `AC-0.1`, и `gate-check --reverify` переписал строки `EVIDENCE` в `docs/specs/backend-core/GATES.md`. Сам гейт AC-0.1 так устроен, поэтому обновление свидетельств в этом файле не считается нарушением C-8: меняются только строки `EVIDENCE`, содержание пакета backend-core остаётся прежним.
- 2026-09-15, T-0, уточнения интерфейсов к «Контракту исполнения». Их читают агенты волны 1:
  - `Scene.oks(...)` возвращает ID точки подключения, он всегда `<id ОКС>-cp`. Несколько колец в `polygon` дают MultiPolygon из отдельных полигонов, одно кольцо — Polygon. `Scene.restriction(id, type, geom)` принимает геометрию shapely в локальных метрах. Функция `heatscen.scene.geojson(geom)` переводит геометрию сцены в GeoJSON EPSG:4326, она нужна для `Scene.raw`.
  - `Run` получил поле `input` (разобранный входной GeoJSON), потому что зоны специальных объектов и отступы считаются по сцене. `heatscen.runner.cached(scenario_id)` читает кэш без запуска CLI, его использует `mutate.py`.
  - `heatscen.expect.check_fields(run, expect, rules)` проверяет только объявленные поля без валидатора; `check()` добавляет правила валидатора. Сообщения валидатора начинаются с `validator:`, сообщения о коде CLI и отсутствии выхода без объявленного поля — с `run:`, сценарий без полей — с `expect:`.
  - В `Expect` три добавления к таблице D-3. `clearance: list[str]` — ID объектов входа (ограничение, `oks_existing`, существующая `heat_network`), до которых каждый новый участок варианта 1 не ближе `clearance + width/2 + half_width_m` по диаметру участка; для неизвестного типа берётся `_fallback`. Нужен семействам S05 и S14, чтобы отступ проверял сам сценарий (T-4). `distinct_tie_in_sets: bool` вынесено из строки `variants` в отдельное поле со своим префиксом. `formula_tol_rub: float = 1.0` — допуск `costs_by_formula`, не ожидание; для TZ-72 ставится 100.
  - `new_chambers=0`, `technical_nodes=0`, `unconnected=[]` считаются объявленными ожиданиями: пустыми считаются только `None` и `False`.
  - `special` считает участки `special`, у которых середина лежит в зоне типа (допуск 0,05 м). `costs_by_formula` берёт `length` из атрибута участка; `k` = 1 для `base`, для `special` — наибольший `k_special` зон, в которых лежит середина.
  - Порог 120 сценариев `scenarios.sh` применяет только к запуску без аргументов. С `-k` маркер печатается при нуле упавших и пропущенных и хотя бы одном прошедшем, а нижнюю границу задаёт регулярное выражение гейта (AC-3.1, AC-3.3, AC-3.4). Иначе гейты с `-k` никогда бы не выполнились.
  - `conftest.py` до тестов прогоняет CLI выбранных сценариев в четыре потока и наполняет кэш; тесты читают кэш.
  - Для `mutate.py` (T-7): мутации, которые сдвигают число на величину допуска или меньше, сравнение не отвергнет. Поэтому числа сдвигаются больше допуска: штраф и `summary` на +5, `costs_by_formula` на `formula_tol_rub + 5`. `dn_used` поднимает на ступень все участки наименьшего диаметра, `special` переводит в `base` все участки в зоне типа, иначе при двух одинаковых объектах мутация проходит незамеченной.
- 2026-09-15, T-0, находка. Сервис требует атрибут `heat_load` у `oks_future` и без него завершается кодом 2 (`oks-1 heat_load: нет обязательного атрибута`). ТП §2.2 перечисляет `heat_load` среди атрибутов ОКС, поэтому это не дефект. `Scene.oks` теперь пишет справочную нагрузку `flow × 0,05`, если сценарий её не задал.
- 2026-09-15, T-0, находка. Валидатор требует от 2 до 3 вариантов (`interpretation.md`, «Вариантов всегда от 2 до 3»; backend-core AC-2.12), а сервис на сценах «одна труба DN 200 и один ОКС» и «камера на конце трубы и один ОКС» выдаёт один вариант. Выбран более строгий путь: сервис выдаёт второй содержательно отличающийся вариант, когда существует другой объект врезки или точка на той же трубе дальше 20 м. Правка поручена листу 1.1 (ревизия 1 PLAN.md), файлы те же. Агентам семейств сказано строить сцены со вторым кандидатом врезки.
