# Требования: бекенд трассировки тепловых сетей

Цели и границы — в [brief.md](brief.md), факты — в [research.md](research.md), решения — в [design.md](design.md). Правила кейса — в [CONSTRAINTS.md](../../../CONSTRAINTS.md), разделы указаны по нему. Все команды проверки запускаются из корня репозитория; скрипты в `scripts/gates/` сами подключают `env.sh`, при ручном запуске Maven сначала `source scripts/gates/env.sh`.

## Истории и критерии приёмки

### US-1: Фронт и эксперт загружают файл через REST и получают результат, чтобы не запускать расчёт руками (P1, цель G-1)

- **AC-1.1** WHEN клиент отправляет `POST /api/v1/jobs` с телом GeoJSON THE SYSTEM SHALL сохранить тело на диск потоком и ответить `202` с `{"id", "status": "QUEUED"}`; IF тело пустое или первый значащий байт не `{` THEN THE SYSTEM SHALL ответить `400` — проверка: `scripts/gates/api.sh AC-1.1` печатает `API AC-1.1 OK`.
- **AC-1.2** WHEN клиент запрашивает `GET /api/v1/jobs/{id}` THE SYSTEM SHALL вернуть статус из набора `QUEUED`, `RUNNING`, `DONE`, `FAILED`, времена и после `DONE` массив `summary` со сводками вариантов; для неизвестного id `404` — проверка: `scripts/gates/api.sh AC-1.2` печатает `API AC-1.2 OK`.
- **AC-1.3** WHEN задача в статусе `DONE` THE SYSTEM SHALL отдавать `GET /api/v1/jobs/{id}/result` как файл `application/geo+json`, который валидатор принимает по правилу `schema`; `GET /api/v1/jobs/{id}/input` отдаёт исходный файл байт в байт; в любом статусе кроме `DONE` результат отвечает `409` — проверка: `scripts/gates/api.sh AC-1.3` печатает `API AC-1.3 OK`.
- **AC-1.4** IF во входном файле у фичи нет обязательного атрибута раздела 12, значение не того типа (для `integer` нецелое число тоже ошибка), `id` повторяется, `oks_id` или `upstream_object_id` ссылается на несуществующий объект THEN THE SYSTEM SHALL завершить задачу статусом `FAILED` с `error.errors[]`, где у каждой записи есть `featureId` (при отсутствии `id` — порядковый номер фичи в виде `#<n>`), `field`, `problem`, и не создавать результат — проверка: `scripts/gates/api.sh AC-1.4` печатает `API AC-1.4 OK`.

### US-2: Сервис строит варианты подключения по правилам кейса, чтобы эксперты не нашли нарушений формальных правил (P1, цель G-1)

Каждый критерий проверяется валидатором на выходах сервиса для шести синтетических наборов (пресеты `small` и `medium`, сиды 1–3), см. D-14. Команда `scripts/gates/validate_rule.sh <rule>` при отсутствии выходов сначала запускает `scripts/gates/produce.sh` и печатает `RULE <rule>: PASSED` только если нарушений нет во всех шести файлах.

- **AC-2.1** THE SYSTEM SHALL обработать все перспективные ОКС за один запуск: каждый ОКС либо соединён путём от точки врезки, либо перечислен в `unconnected_oks_ids` со штрафом; на синтетических наборах список пуст — проверка: `scripts/gates/validate_rule.sh coverage` печатает `RULE coverage: PASSED`.
- **AC-2.2** THE SYSTEM SHALL выполнять врезку в существующей камере только если точка врезки не дальше 10 м от неё и после подключения к камере примыкает не больше четырёх участков, иначе ставить новую камеру в точке врезки (раздел 5) — проверка: `scripts/gates/validate_rule.sh tie_in` печатает `RULE tie_in: PASSED`.
- **AC-2.3** THE SYSTEM SHALL строить новую сеть деревом: от врезки до каждого ОКС ровно один путь, ветвления только в камерах, у камеры не больше четырёх участков и трёх ответвлений, новые участки не пересекаются между собой вне общих узлов — проверка: `scripts/gates/validate_rule.sh topology` печатает `RULE topology: PASSED`.
- **AC-2.4** THE SYSTEM SHALL присваивать участку расход, равный сумме `flow_tph` всех ОКС ниже по дереву, с расхождением не больше 0,001 т/ч — проверка: `scripts/gates/validate_rule.sh flow` печатает `RULE flow: PASSED`.
- **AC-2.5** THE SYSTEM SHALL выбирать участку минимальный диаметр из таблицы раздела 6, у которого пропускная способность не меньше расхода участка; диаметр больше минимального допустим только если цепочка на минимальном диаметре нарушила бы AC-2.6, и тогда он на одну ступень выше — проверка: `scripts/gates/validate_rule.sh diameter` печатает `RULE diameter: PASSED`.
- **AC-2.6** THE SYSTEM SHALL держать длину непрерывной цепочки участков одного диаметра не больше предельной длины этого диаметра; камера и технический узел без смены диаметра цепочку не прерывают — проверка: `scripts/gates/validate_rule.sh length_limit` печатает `RULE length_limit: PASSED`.
- **AC-2.7** THE SYSTEM SHALL для всех 10 типов ограничений раздела 7: не пересекать объекты с правилом «запрещено» и держать от их границы отступ не меньше `clearance + width/2`; пересекать объекты с правилом «специальный проход» только участками `laying_method = special`, где специальный участок это пересечение трассы с объектом, буферизованным на `margin_m`, а угол между трассой и стороной полигона дороги или трамвайных путей в точках входа и выхода не меньше 45°; отступ `clearance` от объекта «специальный проход» проверяется только для обычных участков, не смежных со специальным участком через этот объект — проверка: `scripts/gates/validate_rule.sh forbid` печатает `RULE forbid: PASSED` и `scripts/gates/validate_rule.sh special` печатает `RULE special: PASSED`.
- **AC-2.8** THE SYSTEM SHALL прокидывать добавленный расход каждой врезки по цепочке `upstream_object_id` до источника, суммировать расходы разных врезок на общих участках, для врезки внутри участка учитывать только часть к источнику, и выдавать объект `heat_network_reconstruction` для каждой части, где требуемый диаметр больше существующего, и ни для одной другой — проверка: `scripts/gates/validate_rule.sh reconstruction` печатает `RULE reconstruction: PASSED`.
- **AC-2.9** THE SYSTEM SHALL выдавать `heat_chamber_reconstruction` только для камер врезки, у которых наибольший примыкающий диаметр после подключения больше входного, один раз на камеру, со стоимостью по шкале раздела 9 — проверка: `scripts/gates/validate_rule.sh chamber_recon` печатает `RULE chamber_recon: PASSED`.
- **AC-2.10** THE SYSTEM SHALL считать `cost` каждого объекта по формулам раздела 9 так, что пересчёт валидатором расходится не больше чем на 1 руб., а суммы в `variant_summary` сходятся с суммами объектов варианта — проверка: `scripts/gates/validate_rule.sh cost` печатает `RULE cost: PASSED`.
- **AC-2.11** THE SYSTEM SHALL считать `score` по формуле раздела 10 с расхождением не больше 0,001 и присваивать `rank` по возрастанию `score` начиная с 1 — проверка: `scripts/gates/validate_rule.sh score` печатает `RULE score: PASSED`.
- **AC-2.12** WHEN во входе есть не меньше двух кандидатов врезки для кластера ОКС THE SYSTEM SHALL выдать не меньше двух и не больше трёх вариантов, где любые два различаются набором врезок (другой `existing_object_id` или точка дальше 20 м от всех врезок другого варианта) или разбиением ОКС по деревьям — проверка: `scripts/gates/validate_rule.sh variants` печатает `RULE variants: PASSED`.
- **AC-2.13** THE SYSTEM SHALL строить участки прямыми отрезками: нет вершин с отклонением меньше 3°, нет подотрезков короче 1 м, кроме смежных со специальным участком, число поворотов (вершин с отклонением 3° и больше, включая камеры и узлы) на пути от врезки до ОКС не больше `3k + 4`, где `k` число полигонов с правилом «запрещено» плюс полигонов дорог и трамвайных путей на прямой между ними — проверка: `scripts/gates/validate_rule.sh geometry` печатает `RULE geometry: PASSED`.

### US-3: Команда проверяет любой выходной файл независимым валидатором, чтобы находить нарушения правил до экспертов (P1, цель G-2)

- **AC-3.1** WHEN запускается `uv run --project tools python -m heatcheck <input> <output>` THE SYSTEM SHALL напечатать таблицу по 15 правилам D-14 с числом нарушений и первыми примерами и завершиться кодом 0 с `VALIDATION PASSED` либо кодом 1 с `VALIDATION FAILED: <правила>`; флаг `--only <rule>` проверяет одно правило и печатает `RULE <rule>: PASSED` или `RULE <rule>: FAILED (<n>)` — проверка: `scripts/gates/validate_rule.sh schema` печатает `RULE schema: PASSED`.
- **AC-3.2** THE SYSTEM SHALL для каждого из 15 правил иметь тест, параметризованный именем правила из списка `heatcheck.RULES`, который портит корректную фикстуру в памяти, запускает валидатор через тот же код, что и CLI `--only`, и ожидает `FAILED` именно этого правила; все тесты проходят — проверка: `uv run --project tools pytest -q tools/validator/tests` печатает строку `<n> passed in <t>s` без других статусов, `n` не меньше 15.
- **AC-3.3** THE SYSTEM SHALL держать таблицы и коэффициенты в `rules/rules.json`, и скрипт сверки парсит таблицы и формулы CONSTRAINTS.md и находит те же значения для 18 диаметров по семь полей, четырёх ценовых диапазонов камер, десяти правил ограничений, стоимости врезки, штрафа, коэффициентов score и правила 10 м и четырёх участков — проверка: `uv run --project tools python -m heatcheck.rules_check CONSTRAINTS.md rules/rules.json` печатает `RULES MATCH`.

### US-4: Команда генерирует синтетические наборы, чтобы тестировать и показывать сервис до получения конкурсного набора (P1, цель G-3)

- **AC-4.1** WHEN запускается `uv run --project tools python -m heatsynth --preset <small|medium|large> --seed <n> --out <file>` THE SYSTEM SHALL записать FeatureCollection в EPSG:4326 со всеми семью типами объектов раздела 12 и всеми восемью значениями `restriction_type` раздела 7, где `id` и остальные атрибуты лежат в `properties`, у каждой фичи есть обязательные атрибуты своего типа и нет чужих, а два запуска с одним сидом дают одинаковые файлы — проверка: `scripts/gates/synth.sh` печатает `SYNTH SCHEMA OK`.
- **AC-4.2** THE SYSTEM SHALL в пресете `medium` давать 20 перспективных ОКС, не меньше 200 ограничений со стороной не меньше 20 м у полигонов, не меньше 300 участков сети; не меньше чем у 10 ОКС прямая от точки подключения до ближайшего участка сети пересекает запрещённый полигон и не меньше чем у 5 — полигон дороги или трамвайных путей; у каждого ОКС не меньше двух существующих камер в радиусе 500 м; у ближайшего к каждому ОКС участка сети текущий расход не меньше 80 % пропускной способности его диаметра — проверка: `scripts/gates/synth.sh` печатает `SYNTH MEDIUM OK`.
- **AC-4.3** THE SYSTEM SHALL строить существующую сеть так, что цепочка `upstream_object_id` от каждого участка и камеры заканчивается на `source`, расход и диаметр участков к источнику не убывают, и диаметр камеры равен максимуму примыкающих участков — проверка: `scripts/gates/synth.sh` печатает `SYNTH NETWORK OK`.

### US-5: Организатор разворачивает сервис одной командой, чтобы проверить его на своём стенде (P1, цель G-4)

- **AC-5.1** WHEN выполняется `docker-compose up -d --build` с файлом формата `3.8` THE SYSTEM SHALL поднять приложение и PostgreSQL, `GET /actuator/health` отвечает `UP`, `GET /v3/api-docs` и `GET /swagger-ui/index.html` отвечают `200`, в `api-docs` есть пять операций из таблицы интерфейсов design.md — проверка: `scripts/gates/compose.sh` печатает `COMPOSE OK`.
- **AC-5.2** THE SYSTEM SHALL собираться и проходить все тесты командой `mvn verify`, при этом по XML-отчётам surefire и failsafe выполнено не меньше 30 тестов и ни один не пропущен — проверка: `scripts/gates/mvn_verify.sh` печатает `MVN VERIFY OK tests=<n> skipped=0`, гейт требует `n` не меньше 30.

### US-0: Что не должно измениться

- **AC-0.1** CONSTRAINTS.md в ветке исполнителя байт в байт совпадает с `main` — проверка: `scripts/gates/constraints_unchanged.sh` печатает `CONSTRAINTS UNCHANGED`.

## Нефункциональные требования

- **NFR-1** Расчёт пресета `medium` через CLI D-16 занимает не больше 120 секунд стенных часов на машине исполнителя для каждого из сидов 1–3 — источник числа: Q-10, допущение A-1; замер: `scripts/gates/perf.sh` печатает `PERF medium OK max=<s>s`.
- **NFR-2** Задача с входным файлом не меньше 300 МБ (пресет `small` с `--pad-mb 300`, лишний объём это далёкие полигоны `park`) завершается `DONE` при запуске приложения с `-Xmx1g` — источник числа: раздел 2 CONSTRAINTS.md требует потоковую обработку до 3 ГБ, 300 МБ при 1 ГБ кучи это та же пропорция для 16 ГБ ОЗУ, допущение A-2; замер: `scripts/gates/api.sh NFR-2` печатает `API NFR-2 OK`.
- **NFR-3** Пять задач пресета `small`, отправленных одновременно, все переходят в `DONE` не позже чем через 180 секунд — источник числа: раздел 2 CONSTRAINTS.md, 50 пользователей, допущение A-2; замер: `scripts/gates/api.sh NFR-3` печатает `API NFR-3 OK`.

## Ограничения

- **C-1** Стек организатора: Java 11, `spring-boot-starter-parent` 2.6.3, springdoc-openapi-ui 1.7.0, docker-compose файл формата `3.8`, развёртывание на Ubuntu Server 22. Версии из research.md: jts-core 1.20.0, proj4j 1.4.3 с proj4j-epsg, jgrapht-core 1.5.3, Testcontainers 1.21.4, surefire и failsafe 3.x.
- **C-2** База PostgreSQL 16 без PostGIS; в ней только таблица задач.
- **C-3** Все числа кейса живут в `rules/rules.json`; в Java и Python нет литералов диаметров, цен, коэффициентов и отступов вне этого файла и тестов сверки.
- **C-4** В коде нет координат, ID и структуры конкретного набора данных; все наборы приходят через API или аргументы CLI.
- **C-5** Валидатор и генератор на Python 3.12 или новее в `tools/` (uv ставит 3.13), зависимости shapely 2.1 и pyproj 3.7.1 или новее через `uv`; Java из них не вызывается.
- **C-6** Git: работа в ветке `feature/backend-core`, пуш только этой ветки, merge в `main` делает человек. В сообщениях коммитов нет трейлера `Co-Authored-By`.
- **C-7** Тулчейн ставится исполнителем: `brew install openjdk@11 maven`, Python-окружение через `uv`; `scripts/gates/env.sh` экспортирует `JAVA_HOME` и `PATH`.
- **C-8** Конкурсный набор данных конфиденциален (R-14): каталог `data/` кроме `data/samples/` в `.gitignore`, в репозиторий попадают только синтетические файлы.
- **C-9** Строки для пользователя (сообщения об ошибках API, описания в Swagger) на русском; имена классов, методов, полей JSON на английском. Поля выходного GeoJSON строго по разделу 13.

## Допущения

Приняты без подтверждения. Если допущение окажется ложным, план меняется.

- **A-1** Порог 120 секунд на `medium` подходит для показа вживую и для очереди задач — если ложно: порог NFR-1 меняет пользователь, алгоритм не меняется.
- **A-2** Пропорция 300 МБ на 1 ГБ кучи и пять одновременных задач представляют требования «3 ГБ» и «50 пользователей» — если ложно: стенд организатора упрётся в память, спасает `JOB_WORKERS=1`.
- **A-3** ТЗ в личном кабинете не требует ничего сверх PDF: репозиторий, стенд и формат презентации остаются на усмотрение команды — если ложно: добавляется отдельный пакет под требования сдачи.
- **A-4** Ошибка proj4j для UTM 37N меньше 1 мм и не влияет на отступы в 1 м — если ложно: заменяется на формулу Крюгера в `Projector`, интерфейс не меняется.
- **A-5** Testcontainers 1.21.4 работает с Boot 2.6.3 — если ложно: интеграционные тесты берут PostgreSQL из `docker-compose.yml`, гейты не меняются.
- **A-6** Синтетические наборы по структуре совпадают с конкурсным, потому что оба следуют разделу 12 — если ложно: правится только генератор.
- **A-7** Угол пересечения дороги измеряется между отрезком трассы и стороной полигона дороги в точке входа и выхода — если ложно: меняется одна функция в `graph` и одна в валидаторе.
- **A-8** Файл compose формата `3.8` без ключей, появившихся в compose v2, читается docker-compose 1.29.2 на стенде организатора (R-15); гейт проверяет только формат файла и работу под compose v2 — если ложно: правится один файл `docker-compose.yml`.
- **A-9** Ориентация LineString существующей сети во входных данных не задана; конец, обращённый к источнику, определяется как ближайший к геометрии объекта `upstream_object_id`, совпадение точек с допуском 0,5 м — если ложно: меняется `GeoJsonStreamReader`.
