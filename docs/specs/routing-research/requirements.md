# Требования: ресёрч алгоритмов трассировки и правил разумной трассы

Цели и границы — в [brief.md](brief.md), факты — в [research.md](research.md). Все команды запускаются из корня worktree; `uv run --project tools/research …` — отдельный проект прототипов.

## Истории и критерии приёмки

### US-1: Команда видит, насколько текущий алгоритм и кандидаты далеки от оптимума, чтобы выбрать, что внедрять (P1, цели G-1, G-2)

- **AC-1.1** WHEN выполняется `uv run --project tools/research python -m heatopt.bench --check` THE SYSTEM SHALL прочитать `data/research/scenes.json` (90 сцен: по 30 классов S, M, L с сидами и хешами входных файлов) и `data/research/results.json` и напечатать `BENCH OK scenes=90 service=90 candidates=4 exact=<e> lp=90` только если для каждой сцены есть результат сервиса (через CLI jar) и каждого из четырёх кандидатов в обоих режимах (`quality=off` и `quality=on`, C-3), LP-граница есть на всех 90 сценах, точный MILP запускался на всех 60 сценах S и M с лимитом 1200 с и `e` сцен решено до доказанного оптимума, а на трёх сценах, выбранных по хешу `results.json`, сервис и кандидаты пересчитаны на месте с записанными `seed` и `budget` (детерминированный бюджет итераций, не секунды) и их S совпали с записанными с точностью 0,001; MILP при проверке не пересчитывается, сверяется хеш его лога — проверка: команда печатает `BENCH OK scenes=90 service=90 candidates=4 exact=<e> lp=90`, гейт требует `e` не меньше 40.
- **AC-1.2** THE SYSTEM SHALL для рекомендованного кандидата в режиме `quality=off` иметь на сценах S и M с доказанным оптимумом средний разрыв по показателю S из раздела 10 CONSTRAINTS.md не больше 1 % и максимальный не больше 3 %, при не меньше 20 таких сцен в каждом из классов S и M, где разрыв = max(0, S_кандидата − S_оптимума) / S_оптимума — проверка: `uv run --project tools/research python -m heatopt.bench --check` печатает `GAP OK candidate=<имя> mean=<x>% max=<y>% scenes_s=<n> scenes_m=<m>`.
- **AC-1.3** THE SYSTEM SHALL в `docs/research/routing-benchmark.md` дать таблицу «алгоритм × класс сцен → средний, медианный и максимальный разрыв к нижней оценке, доля сцен с доказанным оптимумом, среднее число поворотов, изломов, камер, врезок, p50 и p95 времени», отдельно для текущего сервиса и каждого кандидата, включая случаи, когда порог AC-1.2 не достигнут — проверка: `uv run --project tools/research python -m heatopt.report --check` печатает `BENCH REPORT OK rows=<n>` с `n` не меньше 15 (пять алгоритмов на три класса).
- **AC-1.4** THE SYSTEM SHALL для рекомендованного кандидата в режиме `quality=on` иметь на каждом из трёх классов среднее число поворотов, изломов и камер на сцену (определения в C-9) не больше, чем у текущего сервиса, и средний S по разделу 10 не больше среднего S сервиса — проверка: та же команда `heatopt.bench --check` печатает `RATIONALITY OK candidate=<имя> s_vs_service=<z>%` с `z` не больше 0.

### US-2: Команда получает правила разумной трассы с ценами, чтобы целевая функция и отчёт тестов учитывали здравый смысл инженера (P1, цель G-3)

- **AC-2.1** THE SYSTEM SHALL держать в `docs/routing-quality.md` таблицу правил `RQ-n`, где у каждого правила: уровень доказательности A, B или C по R-15…R-28, ссылка на источник, формула по геометрии выхода, порог, способ применения (`objective`, `tie-break` или `report`); у правил уровня A и B, применяемых в `objective`, — цена в рублях, метод её расчёта и источник чисел; у правил уровня C — только `tie-break` или `report`; правил не меньше 12, из них не меньше 6 с ценой — проверка: `uv run --project tools/research python -m heatopt.rules_check docs/routing-quality.md` печатает `RULES DOC OK rules=<n> priced=<m>`.
- **AC-2.2** WHEN выполняется `uv run --project tools/research python -m heatopt.metrics <вход> <выход>` THE SYSTEM SHALL напечатать значение каждой метрики из `RQ-n` для каждого варианта выхода в формате JSON, а `--self-test` на шести парах `data/synth` и `data/out` (small и medium, сиды 1–3) и фикстуре валидатора обязан показать, что для каждой метрики есть мутация выхода, меняющая её значение — проверка: `uv run --project tools/research python -m heatopt.metrics --self-test` печатает `METRICS OK outputs=7 rules=<n> mutations=<n>`.
- **AC-2.3** THE SYSTEM SHALL в режиме `quality=on` прибавлять к целевой функции кандидатов штрафы правил с ценой и показывать в бенчмарке два столбца для каждого решения: S по разделу 10 и «S с учётом разумности» (S плюс штрафы, переведённые через 0,7 / 25 000 000); ранжирование в выходе сервиса остаётся по формуле ТЗ — проверка: `heatopt.report --check` печатает `OBJECTIVE OK priced_rules=<m>` с тем же `m`, что в AC-2.1.

### US-3: Нижняя оценка честная, чтобы разрыв не был артефактом модели (P1, цель G-1)

- **AC-3.1** THE SYSTEM SHALL на пяти ручных сценах `tools/research/tests/scenes/` с оптимумом, посчитанным вручную и записанным в файле сцены (один ОКС и прямая; два ОКС с общим стволом дешевле раздельных; препятствие, которое надо обойти; врезка в камеру против трубы; реконструкция, меняющая выбор врезки), вернуть из MILP тот же оптимум с точностью 1 руб. по стоимости и 0,001 по S — проверка: `uv run --project tools/research pytest -q tools/research/tests/test_exact.py` печатает `5 passed`.
- **AC-3.2** THE SYSTEM SHALL на каждой сцене бенчмарка соблюдать LP ≤ MILP-оптимум (или лучшая граница) ≤ стоимость любого решения сервиса и кандидатов, с допуском 0,001 по S — проверка: `heatopt.bench --check` печатает `BOUNDS OK scenes=90`.

### US-4: Команда получает рекомендацию с обоснованием, чтобы запустить внедрение (P1, цель G-4)

- **AC-4.1** THE SYSTEM SHALL держать в `docs/research/routing-report.md` разделы: метод и модель, таблица бенчмарка (ссылка на AC-1.3), правила разумности (ссылка на `routing-quality.md`), рекомендация с числами, совпадающими с `results.json`, черновик ADR (контекст, варианты, решение, последствия), границы применимости, оценка трудозатрат внедрения в Java по каждому кандидату — проверка: `heatopt.report --check` печатает `REPORT OK`, при этом числа в разделе «Рекомендация» сверены со `results.json`.

### US-0: Что не должно измениться

- **AC-0.1** Файлы сервиса, генератора, валидатора и правил в ветке `research/routing` совпадают с точкой ветвления от `feature/backend-core` — проверка: `bash scripts/gates/research_untouched.sh` печатает `SERVICE UNTOUCHED`.
- **AC-0.2** CONSTRAINTS.md байт в байт совпадает с `main` — проверка: `bash scripts/gates/constraints_unchanged.sh` печатает `CONSTRAINTS UNCHANGED`.

## Нефункциональные требования

- **NFR-1** Полный бенчмарк (90 сцен, сервис, четыре кандидата в двух режимах, MILP с лимитом 1200 с на сцену, LP) выполняется не дольше 12 часов стенных часов при трёх параллельных процессах — источник числа: Q-7 (30 сцен на класс, солвер до 20 минут), допущение A-2; замер: `bench run` записывает в `results.json` стенное время всего прогона от старта до конца целым числом секунд, `heatopt.bench --check` печатает `BENCH TIME OK elapsed=<s>s` только если оно не больше 43 200.
- **NFR-2** Каждый кандидат на Python укладывается в 120 секунд на сцене класса L в 95 % сцен; внутренний бюджет кандидата задаётся так, чтобы расчёт останавливался не позже 100 секунд — источник числа: 120 секунд на `medium` из backend-core, допущение A-1; замер: `heatopt.bench --check` печатает `CANDIDATE TIME OK class=L p95=<s>s`, где `s` — наибольший по четырём кандидатам 95-й процентиль времени на классе L в режиме `quality=on`, только если он не больше 120.

## Ограничения

- **C-1** Прототипы — отдельный проект `tools/research` (uv, Python 3.12+), зависимости: `shapely`, `pyproj`, `numpy`, `networkx`, `highspy` (HiGHS, MIT), `pytest`, плюс проект `tools/` как редактируемая path-зависимость (`[tool.uv.sources] heatnet-tools = { path = "..", editable = true }`), чтобы импортировать `heatsynth` и `heatcheck` без правки `tools/`; никаких коммерческих солверов.
- **C-2** Работа в отдельном git worktree и ветке `research/routing` от `feature/backend-core`; пуш только этой ветки; merge делает человек. В сообщениях коммитов нет трейлера `Co-Authored-By`.
- **C-3** Одна модель стоимости для всех кандидатов и для оценки сервиса: `heatopt.model` читает все числа из `rules/rules.json` (цены, ёмкости, камеры, врезка, штраф, коэффициенты S) и считает стоимость по разделам 6–10 CONSTRAINTS.md и `docs/interpretation.md`; показатель сравнения — S из раздела 10; выход сервиса берётся из CLI `java -jar target/heatnet.jar --cli <вход> <выход>` и пересчитывается той же моделью. Кандидаты работают в двух режимах: `quality=off` — целевая функция S; `quality=on` — S плюс штрафы правил с ценой из `docs/routing-quality.md`, переведённые в единицы S через 0,7 / 25 000 000.
- **C-4** Граф кандидатов строится по тем же правилам, что в сервисе (R-3): буферы `clearance + width/2` с mitre-углами, рефлексные вершины, узлы вдоль сторон дорог через 20 м, отсев рёбер под углом меньше 45° к дороге и трамваю, специальные зоны с `k_special`; диаметр буфера — на ступень выше диаметра по суммарному расходу сцены. Граф для нижней оценки (MILP и LP) строится по наименьшему диаметру среди расходов отдельных ОКС сцены, то есть с наименьшими буферами: так оценка остаётся не выше любого решения, которое сервис или кандидат могут построить с большими буферами. Граф нижней оценки строится без прореживания рёбер (`tangent=False`); кандидаты могут оставлять у выпуклых вершин только касательные рёбра (`tangent=True`), кратчайшие пути при этом не теряются. Область графа — рамка терминалов и кандидатов врезки с запасом 600 м.
- **C-5** Классы сцен: S — 3–5 ОКС, 20 ограничений, 30 участков сети; M — 6–8 ОКС, 50 ограничений, 80 участков; L — 20 ОКС, 200 ограничений, 300 участков (пресет `medium`); число ОКС для S и M выбирается по сиду равномерно из диапазона; сцены генерирует `heatsynth` через объект `Preset(oks, restrictions, segments)`, сиды 1–30 на класс, проверка `heatsynth.check`.
- **C-6** Нижняя оценка — оптимум релаксированной задачи P в графе видимости нижней оценки (C-4), лимит 1200 с на сцену, относительный MIP-gap 0,1 %, солвер HiGHS.
  - **Задача P.** Лес деревьев с корнями в узлах врезки; каждый терминал — лист ровно одного дерева или неподключён за штраф раздела 9. Через терминалы и врезки путь не проходит. Диаметр ребра — минимальный по сумме `flow_tph` терминалов ниже по дереву. Стоимость ребра — `new_price(DN) × (длина + (k_special − 1) × длина специальных частей)`. Узел ветвления, кроме корня, получает камеру по ступени диаметра входящего ребра. Каждое дерево платит `tie_in_cost`; дерево врезки в трубу — ещё новую камеру по ступени наибольшего из диаметра дерева и существующего диаметра трубы. В трубу — не больше одного дерева в точке, в существующую камеру — не больше её свободных мест (`min(max_segments, max_branches + 1)` минус примыкающие участки). Реконструкция участков считается точно, как в `heatopt.model`: добавка идёт по цепочке `upstream_object_id`, в трубе врезки — только от точки врезки к источнику, стоимость и длина ступенчатые. Реконструкция камеры врезки берётся по нижней оценке требуемого диаметра: наибольшее из диаметров примыкающих существующих участков после реконструкции и диаметра по наибольшему `flow_tph` одного ОКС в деревьях этой камеры. Целевая функция — S раздела 10, L — сумма длин новых рёбер и реконструкции. Правила предельной длины, поворотов, числа ответвлений некорневых камер и непересечения деревьев не проверяются, поэтому оптимум P не выше стоимости любого решения, чьи рёбра идут по узлам этого графа (R-7).
  - **Точный оптимум P на классах S и M** (`heatopt.exact.solve`). Шаг 1: для каждого непустого подмножества терминалов D и каждого узла v динамика Дрейфуса–Вагнера даёт наименьшую S-стоимость дерева с корнем v, соединяющего D; диаметр рёбер при подъёме от D известен из суммы расходов D, камера добавляется при выходе из узла слияния. Шаг 2: мастер-MILP выбирает деревья `x[D, t]` для узлов врезки t так, чтобы каждый терминал был в одном дереве или неподключён; реконструкция участков моделируется переменными выбора диаметра по кускам существующей сети, реконструкция камер — бинарными переменными по ступеням. Оптимум мастера равен оптимуму P, потому что деревья P не взаимодействуют ничем, кроме реконструкции, а она в мастере точная.
  - **LP-граница на всех 90 сценах** (`heatopt.exact.lp_bound`). Потоковая модель на том же графе без целочисленности: поток добавки идёт от источника по существующей сети, через дугу врезки в новую сеть и к терминалам. Каждая ступенчатая стоимость заменена линейной оценкой снизу: у ребра новой сети — `min по DN (вес ребра при DN / min(cap(DN), F))` на единицу потока, где F — суммарный расход сцены; у дуги врезки — `(tie_in_cost + наименьшая камера) / F`; у куска существующей сети — `max(0, m × (f − (cap(DN_сущ) − G_сущ)))` с `m = min по DN > DN_сущ (стоимость и длина реконструкции в S / min(cap(DN) − G_сущ, F))`; камеры ветвления — ноль. Такая оценка не выше оптимума P на любой сцене.
  - При недоказанном оптимуме записываются лучшая граница, лучшее решение, статус и время.
- **C-7** Гейты запускаются из корня worktree с `--timeout 1800`; длинные вычисления (бенчмарк) идут вне гейтов и пишут `data/research/*.json`, гейты проверяют артефакты; маркеры печатают только модули `heatopt` и скрипты `scripts/gates/research_*.sh` после всех проверок; скрипты начинаются с `set -euo pipefail`, без `|| true`, `|| :` и `exit 0`.
- **C-8** Строки для читателя (документы, отчёт, вывод инструментов) на русском; идентификаторы и ключи JSON на английском; ID правил `RQ-<n>`, кандидатов — `ls`, `dp`, `bend`, `master`, сервис — `service`.
- **C-9** Определения метрик для AC-1.4 и `routing-quality.md`: поворот — вершина трассы или узел между двумя участками пути с отклонением направления 3° и больше (как в правиле `geometry` валидатора); излом — поворот с отклонением от 3° до 50°, у которого в буфере 5 м вокруг вершины нет полигона запрета, дороги или трамвайных путей (R-17); камера — объект `heat_chamber` варианта; для сервиса метрики считаются по варианту с `rank = 1`, для кандидатов — по единственному решению.

## Допущения

Приняты без подтверждения. Если допущение окажется ложным, план меняется.

- **A-1** Python-прототип с networkx укладывается в 120 с на классе L — если ложно: NFR-2 красный, в отчёте оценка ускорения при переносе в Java.
- **A-2** HiGHS доказывает оптимум за 20 минут не меньше чем на 20 сценах из 30 в классах S и M при прореженном графе и диаметрах, ограниченных суммарным расходом — если ложно: порог `e` в AC-1.1 и AC-1.2 не выполняется, отчёт даёт разрыв к лучшей границе с пометкой «не доказано» и предлагает уменьшить класс M.
- **A-3** Оптимум в графе видимости с рефлексными вершинами и узлами вдоль дорог отличается от оптимума в плоскости меньше чем на 1 % по S — если ложно: добавляется сетка кандидатов точек Штейнера с шагом 5 м вокруг терминалов, модель не меняется.
- **A-4** Жюри примет цену поворота и камеры как обоснованное дополнение к стоимости ТЗ, если ранжирование в выходе остаётся по формуле ТЗ — если ложно: правила остаются отчётной метрикой, целевая функция без штрафов.
- **A-5** Сцены классов S и M из `heatsynth` с `Preset(oks, restrictions, segments)` получаются без правки генератора — если ложно: сцены строятся своим генератором в `tools/research` по тем же правилам, `tools/synth` не трогается.
- **A-6** Точки поворота «т.N» в реестре Схемы теплоснабжения — вершины маршрута — если ложно: статистика R-24 используется только для длин, не для поворотов.
