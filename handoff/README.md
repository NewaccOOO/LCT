## Как мерить

Все замеры одним скриптом, чтобы числа были сравнимы:

```bash
source scripts/env.sh
cp target/heatnet.jar handoff/bench/<метка>.jar
python3 -I handoff/bench/metrics.py --repo . --jar handoff/bench/<метка>.jar --out handoff/bench/runs/<метка> --sets organizers,dense,medium,expert,moscow[,city]
python3 -I handoff/bench/compare.py handoff/bench/base-metrics.json handoff/bench/runs/<метка>/metrics.json
```

- `metrics.py` считает каждый набор, гоняет check18 и пишет `metrics.json`: по каждому варианту S, точки без сети, длину, повороты, пары поворотов (список в `pair_list`), нарушения check18 и время. Наборы: `organizers` (оба файла организаторов), `dense`, `medium`, `expert` (пять наборов Э4), `moscow`, `city`. Можно добавить свой вход: `--extra имя=путь`.
- Москва и синтетический город проверяются check18 на срезе 3×3 км (`scripts/city_cut.py`): полный check18 Москвы идёт больше 15 минут. Полный прогон делать отдельно, когда он нужен (Э3).
- `compare.py` печатает таблицу против базы и флаги: S хуже, больше точек без сети, новые нарушения, время больше +20 %.
- `bench/base-metrics.json` — база версии 0.9.0 (c0f8f6f), снятая 16.10 днём, до прохода Сергея по осям. Она нужна, чтобы оценить сам проход. Для остальных задач базу надо снять заново на 901c4a9 и класть рядом отдельным файлом. После каждого вливания в `fix/expert-remarks` базу перемерить.
- Режим с глубиной теперь в `main` (`--depth` у CLI, `check18.py --depth`). Наши задачи его не трогают, `metrics.py` гоняет только обычный режим.
- Все запуски `java -jar` идут через `handoff/bench/heavy.sh <команда>` — это очередь по порядку прихода. На машине с 18 ГБ параллельные расчёты падают по памяти и врут по времени.
- Поворот — внутренняя вершина LineString участка `heat_network`, где направление меняется на 3° и больше. Пара — два соседних поворота в одну сторону внутри одного участка с суммой 60–120° и звеном между ними короче 30 м.
- Модель Москвы и город в городском режиме недетерминированы по id: сравнивать метрики, а не md5. Город режется сроками (районы, не начатые за 275 с, остаются без сети), поэтому его время и число точек без сети сравнивать только парами прогонов база–кандидат подряд, по среднему.

## Пороги приёмки

- Правка по правилам (Т2–Т8): на наборах, которых правка не касается, выход побайтово тот же; S варианта 1 не хуже базы больше чем на 0,0001; точек без сети не больше ни в одном варианте; новых нарушений check18 нет.
- Правка формы трасс (Э1–Э3, Т1, Т9): S может вырасти не больше чем на 1 % на каждом наборе, при этом пар поворотов меньше (на конкурсном наборе — ноль или каждая оставшаяся объяснена), поворотов на километр меньше. Это расходится с правилом `CONTRIBUTING.md` «правка качества не делает вариант 1 хуже». Довод за: S по разъяснению 29.09 п. 1 только ранжирует варианты одного решения, а эксперты оценивают форму. Порог 1 % — решение команды. Проход Сергея по осям даёт +7 % на конкурсном наборе (12,7483 → 13,6408): порог надо пересмотреть вместе с Павлом, прежде чем принимать или отклонять проход.
- Время: не больше +20 %, у синтетического города не больше +10 % по среднему из пар прогонов.
- Проверщик check18 не ослабляется. Любая его правка опирается на пункт правил, а проверяющий прогоняет на выходе кандидата и новый, и старый проверщик.

## Роли и порядок работы

Каждую задачу делают два агента: исполнитель и независимый проверяющий.

### Исполнитель

1. Получает файл задачи из `items/`, работает в своей ветке от `fix/expert-remarks` (накладывает патч из `patches/`, если он есть).
2. Перед кодом читает `CONTRIBUTING.md`, нужные места `docs/interpretation.md`, `docs/algorithm.md`, `architecture/ARCHITECTURE.md` и правила организаторов из `bench/rules-src/`.
3. Правила кода:
   - без комментариев и докстрингов в новом и изменённом коде, включая Javadoc; существующие комментарии, ставшие неправдой, исправить или удалить;
   - имена на английском, тексты для людей (логи, сообщения) на русском, как в соседнем коде;
   - минимальный дифф, без новых зависимостей, числа кейса только в `rules/rules.json`;
   - если меняется поведение или толкование правила — в том же диффе `docs/interpretation.md` и `docs/algorithm.md` (картинки не пересобирать), при смене устройства — `architecture/ARCHITECTURE.md`;
   - сервис и проверщик check18 читают правило одинаково; ослаблять проверщик, чтобы прошёл выход, нельзя;
   - режим с глубиной не трогать.
4. Пишет тест, который падает до правки и проходит после.
5. Мерит `metrics.py` и `compare.py`, сдаёт отчёт: что изменено, на какой пункт правил опирается, какой тест, таблица `compare.py` с объяснением каждого флага, какие документы обновлены, что не сделано и риски. Не коммитит.

### Проверяющий

Свежий агент, который не видел работы исполнителя и не доверяет его отчёту. Код не правит.

1. Сам собирает jar из ветки исполнителя и сам гоняет `metrics.py` на наборах из файла задачи; сравнивает с базой.
2. Юнит-тесты зелёные; новый тест падает на `main`.
3. Правка делает то, что требует задача, и соответствует правилам организаторов; ищет пропущенные случаи и вызовы, которые обошли правку.
4. Регресса нет по порогам выше. Флаг по времени перемеривает парами база–кандидат через `heavy.sh`.
5. Проверщик не ослаблен: каждую строку правки check18 сверяет с пунктом правил, прогоняет проверщик версии 0.9.0 (c0f8f6f) на выходе кандидата и смотрит, что новый перестал видеть.
6. Новых проблем нет: справочные строки check18, варианты-дубли, изменения на наборах, которых правка не касалась.
7. Ожидаемое улучшение есть и измерено.
8. В новом коде нет комментариев, документы обновлены.

Ответ начинается строкой `ВЕРДИКТ: PASS` или `ВЕРДИКТ: FAIL`, дальше таблица `compare.py`, пункты с числами и при FAIL — пронумерованные замечания с местом и тем, что исправить.

### Вливание

- FAIL — замечания уходят исполнителю, не больше двух кругов; потом задача откладывается с записью причины.
- PASS — коммит в ветку задачи и вливание в `fix/expert-remarks`. Сообщение коммита — одна строка на русском о том, что сделано, без ключей задач и без трейлеров атрибуции. После вливания перемерить базу, прогоны и рабочую копию задачи удалить.
- В конце — общая независимая проверка всей ветки против `main` на всех наборах, включая город.
