# Сервис моделирования трасс подключения к тепловым сетям

Решение кейса ДИТ Москвы (Департамента информационных технологий) на конкурсе «Лидеры цифровой трансформации» 2026. Инженер загружает один GeoJSON с существующей тепловой сетью, перспективными ОКС (объектами капитального строительства, которые нужно подключить) и пространственными ограничениями. Сервис для всех ОКС за один запуск строит от двух до трёх вариантов подключения и отдаёт их одним GeoJSON: трассы, точки врезки, камеры, диаметры, реконструкцию существующей сети, стоимость и ранжирование вариантов.

Правила кейса выписаны из документов организатора в [architecture/CONSTRAINTS.md](architecture/CONSTRAINTS.md). При расхождении с любым другим файлом репозитория прав он, а над ним только сами документы в [docs/source/](docs/source/).

## Из чего состоит

| Часть | Что делает | Где | Состояние |
|---|---|---|---|
| Бекенд | принимает файл по REST, считает варианты в фоне, отдаёт результат; тот же расчёт доступен из командной строки | `src/`, Java 11, Spring Boot, PostgreSQL | готов, проверен на синтетике и датасете организаторов |
| Генератор синтетики | делает входные наборы той же структуры, что конкурсный, с пресетами по размеру | `tools/synth/heatsynth` | готов |
| Валидатор | независимо от сервиса проверяет выходной файл по 15 правилам кейса | `tools/validator/heatcheck` | готов |
| Сценарные тесты | 15 семейств сценариев S00–S14 и случайный прогон через CLI сервиса | `tools/scenarios/heatscen`, `tests/scenarios` | готовы |
| Фронтенд | загрузка файла и просмотр вариантов на карте | в репозитории пока нет | планируется поверх готового API |

Конкурсный набор данных в репозиторий не входит, он конфиденциален. Для проб есть `data/samples/small-1.geojson` и генератор.

## Как считает

1. Вход читается потоком и переводится в метры (EPSG:32637). Здания и другие запреты раздуваются на отступ, по их выпуклым вершинам строится граф видимости; рёбра проверяются только там, где касаются зон, а веса от точек запроса кэшируются.
2. Для каждого ОКС и групп близких ОКС подбираются кандидаты врезки: ближайшие камеры и проекции на участки сети, лучшие по грубой стоимости с учётом реконструкции цепочки к источнику.
3. Дерево одной врезки растёт эвристикой Такахаши–Мацуямы: на каждом шаге присоединяется ОКС с самым лёгким маршрутом до дерева, путь до него проверяется правилом поворотов.
4. Черновик варианта собирает деревья по разбиению ОКС на блоки, считает расходы, диаметры, реконструкцию и стоимость. Локальный поиск сливает блоки, переносит и выделяет ОКС, меняет врезку, пока улучшается S или не кончится лимит времени.
5. До трёх лучших черновиков, различающихся врезками или разбиением, выдаются вариантами с рангами.

Подробно — в [architecture/ARCHITECTURE.md](architecture/ARCHITECTURE.md), причины решений — в [ADR-0001](docs/specs/backend-core/adr/0001-routing-approach.md) и [ADR-0002](docs/specs/backend-core/adr/0002-partition-local-search.md). На датасете организаторов расчёт занимает около 70 секунд, вариант 1 стоит 359 млн руб. против 537 у версии без локального поиска; числа и ход ресёрча — в [docs/research/](docs/research/real-dataset.md).

## Быстрый старт

Нужен Docker с compose. Поднимает приложение и PostgreSQL 16:

```bash
make up
```

Остальные команды, от тестов до полного прогона «сгенерировать вход, посчитать, проверить валидатором», собраны в `Makefile`, список печатает `make help`.

Дальше отправить файл и забрать результат по `id` задачи:

```bash
curl -s -X POST -H 'Content-Type: application/geo+json' \
  --data-binary @data/samples/small-1.geojson http://localhost:8080/api/v1/jobs
```

Swagger UI открывается на `http://localhost:8080/swagger-ui/index.html`. Переменные окружения, полное описание API, запуск из командной строки, сборка и тесты описаны в [architecture/BACKEND.md](architecture/BACKEND.md).
