# P5. Производительность на реальном городе (p5-perf)

Отчёт агента P5; записан главным разговором, у агента не было прав на запись файла.
Прототип: ветка `worktree-agent-acbc8762c7da0a60a`, коммит b2a4aba (+146/−35), в main не влит. Выход на всех
наборах побайтово тот же; СПб быстрее в 1,2 раза, Москва-город — в 4 раза.

Замеры шли под нагрузкой (load 20–56); выводы — по долям профиля JFR, CPU user и счётчикам. Строки «q-» сняты
на почти свободной машине (load 3–27, очередь в 1 слот).

## Главный вывод
Время на реальном городе уходит не на линии коммуникаций и не на STRtree. Непропорционально растут:
1. объяснение причин неподключения в критериях;
2. наборы зон и узлы графа при тысячах дорог в области;
3. проверка отступа у пересечений линий.

## Прототип
- **P1.** Полосы margin дорог в STRtree (`ObstacleSet.insideAny`): 9,7 → 3,7 % CPU СПб.
- **P2.** Кэш буфера линии по отступу для `nearCrossing`: `NetworkAssembler` 21 → 3 % CPU в Москве-143.
- **P3.** Причины неподключения: при сомнении объединяются только группы зон у луча; кольцо в кольце — прежнее
  полное объединение; кэш касаний пар. Тест `nestedRingsAndFarZonesKeepEnclosure`. Критерии: СПб 3,0 → 1,9 с,
  Москва-город 198 → 16 с, criteria.json побайтово тот же.
- **P4.** Наборы зон только для проверки — без узлов графа (`withNodes=false`): построение `ObstacleSet` в Москве
  14 → 7,7 %.

## Не сделано
- (A) Рамки спецобъектов в сетке вместо перебора 2 434 рамок на ребро: −15–25 % CPU, риск низкий.
- (B) `Math.hypot` → `sqrt`: ~5 % CPU, возможны отличия в последнем бите, перепроверить S.
- (C) CLI без веб-контекста Spring: −4 с на прогон, выход тот же.
