## Коротко

| Задача | Команда |
|---|---|
| Поднять сервис и PostgreSQL | `make up` или `docker-compose up -d --build` |
| Отправить файл | `curl -X POST -H 'Content-Type: application/geo+json' --data-binary @file.geojson http://localhost:8080/api/v1/jobs` |
| Посчитать без веба и базы | `java -jar target/heatnet.jar --cli IN.geojson OUT.geojson` |
| То же с учётом глубины | `java -jar target/heatnet.jar --cli --depth IN.geojson OUT.geojson` |
| Проверить выход по правилам кейса | `make validate IN=… OUT=…` |
| Собрать и прогнать тесты | `mvn -B verify` или `./gradlew test` |
| Посчитать датасет организаторов с проверкой | `make real` |
| Платформа инженера без сервиса | `make platform`, `http://localhost:8091/` |
| Все цели `make` | `make help` |

## Состав

Сервис лежит в `src/main/java/ru/lct/heatnet/`, версия 0.12.0, Java 11 и Spring Boot 2.6.3. Все числа кейса читаются из `rules/rules.json`, тот же файл читают Python-инструменты. Файл правил можно подменить, раздел «Правила для другого ресурса».

| Пакет | Что внутри |
|---|---|
| `io` | потоковое чтение входа и запись выхода, перевод между EPSG:4326 и EPSG:32637 |
| `rules` | загрузка `rules.json` |
| `graph` | препятствия, граф видимости между выпуклыми вершинами зон только по касательным рёбрам, кратчайший путь по массивам с кэшами |
| `plan` | кандидаты врезки, деревья Такахаши–Мацуямы, точный скелет дерева врезки, правило поворотов, локальный поиск по разбиениям ОКС, варианты, сборка сети, профиль глубины `DepthProfiler` |
| `calc` | расходы, диаметры, предельная длина, стоимость, показатель S из раздела 10 CONSTRAINTS.md, чем меньше, тем лучше |
| `api` | REST и очередь задач в PostgreSQL |
| `cli` | запуск расчёта из командной строки без веба и базы |
| `core` | конвейер расчёта `Pipeline`: общий для API и CLI |
| `model` | объекты входа и выхода |

## Запуск в Docker

Нужен Docker с docker-compose 1.29.2 или compose v2. Файл compose написан в формате 3.8. `make up` вызывает `docker compose`; для старого Compose — `COMPOSE=docker-compose make up`.

```bash
docker-compose up -d --build
```

| Адрес | Что там |
|---|---|
| `http://localhost:8080/` | платформа инженера «Тепломаршрут» ([platform/README.md](../../platform/README.md)) |
| `http://localhost:8080/api/v1/jobs` | API |
| `http://localhost:8080/swagger-ui/index.html` | Swagger UI |
| `http://localhost:8080/actuator/health` | состояние сервиса |

Остановить и удалить контейнеры вместе с томами:

```bash
docker-compose down -v
```

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `APP_PORT` | `8080` | порт приложения на хосте |
| `POSTGRES_HOST_PORT` | `55432` | порт PostgreSQL на хосте; внутри compose приложение ходит в базу по 5432 |
| `JOB_WORKERS` | `2` | сколько задач считается одновременно |
| `JAVA_OPTS` | `-XX:MaxNewSize=512m` | параметры JVM, например `-Xmx4g`. Потолок молодого поколения держите и при своих `JAVA_OPTS`: без него на большом входе G1 раздувает молодое поколение на гигабайты, и файл «город» считался 14 минут вместо 2,5 из-за подкачки; свойства расчёта `-Dheatnet.*` — в разделе «Свойства расчёта» |
| `DATA_DIR` | `/data` в контейнере, `data` локально | каталог входных и выходных файлов задач |
| `HEATNET_RULES` | пусто, берётся `rules.json` из jar | путь к файлу правил или `classpath:/examples/water-supply.json` |
| `SPRING_DATASOURCE_URL` | `jdbc:postgresql://localhost:55432/heatnet` | адрес базы при запуске jar без compose |

> [!WARNING]
> Файл 300 МБ проверен при куче JVM 1 ГБ. Файл «город» на 3,2 ГБ и 3,14 млн ОКС считается через CLI при `-Xmx12g -XX:MaxNewSize=512m` за 335 с, пиковый RSS 4,5 ГБ (последний замер — v0.9.0, [отчёт](../performance.md)). Для такого входа в API нужна такая же куча, а `JOB_WORKERS` стоит поставить в 1.

### Свойства расчёта

Задаются параметром JVM: `java -D<свойство>=<значение> -jar target/heatnet.jar …`, в Docker — через `JAVA_OPTS`. Значения по умолчанию — из кода.

| Свойство | По умолчанию | Что задаёт |
|---|---|---|
| `heatnet.rules` | пусто | файл правил, раздел «Правила для другого ресурса» |
| `heatnet.search.budget` | `1000` | бюджет локального поиска: число сборок черновика, предела по времени нет |
| `heatnet.search.stall` | `100` | остановка поиска после стольких сборок без улучшения |
| `heatnet.search.parallel` | `true` | `false` — деревья кандидатов врезки в одну нить; выход тот же, расчёт дольше |
| `heatnet.route.cache.mb` | `1024`, но не больше половины кучи | потолок кэша маршрутов на расчёт, МБ |
| `heatnet.read.all` | `false` | `true` — держать в памяти все здания и ограничения, а не только вокруг групп ОКС |
| `heatnet.square` | `true` | `false` — без ортогональной формы трасс по замечаниям экспертов 16.10 |
| `heatnet.exact` | `true` | `false` — без точного скелета дерева врезки ([algorithm.md](../algorithm.md)) |
| `heatnet.city.min` | `500` | с какого числа ОКС включается городской режим |
| `heatnet.city.reach` | `300` | до скольких метров от точки до врезки пробуется прямое подключение |
| `heatnet.city.block` | `16` | ОКС в районе |
| `heatnet.city.threads` | по числу ядер | потоков для районов |
| `heatnet.city.budget` | `60` | сборок поиска в районе; `0` — вдвое быстрее, S чуть хуже |
| `heatnet.city.stall` | `50` | остановка поиска в районе после стольких сборок без улучшения |
| `heatnet.city.deadline` | `0` | `0` — срока нет, считаются все районы (п. 2.5); больше нуля — секунд от старта городского расчёта, после которых новые районы не начинаются и их точки остаются без сети, начатые досчитываются |
| `heatnet.city.retry.deadline` | `0` | то же для второго прохода по точкам города без сети: `0` — без срока |
| `heatnet.city.corridor` | `true` | граф района на полосе вдоль прямых от точек к кандидатам врезки, а не на прямоугольнике |
| `heatnet.city.corridor.share` | `0.25` | ширина полосы в долях длины прямой, но не уже 60 м |

В режиме глубины `-Dheatnet.depth.chambers=free` ставит камеры на глубину по стоимости, а не на 3,0 м ([depth-optimization.md](../depth-optimization.md)).

## REST API

Расчёт идёт асинхронно: клиент загружает файл, получает `id` задачи и опрашивает её статус.

| Запрос | Ответ |
|---|---|
| `POST /api/v1/jobs`, тело — сам GeoJSON (`application/json`, `application/geo+json` или `application/octet-stream`); `?depth=true` — режим с учётом глубины, по умолчанию 2D | `202 {"id", "status": "QUEUED"}`; `400`, если тело пустое или не начинается с `{`; `415` при другом `Content-Type` |
| `GET /api/v1/jobs` | список задач, новые первыми |
| `GET /api/v1/jobs/{id}` | статус `QUEUED`, `RUNNING`, `DONE` или `FAILED`, времена, ошибка, после `DONE` — сводки вариантов |
| `GET /api/v1/jobs/{id}/result` | выходной GeoJSON; `409`, пока задача не `DONE` |
| `GET /api/v1/jobs/{id}/input` | исходный файл байт в байт |

На неизвестный или неверный `id` запросы `/{id}…` отвечают `404`.

Сводка варианта в `summary` повторяет `variant_summary` из выхода и дополнительно содержит объект `criteria`, описанный в разделе «Дополнительные критерии».

```bash
curl -s -X POST -H 'Content-Type: application/geo+json' \
  --data-binary @data/samples/small-1.geojson http://localhost:8080/api/v1/jobs
```

> [!IMPORTANT]
> Файл загружается сырым телом, а не multipart. Так вход до 3 ГБ пишется на диск потоком один раз и не упирается в лимиты Tomcat.

### Ошибки

Если во входе нет обязательного атрибута, значение не того типа, `id` повторяется, ссылка ведёт на несуществующий объект или геометрия невалидна, задача завершается `FAILED`. Каждая запись в `error.errors` содержит `featureId`, `field` и `problem`. Хранится до 1000 записей, общее число ошибок написано в `message`.

Ошибки самого API (`400`, `404`, `409`, `415`) приходят в том же формате:

```json
{"message": "…", "errors": [{"featureId": "…", "field": "…", "problem": "…"}]}
```

## Командная строка

Для отладки и замеров расчёт можно запустить без веба и базы:

```bash
java -jar target/heatnet.jar --cli [--depth] [--rules=<файл правил>] data/samples/small-1.geojson data/out/small-1.geojson
```

`--cli` стоит первым аргументом: он включает профиль без веба и базы. `--depth` — режим с учётом глубины, `--rules` — другой файл правил. Каталог выхода создаётся сам.

| Код выхода | Когда | Что печатает |
|---|---|---|
| `0` | расчёт завершён | `PIPELINE DONE variants=<n> elapsed=<s>s` |
| `2` | во входе ошибки данных, выходной файл не создаётся | список ошибок по объектам |
| `1` | не два пути в аргументах или любая другая ошибка | строка использования или текст ошибки |

Рядом с выходом CLI пишет `<имя выхода>.criteria.json`: для каждого варианта `variant_id`, `rank`, `score`, `calculated_cost` и `criteria`. Путь печатается строкой `CRITERIA <путь>`.

### Режим с учётом глубины

Дополнительная задача §5 приложения 18.09. Включается `--depth` в CLI или `?depth=true` в `POST /api/v1/jobs`. Трасса в плане, Ду и камеры берутся из 2D, сверху строится профиль. В выходе:

- у `heat_network` заполнены `depth_start` и `depth_end` (в 2D — `null`), стоимость с Kгл, длина и глубины до мкм; у участка с пересечением газа, кабеля или сети — `depth_crossings` (`type`, `position`, `vertical_clearance_m`); `manual_review: true`, если профиль по правилам не найден;
- участки делятся по изломам профиля техническими узлами с `reason: depth_profile`;
- у `heat_chamber` — `depth_m`, у камеры дальше 5 см от 3,0 м — `depth_shifted: true`;
- сводка и ранги пересчитаны по S с Kгл.

Проверка: `check18.py --depth`. Как строится профиль, нижняя граница стоимости и замеры — [depth-optimization.md](../depth-optimization.md).

### Дополнительные критерии

Критерии не входят в формулу S и не меняют выбор вариантов. Они помогают сравнить варианты на защите. В выходной GeoJSON они не пишутся, пока организаторы не ответили, можно ли добавлять атрибуты сверх раздела 13.

| Поле | Что значит |
|---|---|
| `connected_oks`, `connected_flow_tph` | сколько ОКС подключено и их суммарный расход, т/ч |
| `unconnected_reasons` | почему ОКС из `unconnected_oks_ids` не подключён: `oks_id`, код `reason`, текст `message` и `object_ids` — объекты, которые мешают. Пустой список, если подключены все |
| `existing_chamber_tie_ins`, `new_chambers`, `technical_nodes` | число врезок в существующие камеры, новых камер и технических узлов |
| `special_segments`, `special_length_m` | число участков спецперехода и их длина, м |
| `crossed_objects` | сколько разных объектов каждого типа пересекают участки спецперехода, например `{"road": 3, "heat_network": 1}` |
| `turns`, `max_turn_deg` | изломы трассы от 3° внутри участков и в технических узлах и самый крутой из них, градусы |
| `surcharge_cost` | сколько добавили к стоимости участков коэффициенты спецперехода, руб. |
| `cost_per_oks`, `cost_per_tph` | стоимость без штрафа за неподключённые ОКС на один ОКС и на 1 т/ч; `null`, если подключать нечего |

### Правила для другого ресурса

Все таблицы и коэффициенты берутся из одного файла правил. По умолчанию это `rules.json` внутри jar. Другой файл задаётся одним из способов. Если заданы несколько, побеждает верхний в списке:

1. аргумент `--rules=<путь>` при запуске jar;
2. параметр JVM `-Dheatnet.rules=<путь>`;
3. переменная окружения `HEATNET_RULES`, в том числе в `docker-compose.yml`.

Путь с префиксом `classpath:` читается из jar. Пример правил водопровода лежит в `rules/examples/water-supply.json` и попадает в jar:

```bash
java -jar target/heatnet.jar --cli --rules=classpath:/examples/water-supply.json \
  data/samples/small-1.geojson data/out/small-1-water.geojson
make cli IN=data/samples/small-1.geojson OUT=data/out/water.geojson RULES=rules/examples/water-supply.json
```

Валидатор `check18.py` всегда берёт `rules/rules.json`, поэтому выход с другими правилами им не проверить.

> [!CAUTION]
> Числа в примере водопровода условные: пропускная способность при скорости 1,2 м/с, цены и отступы подобраны для демонстрации. Это не выдержка из СП 31.13330 и СП 42.13330. Перед реальным применением таблицы нужно заполнить по нормам.

Формат файла тот же, что у `rules.json`.

### Причины неподключения

Причина ищется после расчёта, алгоритм она не меняет. Зоны запрета строятся так же, как для поиска маршрута: существующие ОКС, запретные ограничения и точечные объекты с отступом по правилам и половиной ширины трубы диаметра, который нужен по расходу ОКС. Кольцо зон ищется в радиусе 2 км от точки подключения.

| `reason` | Когда |
|---|---|
| `no_connection_point` | у ОКС нет точки подключения |
| — (`beyond_reach_oks`) | точка дальше предельной длины наибольшего Ду (11 276 м) от существующей сети: ни один путь не уложится в предел; такие точки в список причин не входят, в сводке только их число |
| `flow_exceeds_capacity` | расход ОКС больше пропускной способности наибольшего диаметра в правилах |
| `inside_forbidden_zone` | точка подключения внутри зоны запрета с учётом отступа; `object_ids` — эти зоны |
| `enclosed` | точка окружена зонами запрета, обхода нет; `object_ids` — объекты кольца |
| `coincident_point` | точка в той же координате (до 1 см), что подключённая точка из `object_ids`: участок к ней лёг бы на участок к той |
| `no_route` | зоны точку не замыкают, но трассу не дали предельная длина, правило поворотов, углы пересечения или соседние трассы |

Причины `no_route` сервис не уточняет: для этого пришлось бы записывать отказы внутри поиска маршрута.

### Карта результата

`scripts/visualize.py` строит из входа и выхода одну HTML-страницу, которая открывается без сети и без сервера. На ней варианты во вкладках, толщина трубы по диаметру, спецпереходы отдельным цветом, подписи диаметра и расхода, сводка варианта и дополнительные критерии. Клик по объекту показывает его атрибуты.

```bash
python3 scripts/visualize.py data/samples/small-1.geojson data/out/small-1.geojson
make viz IN=data/samples/small-1.geojson OUT=data/out/small-1.geojson
```

Файл критериев ищется рядом с выходом, страница пишется в `<имя выхода>.html`. Другие пути задают `--criteria` и `--html`. Нужен только Python 3 без пакетов.

## Сборка и тесты

Нужны JDK 11, Maven 3.9 или Gradle через обёртку `./gradlew`, [uv](https://docs.astral.sh/uv/) для Python-инструментов и Docker для интеграционных тестов на Testcontainers. На macOS:

```bash
brew install openjdk@11 maven
```

### Maven

Скрипт `scripts/env.sh` выставляет `JAVA_HOME` на JDK 11: берёт уже заданный `JAVA_HOME`, а на macOS — `openjdk@11` из Homebrew. Перед Maven его нужно подключить:

```bash
source scripts/env.sh
mvn -B verify
```

`mvn verify` собирает `target/heatnet.jar` и запускает юнит-тесты `*Test` через surefire и интеграционные `*IT` через failsafe. `JobApiIT` поднимает PostgreSQL в контейнере, `PipelineSampleIT` считает `data/samples/small-1.geojson` и проверяет результат валидатором `check18.py`.

### Gradle

Протокол организаторов от 16.09.2026 просит скрипты деплоя для Maven и Gradle. `build.gradle` повторяет `pom.xml`: Spring Boot 2.6.3, Java 11, тот же набор зависимостей, `rules/` в ресурсах, `platform/` — в `static/`. Обёртка скачивает Gradle 8.13 сама:

```bash
./gradlew bootJar
./gradlew test
./gradlew integrationTest
```

Артефакт лежит в `build/libs/heatnet.jar` и запускается так же, как `target/heatnet.jar`, вместе с платформой инженера на `/`. Dockerfile, `Makefile` и `scripts/check.sh` собирают через Maven.

## Генератор и валидатор

> [!NOTE]
> Исходный датасет организаторов положите в `data/real/dataset.geojson`; его скорректированная редакция от 18.09.2026 лежит в `data/samples/small-1.geojson`. Содержимое `data/`, кроме `data/samples/` и `data/cities/`, исключено из git.

### Генератор синтетики

Делает входы в формате датасета организаторов. Одинаковый сид даёт одинаковый файл.

| Пресет | Размер сцены |
|---|---|
| `small` | 3 ОКС |
| `medium` | 20 ОКС, 200 ограничений, 300 участков сети |
| `large` | 100 ОКС |

```bash
uv run --project tools python -m heatsynth --preset medium --seed 1 --out data/synth/medium-1.geojson
uv run --project tools python -m heatsynth.check data/synth/medium-1.geojson --preset medium
```

Флаг `--pad-mb 300` дописывает далёкие полигоны, пока файл не вырастет до 300 МБ. Так проверяется потоковая обработка больших входов.

### Валидатор

`tools/validator/check18.py` не использует код сервиса и проверяет выходной файл по техническому приложению от 18.09.2026: состав объектов и ссылки узлов, повороты до 90°, прямизну спецпроходов, отступы к зданиям с финальным участком, к запретным ограничениям и сети, дерево и расходы, ДУ по расходу, монотонности и предельной длине пути, камеры и врезки, стоимость и сводку.

```bash
uv run --project tools python tools/validator/check18.py data/real/dataset.geojson data/out/r18/real.out.geojson
```

Печатает нарушения по категориям (строки `i` — справочные) и заканчивается `CHECK18 OK` с кодом 0 или `CHECK18 VIOLATIONS <n>` с кодом 1. `--depth` проверяет выход режима с учётом глубины: глубины обязательны, Kгл в стоимости, проверки G. `--no-shape` отключает проверки формы трасс B8, B16–B18, B20–B22. `make validate IN=… OUT=…` — то же без флагов. Числа берутся из `rules/rules.json`; что они совпадают с таблицами CONSTRAINTS.md, проверяет Java-тест `RulesMatchConstraintsTest`.

Все проверки решения одним скриптом: `scripts/check.sh organizers` считает оба датасета организаторов (`data/real/dataset.geojson` и `data/real/dataset-corrected.geojson`) и проверяет, что все точки подключены и `check18.py` не нашёл нарушений, `scripts/check.sh dense` — сцены «густо» 50/100/200 из `data/synth/dense-<n>.geojson`, `scripts/check.sh city` — файл «город» `data/synth/city-1.geojson`.

Стенд качества `scripts/bench.sh [метка]` печатает S, статьи стоимости и время на датасете организаторов и сценах `medium` 1–3; сцены генерируются при первом запуске. Бенч режима глубины — `scripts/depth_bench.sh <jar> <метка> 2d|3d [набор …]` на наборах `dataset`, `dataset-corrected`, `dataset-gas`, `spb`, `moscow`; входы `data/depth/` в git не лежат, скрипт рассчитан на macOS (`/usr/bin/time -l`, `stat -f`).

## Границы применения

| Тема | Как есть сейчас |
|---|---|
| **Глубина** | по умолчанию расчёт в плане, `depth_start` и `depth_end` — `null`; с `--depth` или `?depth=true` профиль строится поверх готовой 2D-трассы, план не перестраивается ([depth-optimization.md](../depth-optimization.md)) |
| **Оптимальность** | решение эвристическое, минимум стоимости не гарантируется |
| **Повороты** | не круче 90° (с запасом 0,1° на округление координат): Дейкстра отсекает ребро по предшественнику узла, поэтому путь может быть не кратчайшим среди допустимых; сборка отбрасывает дерево с более крутым поворотом |
| **Финальный участок** | к точке внутри здания ведёт прямой участок от ближайшей точки внешнего контура; другая сторона берётся, только если луч через ближайшую упирается в чужую зону отступа или снова входит в своё здание; у угла вход может стоять в ближайшей точке соседней стороны, если она дальше ближайшей точки контура не больше чем на 1 м и поворотов от этого меньше |
| **Время** | датасет организаторов (17 ОКС) — около 12 с через CLI на v0.12.0, MacBook M3 Pro, Java 11; город на 3,2 ГБ — 335 с на v0.9.0 ([замеры](../performance.md)); числа по версиям — в таблице «Версии» [README](../../README.md) |
| **Качество** | на датасете организаторов вариант 1 имеет S 12,6962 на v0.12.0 по правилам 18.09 и замечаниям экспертов 16.10, все 17 точек подключены |
| **Детерминированность** | вне городского режима поиск ограничен числом сборок, а не временем, и на другой машине даёт тот же результат, только дольше или быстрее; в городском режиме по умолчанию срока нет и подключаются те же точки, а нумерация камер меняется от прогона к прогону; если задать срок `heatnet.city.deadline`, он идёт по стенным часам и на медленной машине подключится меньше точек |
| **Точка в зоне отступа** | если точка подключения ОКС лежит внутри зоны отступа от препятствия, маршрута к ней нет, и ОКС уходит в неподключённые |
| **Масштаб графа** | граф строится за время, квадратичное по числу узлов, поэтому для каждой группы ОКС он строится на ограниченную область вокруг неё; геометрия проверяется только у рёбер, касательных к зонам |
| **Отступ от линий** | отступ от газопровода, кабеля или теплосети снимается со всего ребра, которое этот объект пересекает; сборка отбрасывает деревья, где из-за этого нарушен отступ, и на реальных данных это может стоить варианта |
| **Вставки диаметра** | при длинной трассе и малом расходе между цепочками минимального диаметра появляются короткие вставки на ступень больше; правилам это соответствует, но инженер может счесть решение странным |
| **Большие файлы** | файл 300 МБ проверен при куче JVM 1 ГБ; для входа до 3 ГБ нужна пропорционально большая куча и `JOB_WORKERS=1` |
| **Развёртывание** | совместимость `docker-compose.yml` с docker-compose 1.29.2 проверена разбором файла, развёртывание на Ubuntu Server 22 не проверялось |
