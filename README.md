## Что это

Решение кейса ДИТ Москвы на конкурсе «Лидеры цифровой трансформации» 2026: сервис, который проектирует подключение новых зданий к существующей тепловой сети города.

Инженер загружает один GeoJSON: существующую сеть с камерами и источником, точки подключения новых зданий и всё, что мешает прокладке, — застройку, дороги, трамвайные пути, газопроводы, кабели, парки, воду. Без ручной подготовки маршрутов сервис сам строит новую сеть сразу для всех зданий:

- выбирает, где врезаться в существующую сеть и какие здания подключить общими ветками;
- прокладывает трассы в обход препятствий по правилам кейса;
- подбирает диаметры труб по расходу и считает стоимость строительства;
- предлагает до трёх разных вариантов и ранжирует их по показателю S, который сочетает стоимость и длину сети;
- по запросу строит профиль трубы по глубине с обходом подземных коммуникаций;
- отдаёт результат одним GeoJSON и показывает его в 3D на платформе инженера «Тепломаршрут».

Сервис справляется и с кварталом, и с целым городом, одинаковый вход всегда даёт одинаковый результат. Соответствие результата правилам кейса проверяет независимый проверщик [check18](tools/validator/check18.py). Сами правила — в [CONSTRAINTS.md](docs/architecture/CONSTRAINTS.md).

## Быстрый старт

Нужен Docker с compose; для расчёта из командной строки ещё JDK 11, Maven и [uv](https://docs.astral.sh/uv/). С docker-compose 1.29 вместо `docker compose` — `COMPOSE=docker-compose make up`. Подробно — в [INSTRUCTION.md](INSTRUCTION.md).

```bash
make up
curl -s -X POST -H 'Content-Type: application/geo+json' \
  --data-binary @data/samples/small-1.geojson http://localhost:8080/api/v1/jobs
curl -s http://localhost:8080/api/v1/jobs/<id>
curl -s http://localhost:8080/api/v1/jobs/<id>/result -o result.geojson
```

Посчитать файл без веба и базы и сразу проверить выход проверщиком:

```bash
make run IN=data/samples/small-1.geojson OUT=data/out/small-1.geojson
```

Swagger UI — `http://localhost:8080/swagger-ui/index.html`, все команды — `make help`.

Тепломаршрут — веб-платформа, на которой инженер разбирает результат сервиса в 3D:

- новая сеть под землёй рядом с газом, кабелями, водопроводом, канализацией и существующей теплосетью, трубы в настоящем габарите;
- продольный профиль каждой трассы, как в Civil 3D;
- пересечения по высоте с готовым обходом сверху или снизу и его ценой;
- ручная правка трассы с проверкой норм `check18` и пересчётом стоимости и S;
- выгрузка в GeoJSON и в DXF для AutoCAD;
- сравнение вариантов, пролёт вдоль трассы, срез, рентген, поиск;
- целый район города в браузере, телефон и планшет, светлая и тёмная тема.

Что умеет платформа, со снимками — [docs/PLATFORM.md](docs/PLATFORM.md).

## Как считает

```mermaid
flowchart LR
    A[GeoJSON] --> B[Потоковое чтение<br/>и перевод в метры]
    B --> C[Граф видимости<br/>вокруг препятствий]
    C --> D[Кандидаты врезки<br/>по грубой стоимости]
    D --> E[Дерево врезки<br/>и точный скелет]
    E --> F[Локальный поиск<br/>по разбиениям ОКС]
    F --> G[Форма по осям,<br/>диаметры, камеры, стоимость]
    G --> H[До 3 вариантов<br/>GeoJSON]
```

Маршруты ищутся по графу видимости вокруг препятствий с отступами, здания присоединяются к дереву врезки по одному, скелет дерева уточняется точной динамикой по сеткам мест камер, локальный поиск переставляет здания между врезками. Готовые варианты доводятся до строгой формы и получают диаметры, камеры и стоимость. Вход из тысяч зданий считается по районам параллельно.

Пошагово, с таблицей «правило → как соблюдается → проверка» и угловыми случаями — [algorithm.md](docs/algorithm.md); по классам — [ARCHITECTURE.md](docs/architecture/ARCHITECTURE.md); глубина — [раздел ниже](#глубина).

## Глубина

Дополнительная задача кейса: сервис строит не только трассу в плане, но и профиль трубы по глубине, чтобы она прошла выше или ниже газа, кабелей и существующей теплосети с нужным просветом. Режим включается флагом `--depth` в командной строке, параметром `?depth=true` в API или флажком «С учётом глубины» на платформе. Трасса в плане, диаметры и камеры остаются те же, что в 2D: приложение 18.09 разрешает строить глубину поверх готовой трассы. Без флага 2D-выход побайтово прежний.

Какие правила соблюдает профиль:

- верх трубы не мельче 0,7 м; на всём спецпереходе под дорогой — не мельче 1,0 м, под трамваем — не мельче 1,2 м;
- уклон не круче 0,10, в узле у всех участков одна глубина;
- у пересечения с газом, кабелем и существующей теплосетью труба на 2 м по трассе в каждую сторону лежит на постоянной глубине, выше или ниже объекта с просветом из Таблицы 2;
- глубже 3,0 м стоимость участка умножается на коэффициент Kгл = 1 + 0,1 · (h − 3);
- камеры стоят на глубине 3,0 м ± 5 см (строительный допуск), как сказали эксперты на встрече 16.10.2026; внутри допуска глубина выбирается по стоимости. Если иначе профиль не помещается, камера сдвигается на самую дешёвую допустимую глубину и помечается в выходе `depth_shifted: true`;
- излом профиля и переход через 3,0 м делят участок техническим узлом.

Стоимость зависит только от того, насколько профиль уходит глубже 3,0 м. Глубины узлов подбираются покоординатным спуском, профиль между узлами — динамикой по зонам пересечений. Из профилей одной стоимости берётся тот, где меньше вертикальных изломов, затем тот, что ближе к 3,0 м. Профиль считается отдельным проходом: на датасете — 3 мс, на районе Москвы с 5 500 участками — 0,39 с.

Дешевле профиля на той же трассе нет, и это проверено, а не только заявлено. Независимый скрипт [depth_bound.py](tools/validator/depth_bound.py) не использует код сервиса и считает нижнюю границу стоимости любого допустимого профиля. На датасетах организаторов стоимость выхода совпадает с этой границей с точностью до копеек округления, на районе Москвы разрыв — 913 руб. на 9,6 млрд руб., на 20 трудных случаях из `data/samples/depth` — не больше 316 руб.

```bash
java -jar target/heatnet.jar --cli --depth <вход> <выход>
uv run --project tools python tools/validator/check18.py --depth <вход> <выход>
uv run --project tools python tools/validator/depth_bound.py <вход> <выход>
```

Правила по пунктам с источниками, доказательство границы, замеры и сверка с ответами экспертов — в [depth-optimization.md](docs/depth-optimization.md).

## API

| Запрос | Что делает |
|---|---|
| `POST /api/v1/jobs` | принимает GeoJSON телом запроса, ставит задачу в очередь, отвечает `202` с `id`; `?depth=true` — расчёт с учётом глубины |
| `GET /api/v1/jobs` | список задач, новые первыми |
| `GET /api/v1/jobs/{id}` | статус `QUEUED`, `RUNNING`, `DONE` или `FAILED`, ошибки входа по объектам, после `DONE` сводки вариантов |
| `GET /api/v1/jobs/{id}/result` | выходной GeoJSON; `409`, пока задача не готова |
| `GET /api/v1/jobs/{id}/input` | исходный файл байт в байт |

Невалидный вход не считается: задача получает `FAILED` со списком проблем «объект, поле, что не так». Формат выхода — в разделе 13 [CONSTRAINTS.md](docs/architecture/CONSTRAINTS.md), поля сводки и критериев — в [BACKEND.md](docs/architecture/BACKEND.md).

## Проверка качества

| Проверка | Команда |
|---|---|
| Юнит-тесты, без Docker | `make test-unit` |
| Юнит- и интеграционные тесты с PostgreSQL | `make test-java` |
| Проверщик выхода по правилам 18.09.2026 | `make validate IN=… OUT=…` |
| Датасет организаторов: расчёт и проверка | `make real` (датасет кладут в `data/real/dataset.geojson`) |
| Оба датасета организаторов: `data/real/dataset.geojson` и `data/real/dataset-corrected.geojson` | `scripts/check.sh organizers` |
| Сцены «густо» и город, входы `data/synth/dense-{50,100,200}.geojson` и `data/synth/city-1.geojson` в репозиторий не входят | `scripts/check.sh dense`, `city` |
| Стенд качества: S, стоимость, время | `scripts/bench.sh <метка>` |
