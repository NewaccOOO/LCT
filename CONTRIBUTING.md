# Как работать с репозиторием

Файл для людей и агентов, которые вносят изменения. Здесь порядок чтения, раскладка каталогов, правила для документов и команды проверки. Что делает продукт, описано в [README.md](README.md), как запускать и проверять бекенд — в [architecture/BACKEND.md](architecture/BACKEND.md).

## С чего начать

Читать сверху вниз, каждый следующий документ опирается на предыдущий:

1. [architecture/CONSTRAINTS.md](architecture/CONSTRAINTS.md) — правила кейса из ТЗ организатора. Если код или чат противоречат этому файлу, прав файл.
2. [architecture/ARCHITECTURE.md](architecture/ARCHITECTURE.md) — из каких частей состоит сервис и как проходит расчёт. Запуск, API и сборка — в [architecture/BACKEND.md](architecture/BACKEND.md).
3. [docs/interpretation.md](docs/interpretation.md) — как читаются спорные места CONSTRAINTS.md, одинаково для Java и Python.
4. `docs/specs/<slug>/index.md` — пакет спеки той задачи, над которой идёт работа.

## Где что лежит

| Путь | Что там | Кто меняет |
|---|---|---|
| `architecture/` | актуальная архитектура, практика бекенда (запуск, API, сборка) и ограничения кейса | агенты по итогам каждой задачи, которая меняет устройство сервиса |
| `src/main/java/ru/lct/heatnet/` | сервис на Java 11 и Spring Boot | код задач |
| `src/test/java/` | юнит-тесты `*Test` и интеграционные `*IT`, Maven | вместе с кодом |
| `rules/rules.json` | все числа кейса: таблицы, коэффициенты | только через спеку, Java и Python читают только этот файл |
| `tools/synth`, `tools/validator`, `tools/scenarios` | генератор, валидатор и сценарии на Python, один uv-проект | код задач |
| `tests/` | pytest-тесты Python-пакетов: `validator/`, `scenarios/` | вместе с кодом |
| `scripts/gates/` | скрипты приёмки, на них ссылаются `GATES.md` пакетов | вместе со спекой |
| `docs/specs/<slug>/` | пакет спеки задачи: brief, research, requirements, design, tasks, GATES, adr | агент, который ведёт задачу |
| `docs/testing/` | отчёты о прогонах и дефекты | агент по итогам прогона |
| `data/samples/` | небольшой набор для пробы, остальное в `data/` не коммитится | редко |

## Документы

**`architecture/`** описывает, как сервис устроен сейчас, а не как планировался. Задача, которая меняет пакет, поток данных или формат файлов, заканчивается правкой `ARCHITECTURE.md` в том же коммите. `CONSTRAINTS.md` внутри задач не правится: его сверяет гейт `scripts/gates/constraints_unchanged.sh` с веткой `main`. Изменение возможно только по новому документу организатора и отдельным коммитом.

**`docs/specs/<slug>/`** — рабочий пакет одной задачи. Файлы и их роли перечислены в `index.md` каждого пакета, там же статус и промт запуска. Факт живёт в одном документе, остальные ссылаются на его ID. Прошлые пакеты не редактируются, кроме статуса в `index.md`: новая работа — новый пакет.

Тексты в репозитории на русском. Имена переменных, функций и классов на английском.

## Проверка

Все команды из корня репозитория. Перед Maven нужен JDK 11 через `scripts/gates/env.sh`:

```bash
source scripts/gates/env.sh
mvn -B verify
```

Python-тесты:

```bash
uv run --project tools pytest tests/validator tests/scenarios
```

Приёмка задачи — гейты из `docs/specs/<slug>/GATES.md`, у каждого критерия `AC-` и `NFR-` свой гейт с тем же ID. Отдельный гейт запускается своим скриптом, например `scripts/gates/scenarios.sh`. Готовность подтверждает прогон гейтов, а не отчёт исполнителя.

## Версии

Версия — аннотированный git-тег `vX.Y.Z` на коммите в `main`. Та же версия записана в `pom.xml` и `build.gradle`. Каждая версия — строка в таблице «Версии и динамика качества» в [README.md](README.md#-версии-и-динамика-качества): по ней видно, как менялись S и подключение на датасете организаторов, сценах «густо» и городе; график `docs/assets/progress.svg` строится из этой таблицы командой `python3 scripts/readme_assets.py`. История по прежним правилам лежит там же под спойлером. Коммит только с документацией версию не получает.

### Какую цифру поднимать

| Часть | Когда | Пример |
|---|---|---|
| X | сдача организаторам или несовместимое изменение формата входа или выхода | 1.0.0 на финальной сдаче |
| Y | меняется выход на датасете организаторов: алгоритм, правила кейса, параметры поиска | 0.2.0 → 0.3.0 после перехода на бюджет сборок |
| Z | выход на датасете побайтно прежний: ускорение, рефакторинг, инструменты, исправление вне датасета | 0.3.0 → 0.3.1 после надбавок, не изменивших датасет |

Для версии Z выход сверяется с предыдущей версией: `cmp data/out/bench/dataset-vX.Y.Z.geojson data/out/bench/dataset-<предыдущая>.geojson`. Если файлы различаются, это версия Y.

### Как выпустить версию

1. В ветке задачи зелёные `mvn -B verify`, `make test-python`, `make test-scenarios`, а `make real` печатает `VALIDATION PASSED`.
2. `scripts/bench.sh vX.Y.Z` на свободной машине, одним процессом. Из строки `dataset` берутся S, стоимость и время.
3. Версия поднимается в `pom.xml` и `build.gradle`, в таблицу README добавляется строка сверху: версия, дата, S, стоимость, время, что изменилось одной-двумя фразами.
4. Коммит `Версия X.Y.Z: <что изменилось>`, слияние в `main`.
5. Тег на этом коммите в `main` и пуш тега:

   ```bash
   git tag -a vX.Y.Z -m "Версия X.Y.Z: S <число>, <стоимость> млн руб., <время> с на датасете организаторов"
   git push origin main vX.Y.Z
   ```

Опубликованный тег не переносится и не удаляется. Ошибка в числах исправляется следующей версией.

### Лучшая рабочая версия

Лучшая версия — с наименьшим S на датасете организаторов при зелёных тестах и валидаторе. Её сообщение тега начинается со слов «Лучшая рабочая версия», и она указана в строке «Лучшая рабочая версия» раздела «Версии и динамика качества» в README. Если новая версия лучше, при выпуске меняется эта строка README, а новый тег получает сообщение «Лучшая рабочая версия: …».

В `main` не вливается изменение, которое ухудшает S на датасете, если в тех же правилах кейса есть версия лучше. Исключение — новый документ организатора, который меняет правила: тогда в строке таблицы пишется, что S со старыми версиями не сравнивается.

Вернуться к лучшей или любой версии:

```bash
git tag -l "v*" --sort=-v:refname -n1
git checkout v0.3.1
git worktree add ../LCT-v0.3.1 v0.3.1
git switch -c fix/<что-чиним> v0.3.1
```

Первая команда печатает версии с сообщениями тегов. `checkout` переключает текущую папку на версию только для чтения, `worktree add` кладёт её рядом, не трогая рабочую папку, `switch -c` заводит ветку исправления от версии.

## Коммиты

Ветка от `main`, одна задача — одна ветка. Сообщение коммита: тема и тело по делу, без трейлеров атрибуции. Файлы из `data/`, кроме `samples/`, и `target/` в коммит не попадают.
