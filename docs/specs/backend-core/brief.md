# Бриф: бекенд трассировки тепловых сетей

## Зачем

Команда участвует в конкурсе «Лидеры цифровой трансформации» 2026 с кейсом ДИТ Москвы: сервис, который автоматически строит подключение новых зданий к тепловой сети. Сейчас кода нет, есть только правила кейса в [CONSTRAINTS.md](../../../CONSTRAINTS.md). Промежуточная сдача требует прототип загрузки данных и построение хотя бы части сети, и на неё около недели. Бекенд делается первым, фронт прикручивается позже к готовому API. Вместе с бекендом нужен независимый валидатор результата, потому что эксперты сначала проверяют формальные правила, а эталонного ответа организатор не даёт.

## Цели

- **G-1** REST-сервис на Java 11 и Spring Boot 2.6.3 принимает входной GeoJSON, для всех перспективных ОКС строит не меньше двух содержательно разных вариантов подключения и отдаёт выходной GeoJSON по схеме раздела 13 CONSTRAINTS.md.
- **G-2** Независимый валидатор на Python проверяет выходной файл по правилам разделов 5–13 CONSTRAINTS.md и на результатах сервиса для синтетических наборов печатает `VALIDATION PASSED`.
- **G-3** Генератор синтетических наборов той же структуры, что конкурсный, даёт входные файлы трёх размеров с воспроизводимостью по сиду.
- **G-4** `docker-compose up` поднимает приложение и PostgreSQL, Swagger UI отвечает, сборка и все тесты проходят одной командой Maven.

## Не-цели

Разумные варианты, которые сознательно не делаем. Исполнитель их не реализует, даже если «заодно быстро».

- **NG-1** Фронтенд и любая визуализация карты — отдельный пакет после бекенда.
- **NG-2** Дополнительная задача по глубине (раздел 14 CONSTRAINTS.md) — отдельный пакет; поля `depth_start` и `depth_end` в выходе всегда `null`.
- **NG-3** Гидравлический расчёт, мощность источника, продольный профиль — раздел 15 CONSTRAINTS.md.
- **NG-4** PostGIS и пространственные запросы в базе — геометрия считается в памяти на JTS, база хранит только задачи и метаданные файлов.
- **NG-5** Точное решение задачи Штейнера с доказательством минимума стоимости — берётся эвристика, которая укладывается в NFR-1.
- **NG-6** Аутентификация, пользователи, квоты — до 50 пользователей обслуживаются без учёток.
- **NG-7** OpenSearch — выбран PostgreSQL.

## Бюджет

- Календарно: до 2026-09-22.
- Исполнителю: три полных прохода по волнам tasks.md. Если после третьего прохода остаются красные гейты, работа сдаётся как «передано с долгом» с перечнем красных гейтов в отчёте.
- Нагрузочный порог одного расчёта: 120 секунд на среднем синтетическом наборе (NFR-1), это допущение A-1, а не требование организатора.

## Границы автономии

Во время исполнения пользователя рядом нет, поэтому шага «спросить» в процессе нет.

- **Делает сам:** ставит тулчейн (`brew install openjdk@11 maven`, Python-окружение через `uv`); добавляет Maven-зависимости из research.md и любые другие с открытой лицензией; создаёт ветку `feature/backend-core`, коммитит и пушит её; создаёт и правит любые файлы репозитория, кроме перечисленных ниже.
- **Запрещено:** merge или push в `main`; менять числа и правила в CONSTRAINTS.md; удалять или переписывать документы пакета `docs/specs/backend-core/` кроме журнала в tasks.md, строки статуса в index.md и добавления гейтов; зашивать в код координаты, ID или структуру конкретного набора данных; трейлер `Co-Authored-By` в коммитах; менять `CHECK:` одобренных гейтов без записи `ABANDON`.
- **Если упёрся:** фиксирует в журнале tasks.md, выбирает консервативный вариант (меньше кода, правило трактуется строже) и идёт дальше; невыполнимый гейт помечает `ABANDON` с причиной.

## Контекст до старта

- [CONSTRAINTS.md](../../../CONSTRAINTS.md) — единственный источник правил кейса. Исходные PDF и DOCX организатора в репозитории отсутствуют и исполнителю не нужны.
- [research.md](research.md) — версии библиотек и выбранные алгоритмы, находки R-*.
- Конкурсного набора данных нет. Все гейты работают на синтетике из генератора (G-3). Когда набор появится, он кладётся в `data/` и прогоняется теми же командами без изменения кода.
- На машине исполнителя: macOS, Homebrew, `uv`, Docker Desktop с compose v2. JDK 11 и Maven ставятся исполнителем. Файл compose пишется в формате 3.8, который читает и docker-compose 1.29.2 на стенде организатора.

## Как выполнить формально без пользы

Способы набить критерии мусором и чем спека это запрещает.

- Валидатор, который всегда печатает `VALIDATION PASSED` → AC-3.2: для каждого правила есть испорченная фикстура, на которой валидатор обязан упасть с именем правила.
- Сервис объявляет все ОКС неподключёнными и платит штраф → AC-2.1: на синтетических наборах список `unconnected_oks_ids` пуст.
- Прямые линии сквозь здания → AC-2.7: валидатор считает пересечения с запрещёнными полигонами и отступы через буферы.
- Три копии одного варианта → AC-2.12: варианты обязаны различаться точкой врезки или составом ОКС на общем стволе.
- Ступенчатые трассы из сеточного поиска → AC-2.13: ограничение на число поворотов на пути до каждого ОКС.
- Генератор без препятствий, чтобы трассировка была тривиальной → AC-4.2: в среднем наборе прямая от ОКС к сети пересекает запрещённый полигон не меньше чем у половины ОКС.
- Тесты, помеченные `@Disabled`, или пустые тестовые классы → AC-5.2: гейт считает выполненные тесты и требует ноль пропущенных.
- Числа таблиц скопированы в код в нескольких местах с расхождениями → C-3: таблицы живут в одном файле `rules/rules.json`, который читают и Java, и Python, и он сверяется с CONSTRAINTS.md по AC-3.3.
- Скрипты гейтов глушат ошибки (`|| true`, `exit 0`) и печатают маркер сами → гейт G1 требует `set -euo pipefail` в каждом скрипте и запрещает эти конструкции; маркеры `RULE …`, `SYNTH …`, `RULES MATCH` печатают только Python-модули, маркер `PIPELINE DONE` только Java CLI.
- Правила реконструкции и специальных проходов проходят вхолостую, потому что на синтетике нечего реконструировать и нечего пересекать → AC-4.2 требует перегруженный участок у каждого ОКС и дороги на прямой у пяти ОКС, а `validate_rule.sh` для правил `reconstruction` и `special` требует хотя бы один объект реконструкции и один специальный участок суммарно по шести выходам.
