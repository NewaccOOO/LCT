# Как вносить изменения

Порядок чтения, раскладка каталогов, команды проверки и выпуск версий. Что делает сервис — в [README.md](README.md), как его запустить — в [INSTRUCTION.md](INSTRUCTION.md).

## С чего начать

Читать сверху вниз, каждый следующий документ опирается на предыдущий:

1. [architecture/CONSTRAINTS.md](architecture/CONSTRAINTS.md) — правила кейса из документов организатора. Если код противоречит этому файлу, прав файл.
2. [architecture/ARCHITECTURE.md](architecture/ARCHITECTURE.md) — из каких частей состоит сервис и как проходит расчёт.
3. [docs/interpretation.md](docs/interpretation.md) — как сервис и проверщик одинаково читают спорные места правил.
4. [architecture/BACKEND.md](architecture/BACKEND.md) — API, критерии, сборка и тесты подробно.

## Где что лежит

| Путь | Что там |
|---|---|
| `src/main/java/ru/lct/heatnet/` | сервис на Java 11 и Spring Boot |
| `src/test/java/` | юнит-тесты `*Test` и интеграционные `*IT` |
| `rules/rules.json` | все числа кейса: диаметры, цены, отступы, коэффициенты; сервис и проверщик читают только его |
| `rules/examples/` | пример правил для другого ресурса (водопровод) |
| `tools/validator/check18.py` | независимый проверщик выхода по правилам 18.09.2026 |
| `tools/synth/` | генератор синтетических входов |
| `scripts/` | проверка решения `check.sh`, стенд `bench.sh`, карта результата `visualize.py`, картинки документации |
| `architecture/` | правила кейса и устройство сервиса |
| `docs/` | толкования правил, история поиска алгоритма, замеры, ADR |
| `data/samples/` | небольшой пример входа; остальное в `data/` в git не попадает |

## Правила для изменений

- **Код и `architecture/` меняются вместе.** Изменение, которое меняет пакет, поток данных или формат файлов, заканчивается правкой `ARCHITECTURE.md` в том же коммите.
- **`CONSTRAINTS.md` меняется только по новому документу организатора** и отдельным коммитом. Толкования спорных мест пишутся в `docs/interpretation.md`.
- **Числа кейса живут только в `rules/rules.json`.** В коде их не дублируют; тест `RulesMatchConstraintsTest` сверяет файл с таблицами `CONSTRAINTS.md`.
- **Ускорение не меняет выход.** Правка, заявленная как ускорение, даёт на датасете организаторов побайтово тот же GeoJSON. Правка качества не делает вариант 1 хуже ни на одном наборе.
- Тексты на русском, имена переменных, функций и классов — на английском.

## Проверка

Все команды из корня репозитория. `scripts/env.sh` выставляет JDK 11: из `JAVA_HOME`, а на macOS — из Homebrew.

```bash
source scripts/env.sh
mvn -B verify
```

| Проверка | Команда | Что ловит |
|---|---|---|
| юнит-тесты | `make test-unit` | ошибки расчёта, чтения и записи |
| юнит- и интеграционные тесты | `make test-java` | то же плюс API с PostgreSQL в Testcontainers и сквозной прогон с проверщиком; нужен Docker |
| проверка выхода | `make run IN=… OUT=…` | считает вход и проверяет выход `check18.py` |
| датасет организаторов | `scripts/check.sh organizers` | оба файла организаторов в `data/real/` считаются, все точки подключены, `check18` без нарушений |
| плотные сцены и город | `scripts/check.sh dense`, `scripts/check.sh city` | нужны входы `data/synth/dense-{50,100,200}.geojson` и `data/synth/city-1.geojson`, в репозитории их нет |
| стенд качества | `scripts/bench.sh <метка>` | S, статьи стоимости и время на датасете организаторов и сценах `medium` |

## Версии

Версия — аннотированный git-тег `vX.Y.Z` на коммите в `main`. Та же версия записана в `pom.xml` и `build.gradle`. Каждая версия — строка в таблице «Версии и динамика качества» в [README.md](README.md#-версии-и-динамика-качества).

| Часть | Когда поднимать | Пример |
|---|---|---|
| X | сдача организаторам или несовместимое изменение формата входа или выхода | 1.0.0 на финальной сдаче |
| Y | меняется выход на датасете организаторов: алгоритм, правила, параметры поиска | 0.6.3 → 0.7.0 |
| Z | выход на датасете побайтово прежний: ускорение, рефакторинг, инструменты | 0.6.2 → 0.6.3 |

Выпуск:

1. Зелёные `mvn -B verify` и `scripts/check.sh organizers`.
2. `scripts/bench.sh vX.Y.Z` на свободной машине, одним процессом: из строки `dataset` берутся S, стоимость и время.
3. Версия поднимается в `pom.xml` и `build.gradle`, в таблицу README добавляется строка сверху, графики пересобираются: `uv run --project tools python scripts/readme_assets.py`.
4. Коммит `Версия X.Y.Z: <что изменилось>`, слияние в `main`.
5. Тег на этом коммите и пуш:

   ```bash
   git tag -a vX.Y.Z -m "Версия X.Y.Z: S <число>, <стоимость> млн руб., <время> с на датасете организаторов"
   git push origin main vX.Y.Z
   ```

Опубликованный тег не переносится и не удаляется. Ошибка в числах исправляется следующей версией. В `main` не вливается изменение, которое ухудшает S на датасете организаторов при тех же правилах кейса.

Вернуться к любой версии:

```bash
git tag -l "v*" --sort=-v:refname -n1
git checkout v0.7.0
```

## Коммиты

Одна задача — одна ветка от `main`. Сообщение коммита — тема и тело по делу. Файлы из `data/`, кроме `samples/`, и каталоги `target/`, `build/` в коммит не попадают.
