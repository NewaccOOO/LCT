## 1. Как запустить

Пошагово, со всеми способами запуска и разбором ошибок, — [INSTRUCTION.md](../INSTRUCTION.md). Коротко, из корня репозитория:

```bash
make up                                                     # сервис + PostgreSQL в Docker
curl -s -X POST -H 'Content-Type: application/geo+json' \
  --data-binary @data/samples/small-1.geojson http://localhost:8080/api/v1/jobs          # → id
curl -s http://localhost:8080/api/v1/jobs/<id>               # ждём DONE
curl -s http://localhost:8080/api/v1/jobs/<id>/result -o result.geojson

make run IN=data/samples/small-1.geojson OUT=data/out/small-1.geojson   # CLI без веба и базы + check18
```

Режим глубины: `java -jar target/heatnet.jar --cli --depth <вход> <выход>` или `POST /api/v1/jobs?depth=true`. Swagger: `http://localhost:8080/swagger-ui/index.html`. Все числа кейса — в `rules/rules.json`, другой файл правил — `--rules=<путь>` или `HEATNET_RULES`.

## 2. Алгоритм поиска маршрутов и совместного подключения ОКС

Подробно по шагам, с таблицей «правило → как соблюдается → проверка» и угловыми случаями — [algorithm.md](algorithm.md). По классам — [ARCHITECTURE.md](architecture/ARCHITECTURE.md).

```mermaid
flowchart TD
    read[Чтение и проверка входа] --> big{больше 500 точек?}
    big -->|да| city[Городской режим: прямые подключения + районы до 16 ОКС]
    big -->|нет| graph[Зоны отступа, спецпереходы, граф видимости]
    graph --> ties[Кандидаты врезки]
    ties --> tree[Дерево врезки: жадное + точный скелет]
    tree --> search[Локальный поиск по разбиениям ОКС]
    search --> form[До 3 вариантов, доводка формы]
    city --> asm
    form --> asm[Сборка: расход, Ду, предельная длина, стоимость, S]
    asm --> write[Запись GeoJSON]
```

**Чтение.** Вход читается потоком, без загрузки целиком в память. Ошибки данных (нет поля, невалидная геометрия, повтор `id`, ссылка в пустоту) копятся по объектам; при хотя бы одной расчёт не запускается. Принимается и формат ТЗ, и формат датасета организаторов ([interpretation.md](interpretation.md)). Длины и отступы — в метрах, EPSG:32637.

**Препятствия и спецпереходы.** Все здания, включая своё здание точки, — препятствия. Зона запрета — отступ по табл. 2 плюс половина ширины пары труб по Ду; проверяется точным расстоянием до сторон. Дорогу, трамвай, газопровод, кабель и существующую сеть трасса пересекает только спецпереходом: один прямой отрезок, у дороги и путей под углом не меньше 45°, на границах — технические узлы.

**Маршрут.** Граф видимости: узлы — выпуклые вершины зон и узлы у спецобъектов, рёбра — отрезки вне зон. Вес — длина плюс надбавка `(Kспец − 1) × длина спецучастка`. Дейкстра не пропускает поворот круче 90°. Готовый путь спрямляется: углы срезаются хордами, лишние вершины, двойные повороты и зигзаги убираются.

**Врезка.** Для группы точек берутся ближайшие камеры и проекции на ближайшие трубы. Существующая камера ближе 10 м со свободным местом обязательна, иначе на трубе ставится новая камера. Деревья строятся на лучших по грубой стоимости кандидатах.

**Совместное подключение — дерево врезки.** От врезки растёт дерево эвристикой Такахаши–Мацуямы: на каждом шаге присоединяется точка с самым дешёвым маршрутом до дерева, в месте касания — камера ветвления (не больше четырёх примыканий). Надбавки за новую камеру и за лишний луч врезки переводятся в метры по весам S. Финальный участок — один прямой отрезок от ближайшей допустимой точки контура своего здания (п. 2.2).

**Точный скелет (с v0.10.0).** Жадное дерево ставит камеры там, где ветка впервые коснулась дерева, а не там, где дешевле. Поэтому для деревьев с 3–16 точками строится ещё одно: места камер — узлы сетки 20 м (на входах до 40 точек самое большое дерево черновика — ещё на сетках 21–30 м), вес пары мест — длина маршрута, динамика Дрейфуса–Вагнера по подмножествам точек (`ExactSteiner`) находит дерево с наименьшей ценой в S. Камеры затем доводятся без сетки. Скелет заменяет жадное дерево, только если после доводки формы не хуже ни по одному показателю: S, точки без сети, повороты, пары поворотов, дефекты формы. С v0.11.0 скелет строится для каждого черновика, а не только для лучшего. Выключается `-Dheatnet.exact=false`.

**Какие ОКС подключать вместе.** Точки ближе 300 м по цепочке — одна группа. Черновики строятся по разбиениям точек на блоки, у каждого блока своя врезка. Локальный поиск сливает блоки, переносит и выделяет точки, разбивает блоки, меняет врезку. Бюджет — 1000 сборок, остановка после 100 сборок без улучшения. Поиск ограничен числом сборок, а не временем, поэтому вне городского режима выход на любой машине побайтово один и тот же. Главный выигрыш дают слияния: одна врезка и общий ствол вместо нескольких.

**Варианты.** Из лучших черновиков берётся до трёх содержательно разных: другая врезка, разбиение или трасса. Вариант с лишней неподключённой точкой не выдаётся. Ранг 1 — наименьший S.

**Форма по замечаниям экспертов 16.10.2026 (с v0.10.0).** Трасса идёт прямыми вдоль осей застройки, а не диагоналями; один поворот 90° вместо двух по 45°; без изломов вдоль коридоров. Пары поворотов 60–120° со звеном короче 30 м заменяются одной вершиной. Перекладка по осям принимается, если участок не длиннее прежнего в 1,3 раза и вершин не больше. Такая трасса длиннее: без ортогональной формы (`-Dheatnet.square=false`) S = 12,4044 вместо 12,6962.

**Сборка.** Расход участка — сумма `flow_tph` точек ниже по дереву. Ду — наименьший по пропускной способности, не убывает к врезке и укладывает в предельную длину каждый путь от точки до места присоединения. Технический узел — на каждой границе спецзоны. Затем повторно проверяются отступы, повороты и касания трасс: нарушение отбрасывает вариант. Стоимость — участки (длина × цена метра Ду × Kспец), новые камеры по Ду, врезки в существующие камеры по 5 млн руб., штрафы. S округляется до четырёх знаков.

**Городской режим (больше 500 точек).** Граф на весь вход строился бы часами. Точки у сети подключаются прямыми участками. Точки дальше 11 276 м от сети недостижимы: даже Ду 1400 не укладывает путь в предельную длину. Остальные делятся на районы до 16 ОКС и считаются теми же шагами параллельно, от ближних к сети к дальним. По умолчанию срока нет: считаются все районы (п. 2.5); срок `heatnet.city.deadline` задаётся только для показа.

Почему выбраны граф видимости и поиск по разбиениям, а не сетка, MILP или хирургия деревьев, — [ADR-0001](adr/0001-routing-approach.md), [ADR-0002](adr/0002-partition-local-search.md). Что пробовали и что не сработало — [research.md](research.md).

## 3. ОКС без маршрута

Не подключить точку можно только если допустимого маршрута нет (п. 2.5). Намеренно оставлять доступную точку без сети ради S нельзя: черновик или вариант, где без сети точек больше, чем в лучшем, не выдаётся.

Прежде чем признать точку неподключённой, сервис пробует:
- широкую область графа вместо обычной;
- точный поиск по состояниям «узел и откуда пришли» — находит путь, в который нужно войти с другой стороны;
- маршрут на графе фактического Ду, если дерево отброшено только из-за отступов при выросшем Ду;
- места врезки на трубах в радиусе 150 м;
- до восьми следующих выходов из здания, если от ближайшего маршрута нет ни к одной врезке (разъяснение 15 от 29.09).

Если ничего не дало трассы, остальная сеть сохраняется, а точка попадает в выход так:
- `unconnected_oks_ids` в `variant_summary` — ID с исходным типом (строка или число);
- `unconnected_penalty` — 100 млн руб. + 500 тыс. руб. × расход т/ч за каждую точку, входит в `calculated_cost` и S;
- причина — в `criteria.unconnected_reasons` сводки задачи API и в `*.criteria.json` рядом с выходом CLI.

| `reason` | Когда |
|---|---|
| `no_connection_point` | у ОКС нет точки подключения |
| `flow_exceeds_capacity` | расход больше пропускной способности наибольшего Ду |
| `inside_forbidden_zone` | точка внутри зоны запрета с учётом отступа; `object_ids` — эти зоны |
| `enclosed` | точка окружена зонами запрета, обхода нет |
| `coincident_point` | точка в той же координате, что подключённая |
| `no_route` | зоны точку не замыкают, но трассы не дали предельная длина, повороты, углы пересечения или соседние трассы |

Точки дальше досягаемости сети в список причин не входят, в сводке только их число (`beyond_reach_oks`). Подробно — [BACKEND.md](architecture/BACKEND.md#причины-неподключения). На датасетах организаторов неподключённых точек нет; это проверяет `scripts/check.sh organizers`.

## 4. Выходные данные

Один GeoJSON `FeatureCollection` в EPSG:4326, все варианты в одном массиве, различаются по `variant_id`. Формат — раздел 13 [CONSTRAINTS.md](architecture/CONSTRAINTS.md). Точки подключения повторно не передаются, ссылки на объекты входа сохраняют их тип.

| `object_type` | Геометрия | Поля |
|---|---|---|
| `heat_network` | LineString | `start_node_id`, `end_node_id`, `flow_tph`, `diameter`, `length`, `laying_method` (`base` / `special`), `depth_start`, `depth_end`, `cost` |
| `heat_chamber` | Point | `diameter` (наибольший Ду примыканий), `cost` |
| `technical_node` | Point | граница спецперехода |
| `variant_summary` | нет | `rank`, `construction_cost`, `chamber_construction_cost`, `existing_chamber_tie_in_count`, `existing_chamber_tie_in_cost`, `unconnected_penalty`, `calculated_cost`, `new_network_length`, `score`, `unconnected_oks_ids` |

В 2D `depth_start` и `depth_end` — `null`. В режиме глубины добавляются `depth_crossings` у участка, `depth_m` и `depth_shifted` у камеры, `reason: depth_profile` у технического узла (раздел 5).

Помимо GeoJSON:
- API отдаёт статус задачи, ошибки входа по объектам и сводки вариантов с `criteria`: пересечённые объекты, повороты, длина спецпереходов, надбавки, удельная стоимость, причины неподключения;
- CLI пишет то же в `<выход>.criteria.json`. Поля — [BACKEND.md](architecture/BACKEND.md#дополнительные-критерии).

**Проверка выхода.** Проверщик `tools/validator/check18.py` написан отдельно от сервиса и читает только вход, выход и `rules/rules.json`. Он заново считает отступы, углы, расходы, Ду, стоимость и S. Категории: A — состав и ссылки, B — геометрия и форма, C — расходы и Ду, D — камеры, E — стоимость и сводка, G — глубина (`--depth`). Строгий запуск — без `--no-shape`. Последняя строка `CHECK18 OK` — нарушений нет.

```bash
uv run --project tools python tools/validator/check18.py <вход> <выход>
scripts/check.sh organizers        # оба датасета: все точки подключены, check18 без нарушений
```

## 5. Алгоритм по глубине

Дополнительная задача (§5 приложения 18.09). Подробно, с доказательством и замерами, — [depth-optimization.md](depth-optimization.md); толкования — раздел 14 [CONSTRAINTS.md](architecture/CONSTRAINTS.md); числа — раздел `depth` в `rules/rules.json`.

**Что меняется.** Трасса в плане, Ду и камеры те же, что в 2D: §5 разрешает строить глубину поверх готовой трассы. Выбирается только профиль — глубина верха трубы вдоль трассы. Без флага `--depth` выход 2D побайтово прежний.

**Правила профиля.**
- верх трубы не мельче 0,7 м; под дорогой — не мельче 1,0 м, под трамваем — 1,2 м, на всём спецпереходе;
- уклон не круче 0,10; в узле у всех участков одна глубина;
- у газа, кабеля и существующей теплосети труба на 2 м по трассе в каждую сторону от пересечения лежит на постоянной глубине выше или ниже объекта с просветом из табл. 2; в `depth_crossings` — тип объекта, `over` / `under` и просвет;
- канализация — дополнительный тип, которого нет в табл. 2: глубина условная (верх 3,5 м, габарит 0,4 м), просвет 0,2 м по СП 124.13330 табл. А.1. Если на цепочке профиль с ней не помещается в уклон 0,10, на этой цепочке канализация не учитывается, а правила приложения соблюдаются;
- глубже 3,0 м стоимость участка умножается на Kгл = 1 + 0,1 · (h − 3);
- камеры — на 3,0 м ± 5 см (по ответу экспертов 16.10.2026: трубы входят в камеру на заданной глубине), внутри допуска — по стоимости. Если иначе профиль не помещается, камера сдвигается на самую дешёвую допустимую глубину и помечается `depth_shifted: true`;
- излом профиля и переход через 3,0 м делят участок техническим узлом.

**Как считается.** Стоимость зависит только от того, насколько профиль глубже 3,0 м. Глубины узлов подбираются покоординатным спуском, профиль цепочки между узлами — динамикой по зонам пересечений. Из профилей равной стоимости берётся тот, где меньше вертикальных изломов, затем ближе к 3,0 м.

**Почему оптимально.** Независимый скрипт `tools/validator/depth_bound.py` считает нижнюю границу стоимости любого допустимого профиля на той же трассе. На датасетах организаторов стоимость выхода равна этой границе с точностью до округления — значит, дешевле профиля нет. На 20 трудных случаях `data/samples/depth` разрыв с границей — 0–316 руб. (цена запаса уклона 0,998 против округления). Расчёт профиля на датасете — 3 мс.

```bash
java -jar target/heatnet.jar --cli --depth <вход> <выход>
uv run --project tools python tools/validator/check18.py --depth <вход> <выход>
uv run --project tools python tools/validator/depth_bound.py <вход> <выход>     # нижняя граница
```

## 7. Платформа инженера «Тепломаршрут»

Веб-интерфейс к сервису, офлайн: исходные данные и результат в 3D, трубы под землёй настоящего габарита, продольный профиль с пересечениями и зазорами, пролёт вдоль трассы, сравнение вариантов, отправка расчёта на сервер (в том числе с глубиной) и история расчётов. После `make up` — `http://localhost:8080/`, без сервиса — `make platform` и `http://localhost:8091/` с демо-наборами. Подробно — [platform/README.md](../platform/README.md). ТЗ интерфейс не требует, это дополнительная функция.

## 8. Границы применения

| Тема | Как есть |
|---|---|
| **Оптимальность в плане** | эвристика: дерево Такахаши–Мацуямы, точный скелет на сетке мест камер и локальный поиск находят допустимое решение, но минимум стоимости не доказывают. Точный скелет точен только для мест на сетке и деревьев до 16 точек |
| **Оптимальность по глубине** | профиль оптимален для заданной трассы; трасса под глубину не перестраивается |
| **Форма трасс** | ось ребра одна — преобладающее направление сторон зданий и ограничений длиннее 8 м в 30 м от ребра. Если таких сторон рядом нет, ребро по осям не перекладывается и может остаться диагональю |
| **Детерминированность** | вне городского режима выход один и тот же на любой машине. В городском режиме номера объектов зависят от расписания нитей; если задать срок `heatnet.city.deadline`, на медленной машине подключится меньше точек |
| **Масштаб** | граф строится за время, квадратичное по числу узлов, поэтому область расчёта ограничена рамкой вокруг группы. Вход до 3 ГБ читается потоком; для него нужна куча `-Xmx12g -XX:MaxNewSize=512m` и `JOB_WORKERS=1`. Синтетический город 3,2 ГБ (3,14 млн точек): подключено 12 681 за 335 с — замер v0.9.0, на v0.10.0+ не повторялся |
| **Время** | почти всё время уходит на точный скелет: динамика по подмножествам точек растёт экспоненциально, поэтому она ограничена деревьями до 16 точек, а сетки 21–30 м — входами до 40 точек |
| **Точка в зоне отступа** | маршрута к ней нет, ОКС уходит в неподключённые с причиной `inside_forbidden_zone` |
| **Известные случаи `no_route` и отказов** | по [depth-optimization.md](depth-optimization.md#найдено-попутно-2d-не-глубина-не-исправлялось): точка ровно на границе полигона ОКС при Ду ≥ 500; Ду ≥ 1200 через дорогу или трамвай; газопровод, заданный полигоном; суммарный расход больше пропускной способности Ду 1400 — расчёт падает |
| **Правила** | все числа — в `rules/rules.json`; есть пример правил водопровода `rules/examples/water-supply.json` с условными числами. `check18` всегда берёт `rules/rules.json` |
| **СП и нормы** | в документах организаторов ссылок на СП нет, пункты СП в расчёте не используются |
| **Развёртывание** | `docker-compose.yml` рассчитан на docker-compose 1.29.2; на Ubuntu Server 22 развёртывание не проверялось |
