# Алгоритмы на датасете организаторов

Исследование по `docs/agent.txt`, продолжено 16 сентября 2026 года в `LCT-real`.
Датасет: 17 ОКС, 488,7 т/ч, 29 участков сети Ду 300–500, 9 камер,
88 зданий, река и железная дорога. Всего 144 фичи.

**Лучшее полностью проверенное решение — S = 15,033.** Оно получено прежним
`ls` с бюджетом 30 000. Геометрическая нижняя граница для всех 17 ОКС —
**S ≥ 4,884**. Граница доказана ниже, но разрыв 67,5% относительно лучшего
найденного решения слишком велик для вывода о близости к оптимуму.
16,924 уже уступает найденному 15,033 на 12,6% по S.

Доработка готового решения Java достигает **17,379 за 24,6 с** при бюджете 400.
Эти 24,6 с включают импорт, построение графа и поиск, но получение исходного
решения Java ранее занимало 528 с. Это результат для повторного расчёта;
его нельзя выдавать за ускорение всего первого расчёта с нуля.

Пакет задачи: [real-routing-research](../specs/real-routing-research/index.md).
Проверки и дефекты: [протокол](../testing/real-routing-research-2026-09-16.md).
Рекомендация для переноса — в разделе «Что переносить в Java».

### Почему кластеры не дают нижнюю границу

Точная модель решала подсцены {1,2,3,4,6,8,11}, {5,9,10,12,13,14,15}
и {7,16,17}. Их объединённая оценка 17,565 не ограничивает оптимум полной
задачи снизу: разбиение запрещает слияния между кластерами. Кроме того,
в результате две камеры с 5 и 6 участками, пересечения деревьев и недобор
отступа на 9 см. Это недопустимое решение, полезное только для изучения структуры.
Врезки получались в камеры 107 и 108 и трубу 127; результат 30 000 выбрал ещё
одну врезку выше по сети и сократил реконструкцию с 229 до 104 м.

исходный `ls` — 18,195. Смена порядка стартов тоже оставила 18,195.
Ду 400 дал 17,790, но без ОКС 6; эту строку нельзя сравнивать с полным покрытием.
Результаты не дают основания заменить граф Ду 500 одним графом меньшего диаметра.

Начальное решение Java воспроизведено без перестройки трасс: 26,356406 S
и ноль нарушений. Runner импортирует врезки и вершины, добавляет их в граф,
сохраняет дерево и проверяет его общей моделью. Бюджет 400 дал 17,379,
бюджет 3000 — 17,179. Добавочные 111 с принесли только 0,200 S.
Для быстрого повторного расчёта разумный стартовый бюджет — 400.
Для холодного старта прежние 10 000 остаются подтверждённым ориентиром
16,924 за 223 с поиска; подтверждённого сокращения полного времени до такого
же качества в этой серии пока нет.

Первоначальный вывод «весь выигрыш дали только merge/fuse» был слишком сильным.
Новая инструментированная серия фиксирует также принятые `move`, `retie`,
`alone`, `split`, `path`, `eliminate`, `insert`. Например, у быстрого старта Java
приняты 8 merge, 7 move, 3 alone, 6 retie и 1 fuse. Это счётчики по всему поиску,
включая рестарты; они не измеряют отдельный вклад хода в итоговое S.

Два прогона (`service-forest-b400`, `dn250-b3000`) и `dn400-b5000`
попали на изменение файлов другой сессией: модель снова писала диаметр
реконструируемого объекта вместо диаметра новой сети от врезки. Их результаты
имеют ошибки `tie_in` и исключены из сравнения допустимых решений.
Исправлены четыре строки модели; повторный `service-forest-b400-fixed`
прошёл проверку. Новые записи содержат SHA-256 исходников и `source_unchanged`.

## Настоящая нижняя граница

### Что именно ограничено

`lower_bound.py` не использует граф видимости и не фиксирует врезки или
точки ветвления. Граница относится к связным геометрическим трассам по ТЗ
с ценами `rules/rules.json`, трактовками `docs/interpretation.md` и округлением
длин до 0,01 м. Она допускает любой набор неподключённых ОКС с положенным штрафом.
Реконструкция, камеры, препятствия и ограничения ветвления отброшены там,
где они могли бы только увеличить стоимость. Поэтому эта релаксация
не исключает более выгодные допустимые маршруты.

Датасет SHA-256:
`07921d7740c0297a63111846d4b77dfb6ccb33da65ffd7ccb14c5b2d786dd7d0`.
Правила SHA-256:
`e47d32b2bb4a5fb4a2ed526c44569ae6d944a77c94e6cce4e7961cf4e5369393`.
Числа относятся к принятому `existing_flow.share = 0`. При другом расходе
изменится стоимость допустимых решений; геометрическая граница, которая
отбрасывает реконструкцию, останется применимой при тех же ценах.

### Доказательство через непересекающиеся диски

Обозначим `a = w_cost / cost_base`, `b = w_length / length_base_m`.
Для терминала i с расходом gᵢ возьмём минимальную ставку трубы cᵢ,
способной пропустить этот расход. Все участки его пути имеют ставку не ниже cᵢ.

1. Вокруг каждого терминала строится диск радиуса rᵢ. Диски не пересекаются,
   не содержат существующую сеть/камеры и отстоят от любого специального
   объекта дальше `margin_m + 1,1 м` (в расчёте добавлен запас).
   LP максимизирует сумму оплачиваемых радиусов при этих линейных ограничениях.
2. Путь подключённого ОКС должен выйти из своего диска. Длина внутри —
   не меньше `max(0, rᵢ − 0,05)`. Отступ 0,05 м учитывает привязку конца трассы.
   Диски раздельны, поэтому эти части нельзя посчитать дважды даже при слиянии путей.
3. Участок короче 1 м допускается только у специального прохода. Он не может
   достичь защищённого диска: специальная часть находится в зоне `margin_m`,
   а смежный короткий участок проходит меньше ещё одного метра. Значит,
   каждый участок, из которого берётся эта длина, имеет длину хотя бы 0,999 м
   с запасом на координатную точность.
4. Округление его длины теряет не больше 0,005 м, стоимости — 0,005 руб.
   Поэтому консервативная ставка в единицах S равна
   `wᵢ = (1 − 0,005/0,999) × (a cᵢ + b) − a × 0,005/0,999`.
   Специальные коэффициенты не меньше единицы и оценку не уменьшают.
5. Для подключённого i учитывается кредит `wᵢ max(0,rᵢ−0,05)`.
   Для неподключённого вместо него уплачивается штраф. В сертификате
   кредит каждого i меньше его штрафа, поэтому сумма кредитов — граница
   для любого поднабора подключений. При хотя бы одном подключении добавляется
   минимум одна врезка: 0,14 S. Пустой вариант сравнивается отдельно с суммой штрафов.
6. После вычета 0,0005 на окончательное округление S получается
   **4,8841716296**, или **4,884 при округлении вниз до тысячных**.

Сертификат с радиусами, кредитами, запасами ограничений и хешами —
`data/research/real/out/lower-bound.json`. `check_research.py` пересчитывает
расстояния и ограничения независимо от решателя; оптимальность LP для
достоверности нижней границы не требуется, достаточно допустимости сертификата.
Допуски проверки не используются как возможность строить разорванные трассы
или произвольно занижать цены.

### Дополнительные релаксации и предел вывода

Без поучасткового округления получена граница **5,1746655638**.
Она использует неотрицательные yᵢ и z с ограничениями
`sum(yᵢ, i∈A) + z ≤ a c(sum(gᵢ, i∈A)) + b`
для всех **131 071** непустых подмножеств A. Часть y оплачивает длины путей
до всей существующей сети, z — выход из непересекающихся дисков.
Подсчёт по каждому ребру доказывает, что общая оценка не превосходит его цены.
Все ограничения повторно проверяются по сохранённому вектору.
Эту более сильную цифру нельзя без поправки подставлять вместо границы
для сериализованного S.

Проверено усиление дисков одним общим кольцом вокруг группы терминалов:
146 групп-кандидатов, 62 допустимых LP; улучшения границы не получено
(`annulus_bound.py`, `annulus-bound.json`).

Итоговый доказанный интервал по сохранённым допустимым решениям:
**4,884 ≤ S* ≤ 15,033**. Доказательства близости к оптимуму нет.
Чтобы сузить интервал, потребуется более сильная модель совместной прокладки
и реконструкции. Разбиение на независимые кластеры с последующим сложением
такую модель не заменяет.

## Граф и более крупный набор

`graph_bench.py` сравнивает один и тот же граф реальной сцены с отсечением
некасательных рёбер и без него, затем строит граф синтетики seed 19:
20 ОКС, 200 ограничений и 300 участков сети до добавочных объектов генератора.

| Набор | Фич | Узлов | Рёбер | Построение + списки смежности, с |
|---|---|---|---|---|
| Реальный, касательные рёбра | 144 | 959 | 14 754 | 0,90 |
| Реальный, полный граф допустимой видимости | 144 | 959 | 32 293 | 2,74 |
| Более крупный синтетический, касательные рёбра | 684 | 4 090 | 346 857 | 37,61 |

Это замеры Python на macOS arm64; большой набор проверяет построение графа,
а не качество или время полного поиска. `maxrss` процесса вырос примерно
до 506 МБ; это накопленный пик родителя, без полного учёта дочерних процессов.
Он не доказывает соблюдение 16 ГБ при 50 пользователях.

Касательный фильтр уменьшил число рёбер реальной сцены в 2,19 раза и время
построения примерно в 3 раза. Сам `connect` всё ещё перечисляет O(V²) пар,
а кэш таблиц Дейкстры растёт с числом источников и диаметров. Нельзя переносить
его глобально на вход до 3 ГБ или обещать фиксированное время только по числу ОКС.

## Что переносить в Java

### Поиск и оценка

- Сохранить лес ориентированных деревьев с явной врезкой, терминалами,
  расходами и допустимой степенью камер. Для повторного расчёта использовать
  уже проверенный вариант Java как один из стартов. Для холодного — несколько
  автоматически полученных разбиений; координаты и номера ОКС не фиксировать.
- Первый уровень: `connect`, `merge`, `fuse`, `move`, `alone`, `retie`, `split`.
  Это присоединение, слияние деревьев, перенос ОКС, перенос врезки и разделение.
  После улучшения снова начинать с первого уровня.
  Для длинного расчёта оставить перекладку пути и удаление узла (`path`, `eliminate`),
  затем вставку точки ветвления (`insert`). Удаление этих уровней ухудшило результат.
- Предварительно оценивать изменение новой трубы, камер, врезок, специальной
  прокладки и **совместной** реконструкции цепочки к источнику. Реконструкция
  нелинейна: цены разных деревьев нельзя независимо сложить. Быстрая оценка
  служит фильтром; принятие — только после полного пересчёта S и ограничений.
- Не ухудшать число подключённых ОКС при сравнении стартов и ходов.
  Проверять конечный вариант независимо от внутреннего счётчика нарушений.
  Собирать 2–3 отличающихся варианта с корректными рангами и ID.
- Не копировать без исправления `Search.failed`: часть ключей содержит только
  изменяемое дерево или пару деревьев, хотя допустимость пересечений и цена
  реконструкции зависят от остальных деревьев. Для Java включать версию
  контекста леса либо сбрасывать такие отказы при его изменении.

### Бюджет

Для улучшения готового плана начать с 400 единиц бюджета и мягкого лимита
30 с поиска. Это соответствует проверенному результату 17,379; граф и поиск
на другой машине требуют повторной калибровки. Дорогой ход может выйти за
мягкий лимит, поэтому проверять срок также внутри построения путей и перебора врезок.

Для первого расчёта использовать конфигурируемый бюджет; 10 000 — измеренный
ориентир, 30 000 — режим улучшенного качества. В текущем Python единица хода —
`max((E/100000)^1.5, 0.5)`, `insert` и рестарт тоже расходуют бюджет.
Это не число итераций и не переносимая единица времени. Нужны общий срок,
лимит оценок и лучший уже проверенный результат на случай исчерпания бюджета.
Параметры 30 с / 10 000 — предложение для настройки, а не подтверждённая
производительность Java на Ubuntu.

### Геометрия и память

1. Построить пространственный индекс геометрий в метрических координатах.
   Запрашивать препятствия по envelope проверяемого отрезка, затем делать
   точную проверку только кандидатов. Для JTS подходит
   [STRtree](https://locationtech.github.io/jts/javadoc-1.18.0/org/locationtech/jts/index/strtree/STRtree.html):
   документация описывает запросы по envelope и поиск ближайших соседей.
2. Граф строить на группу ОКС и кандидатов врезки с ограниченной областью;
   расширять её при отсутствии пути. Кэшировать по области и классу отступа
   диаметра. После локального поиска проверять возможные слияния соседних групп,
   чтобы разбиение не стало жёстким запретом общих стволов.
3. Брать выпуклые наружу вершины буферов, касательные связи, точки врезок
   и подключения. Для дорог и железной дороги сохранять точки допустимых
   пересечений; нужны и связи между ними. Упрощение контуров должно оставлять
   консервативный запас относительно исходной геометрии.
4. Начальные и конечные точки запроса подключать один раз и кэшировать.
   Переиспользовать таблицы кратчайших путей по источнику/диаметру/версии препятствий.
   Для повторяющихся проверок геометрии использовать подготовленные геометрии
   и ограниченный кэш. Для таблиц — предел памяти и вытеснение.
5. Касательный граф не считать доказательством оптимума при разных диаметрах,
   специальных коэффициентах и свободных точках Штейнера. На финальной трассе
   проверять исходные полигоны при фактическом диаметре; при нарушениях перестраивать
   путь в соответствующем классе отступа. Один малый диаметр на всю сцену
   не подтвердил работоспособную замену.
6. Ограничить одновременно активные расчёты доступной памятью и CPU, а остальные
   держать в очереди. Потоковый вход не решает проблему O(V²) внутри графа.
