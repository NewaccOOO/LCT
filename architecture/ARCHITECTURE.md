## Общая схема

Сервис — одно приложение на Spring Boot. Расчёт не зависит от веба и базы: одно и то же ядро `Pipeline` вызывают и REST-воркер, и CLI.

```mermaid
flowchart LR
    client[Клиент] -->|POST GeoJSON| api[JobController]
    api -->|input.geojson| disk[(DATA_DIR/jobs/id)]
    api -->|запись QUEUED| db[(PostgreSQL: jobs)]
    api -->|submit id| worker[JobWorker<br/>пул JOB_WORKERS]
    worker --> reader[GeoJsonStreamReader]
    reader --> pipeline[Pipeline<br/>VariantEnumerator]
    pipeline --> writer[GeoJsonStreamWriter]
    writer -->|result.geojson| disk
    worker -->|статус, сводки, ошибки| db
    cli[CliRunner<br/>профиль cli] --> reader
    rules[rules/rules.json] --> pipeline
```

| Пакет | Роль |
|---|---|
| `api` | REST, сущность задачи, воркер и обработчик ошибок |
| `cli` | запуск расчёта из командной строки, профиль `cli` без веба и базы |
| `core` | интерфейс `Pipeline` и его реализация, которая создаёт `VariantEnumerator` на каждый запуск |
| `io` | потоковое чтение и запись GeoJSON, перевод EPSG:4326 ↔ EPSG:32637 |
| `model` | входные объекты и объекты результата |
| `rules` | загрузка `rules/rules.json`: диаметры, стоимости, отступы, коэффициенты |
| `graph` | зоны препятствий, граф видимости между вершинами зон, кратчайший путь |
| `plan` | кандидаты врезки, деревья, варианты, сборка сети |
| `calc` | расходы, диаметры, стоимость, ранжирование, критерии |

## Жизненный цикл задачи

```mermaid
sequenceDiagram
    participant C as Клиент
    participant A as JobController
    participant D as Диск
    participant P as PostgreSQL
    participant W as JobWorker
    C->>A: POST /api/v1/jobs (сырое тело)
    A->>D: потоком пишет input.geojson
    A->>A: первый значимый байт должен быть «{»
    A->>P: INSERT jobs, status=QUEUED
    A->>W: submit(id)
    A-->>C: 202 {id, status: QUEUED}
    W->>P: status=RUNNING, started_at
    W->>D: читает input.geojson
    alt во входе есть ошибки данных
        W->>P: status=FAILED, error = до 1000 диагностик
    else вход корректен
        W->>W: pipeline.run(data)
        W->>D: пишет result.geojson
        W->>W: вынимает variant_summary из готового файла
        W->>P: status=DONE, summary, output_path
    end
    C->>A: GET /api/v1/jobs/{id}
    A-->>C: статус и сводки
    C->>A: GET /api/v1/jobs/{id}/result
    A-->>C: result.geojson или 409, пока не DONE
```

```mermaid
stateDiagram-v2
    [*] --> QUEUED: POST принят
    QUEUED --> RUNNING: воркер взял задачу
    RUNNING --> DONE: результат записан
    RUNNING --> FAILED: ошибки входа или исключение
    QUEUED --> FAILED: перезапуск сервиса
    RUNNING --> FAILED: перезапуск сервиса
```

Детали, которые влияют на поведение:

| Решение | Зачем |
|---|---|
| Тело запроса пишется на диск как есть, без multipart | файл до 3 ГБ не держится в памяти и не упирается в лимиты Tomcat; пустое тело или не JSON-объект удаляют каталог задачи и дают `400` |
| Запись задачи коммитится до `submit` | воркер всегда видит задачу в базе |
| Каждая смена статуса — отдельная короткая транзакция | расчёт идёт вне транзакции |
| Воркер ловит `OutOfMemoryError` и `StackOverflowError` | иначе задача навсегда осталась бы в `RUNNING` |
| Сводки для API берутся из записанного `result.geojson` | числа в API и в файле совпадают до знака, `12.30` не превращается в `12.3` |
| При старте все `QUEUED` и `RUNNING` становятся `FAILED` с сообщением «Задача прервана перезапуском сервиса» | очередь в памяти после рестарта не восстанавливается |

## Расчёт по шагам

`PipelineImpl` загружает `rules.json` один раз на процесс и на каждый вызов создаёт новый `VariantEnumerator`. Всё состояние расчёта живёт в этом объекте, поэтому параллельные задачи друг другу не мешают.

```mermaid
flowchart TD
    read[1. Чтение входа<br/>GeoJsonStreamReader] --> big{больше 500 ОКС?}
    big -->|да| city[Прямые подключения к сети рядом<br/>DirectTies, остальное районами до 16 ОКС<br/>параллельно: шаги 2–6 в каждом районе]
    city --> assemble
    big -->|нет| groups[2. Группы близких ОКС<br/>до 300 м по цепочке]
    groups --> region[Region на группу:<br/>диаметр ствола, область графа]
    region --> ties[3. Кандидаты врезки]
    ties --> tree[4–5. Маршруты и деревья врезок]
    tree --> partitions[6. Разбиения ОКС и черновики]
    partitions --> search[Локальный поиск<br/>до 1000 сборок]
    search --> pick[Отбор до 3 различающихся вариантов]
    pick --> relay[Перенос камер ветвления<br/>JunctionMover]
    relay --> slide[Сдвиг камер вдоль рёбер<br/>TreeBuilder.slides]
    slide --> assemble[7. Сборка сети с рангами<br/>NetworkAssembler]
    assemble --> write[8. Запись результата<br/>GeoJsonStreamWriter]
```

### 1. Чтение входа

`GeoJsonStreamReader` идёт по файлу потоком и не держит его целиком в памяти. Файл читается блоками по 1 МБ, фичи разбирает пул потоков по числу ядер, а главный поток сливает готовые части по порядку файла, поэтому диагностики и порядок объектов те же, что при чтении в один поток. Разбор фичи идёт своим байтовым разборщиком без дерева Jackson: координаты сразу ложатся в упакованные последовательности, числа читаются тем же путём, что `Double.parseDouble`. Всё, что он не узнаёт (экранирование, не-ASCII, необычный порядок ключей), разбирает Jackson. Дальше строится геометрия: проверка валидности и перевод в EPSG:32637 (UTM 37N), где все длины и отступы считаются в метрах.

Границы фич ищутся тремя способами, от быстрого к надёжному:

1. **Строками.** Если фичи лежат по одной на строку, как в файле «город», блок режется по переводу строки и границы внутри куска находит сама нить пула. Кусок за концом массива `features` не разбирается, а если успел начать до того, как главный поток нашёл конец массива, файл перечитывается срезами: иначе объекты чужого массива попали бы в таблицу `id`. Если фича переходит через перевод строки, строка длиннее 16 МБ или диагностике нужен номер фичи, файл читается вторым способом.
2. **Срезами.** Главный поток находит байтовые границы фич подсчётом скобок с учётом строк и экранирования, фичи разбирает пул.
3. **Деревьями.** Если смещения разошлись с фичей (другая кодировка), файл читается Jackson на главном потоке.

Чтение идёт в два прохода. Первый берёт всё, кроме зданий и ограничений, а у них только проверяет синтаксис без разбора координат. По его итогу считается рамка, вне которой препятствия на расчёт не влияют. Второй проход читает только препятствия: каждое проверяется как обычно, в память ложатся те, что пересекают рамку. Если первый проход нашёл ошибки, второй читает весь файл, как раньше. Файл «город» на 3,2 ГБ читается так за 16–21 с (было 48–59 с). Ошибки данных копятся как `Diagnostic`: нет обязательного поля, не тот тип, повтор `id`, ссылка в пустоту, невалидная геометрия. Если хоть одна есть, расчёт не запускается.

Читатель принимает и формат раздела 12 CONSTRAINTS.md, и формат датасета организаторов. В датасете нет `upstream_object_id`, текущего расхода сети, диаметра камер и `oks_future`, а здания заданы ограничениями `oks`. Недостающее читатель выводит после прохода по файлу:

| Чего нет во входе | Как выводится |
|---|---|
| направление сети | обходом от источника по стыкам концов участков |
| диаметр камеры | наибольший диаметр примыкающих участков |
| текущий расход участка | по его диаметру |
| перспективный ОКС | по точке подключения внутри здания |

Правила вывода записаны в [interpretation.md](../docs/interpretation.md), валидатор выводит то же самое независимо.

### 2. Группы и области

ОКС, чьи точки подключения ближе 300 м друг к другу по цепочке, объединяются в группу. На каждую группу создаётся `Region`:

- **диаметр ствола** — по суммарному расходу группы плюс одна ступень запаса, чтобы отступы были верны и для участков, которые позже поднимут по предельной длине. Дерево подмножества строится по графу диаметра своего расхода с той же ступенью запаса, но не больше диаметра группы;
- **область графа** — прямоугольник вокруг точек подключения и кандидатов врезки с запасом 150 м и широкая область с запасом 600 м для повторной попытки;
- **кэши** — построенные деревья по подмножествам ОКС и `Router` по паре «диаметр, область».

Граф строится за время, квадратичное по числу узлов, поэтому он строится на область группы, а не на весь город; рёбра и зоны узлов считаются параллельно в своём пуле `ObstacleSet.PARTS`. Общий пул для этого не годится: граф строится под замком кэша области, этот замок ждут нити общего пула, и собирать части было бы некому. Здания и ограничения читаются только в рамке перспективных ОКС с запасом 2,5 км, а точки дальше предельной длины наибольшего Ду (11 276 м) от сети в рамку не входят: их здания на расчёт не влияют (на городе это 82 432 зданий-препятствий вместо 3,14 млн).

### 3. Кандидаты врезки

`TieInFinder` для каждой точки подключения берёт три ближайшие камеры и перпендикулярные проекции на три ближайших участка сети. Проекция становится врезкой в камеру, если камера не дальше `max_dist_m` (10 м) и после подключения у неё будет не больше `max_segments` участков. Из нескольких таких камер берётся ближняя. Иначе врезка идёт в трубу, и в точке врезки ставится новая камера; её Ду не меньше Ду трубы, ведь обе части разрезанной трубы к ней примыкают.

Если точка подключения ближе 1,2 м к оси трубы, врезка по перпендикуляру дала бы отрезок короче метра: правило длины подотрезка его не пропускает, и трасса уходила петлёй по зоне трубы. Поэтому врезка сдвигается вдоль оси к середине участка так, чтобы до точки было 1,2 м. На датасете организаторов точки не ближе 23 м к сети, сдвиг срабатывает только на сценах, где здания стоят вплотную к трубам.

Врезка в трубу не ставится в полигон дороги или трамвайных путей и в его полосу `margin_m`, если на трубе есть место вне полосы. Иначе спецпроход начинался бы в камере посреди полосы, а по разъяснению 6 он один прямой участок и угол проверяется в точке входа. `TieInFinder` один раз на трубу находит её части в буферах полигонов спецпрохода и переносит врезку вдоль трубы за ближайшую границу полосы, на 5 см дальше неё; спецучасток через дорогу тогда начинается в самой камере. Место любой врезки в трубу, в том числе при переносе к стволу и сдвигах у готовых деревьев, выбирает `pipeCandidate`, поэтому правило действует везде. На dense-50 так ушли из дорог камеры v1_ch_4 и v1_ch_32 (S варианта 1 — 52,742 вместо 52,728), на dense-200 — v1_ch_25 (220,860 вместо 220,873). На dense-100 камер в дорогах не было, но из-за других кандидатов поиск пришёл к другой врезке одной точки: 102,849 вместо 102,839.

Если все ближайшие кандидаты дают одну и ту же врезку, а вариантов нужно минимум два, `TieInFinder.along` ищет врезку в той же сети дальше 20 м от лучшей.

### 4. Маршрут: граф видимости

<img src="../docs/assets/graph-steps.svg" alt="Четыре шага построения маршрута: препятствия, зоны отступа с выпуклыми вершинами, касательные рёбра, кратчайший путь" width="100%">

Все полигоны ОКС — препятствия, и здание с подключаемой точкой тоже (приложение 18.09, п. 2.2). Зоны запрета хранятся по одной на объект со своим id: финальный прямой участок к точке подключения проверяется без зоны своего здания. Освобождение касается только части участка в зоне перед границей, поэтому участок выходит из зоны своего здания один раз и к другой его стене ближе отступа не подходит (`TreeBuilder.leavesZoneOnce`). `TreeBuilder.portal` ставит точку выхода на луче от точки через ближайшую точку внешнего контура здания сразу за зоной отступа и дальше, пока выход в чужой зоне; если участок до выхода недопустим или луч снова входит в своё здание или в его зону отступа, пробуются ближайшие точки других сторон, до восьми. Если закрыты и они, берётся ближайшая допустимая точка среди всех точек внешнего контура через 5 см (`TreeBuilder.entries`, `TreeBuilder.window`): у таких лучей проверяется ещё, что в зоне отступа они не подходят к другой стене здания (`TreeBuilder.recedes`). Выход ставится по зоне графа, а у фактического Ду участка зона другая, поэтому собранное дерево проверяется ещё раз по Ду участка (`VariantEnumerator.raysClear`). Зона для точки выхода берётся с углами `JOIN_MITRE`: по точной зоне выход между частями здания попадал в тупик. Отступ берётся по Ду графа дерева, а он бывает на ступени выше Ду ветки: граф строится для всего блока с запасом. Если по Ду графа ближняя сторона закрыта, а по Ду участка точки (по её расходу) открыта, выход ставится по Ду участка, ветка от него идёт по графу этого Ду, а отступы такого дерева при проверке считаются по Ду каждого участка (`Tree.narrow`). Если от этого выхода ветки к дереву нет, точка не переходит на выход по Ду графа через дальнюю сторону: п. 2.2 разрешает другую сторону, только когда ближняя закрыта. Такая точка уходит из дерева в `tree.unconnected` и подключается отдельно, попытками из пункта «Без маршрута». По той же причине дерево, которое сборка отвергла, заново по графу блока не строится. Маршрут ищется от точки выхода, ветка начинается прямым участком точка–выход.

Дейкстра не релаксирует ребро, которое ломает путь в узле круче 90°: поворот считается по предшественнику узла, поэтому путь может быть не кратчайшим среди путей с поворотами до 90°, зато таблица остаётся линейной по узлам. Узлы графа не ставятся в полосе `margin_m` вокруг дорог и путей, а узлы для их пересечения стоят у внешней границы полосы: так спецпроход — один прямой участок от узла до узла.

#### Зоны и узлы

Зона запрета — точки ближе минимального отступа плюс половины ширины пары труб к существующему зданию, парку, социальному объекту, запретной территории, воде. `ObstacleSet` проверяет её точным расстоянием до сторон объекта с запасом 0,05 м, как правило и check18, а не по буферу. Буфер с углами `JOIN_MITRE` торчит у угла здания на d·√2: он закрывал проходы между углами соседних зданий и уводил трассу от угла. Стороны объекта лежат в массиве кусками по 8 с общей рамкой; отрезок дальше круга вокруг объекта с отступом отсеивается без перебора сторон.

Узлы графа — выпуклые вершины буферов `JOIN_MITRE` на 0,15 м шире отступа и точки вдоль сторон дорог, не лежащие ни в одной зоне. Если вершина угла попала в зону соседа, вместо неё ставятся две вершины описанного многоугольника. Узлы берутся только внутри области графа: зона дороги или магистрали длиной в километры иначе приносит узлы далеко за областью, а граф строится за время, квадратичное по числу узлов.

Зоны запрета лежат в равномерной сетке `ZoneGrid`. Отрезок проверяется обходом клеток вдоль него с выходом на первой задетой зоне: у длинного ребра рамка накрывает тысячи зон, и прежний запрос к `STRtree` собирал их все, прежде чем проверить первую. На дальних районах города построение графа от этого стало в 5–7 раз быстрее.

Рёбра из одного узла проверяются подряд, и зона или спецобъект, запретившие прошлое ребро, проверяются первыми (`ObstacleSet.Hint`): соседние по номеру узлы стоят на кольце одной зоны, и ребро к ним обычно запрещает тот же объект. Ребро запрещено, если его запрещает хоть один объект, поэтому граф от порядка проверок не зависит.

#### Рёбра

У выпуклой вершины запоминаются соседи по кольцу зоны. Ребро проверяется, только если касается зоны в обоих концах, то есть не уходит внутрь угла. В кратчайшем пути других рёбер не бывает, а геометрических проверок становится в несколько раз меньше. Ребро допустимо, если:

- не заходит в запрещённую зону;
- дорогу и трамвайные пути пересекает под углом не меньше 45°;
- газопровод, кабель и существующую теплосеть либо пересекает, либо проходит от них не ближе отступа.

Вес ребра — длина плюс надбавка `(Kспец − 1) × длина специального прохода`. У линии это `margin_m` в обе стороны от пересечения. У дороги и путей в вес идёт часть ребра в полосе `margin_m` поперёк границы: эта оценка не короче спецучастка вдоль трассы и держит переходы ближе к прямому углу. С весом по спецучастку вдоль трассы S на «густо-100» выходил хуже на 0,1. Спецчасти готовой трассы `ObstacleSet.spans` и сборка считают вдоль трассы.

#### Спрямление

Если на пути остаётся излом меньше 3°, а убрать вершину нельзя, вершина сдвигается от хорды шагами 0,5–8 м. Сетки 45° и надбавки за угол в редакции правил от 18.09 нет: угол поворота в пределах 90° любой.

Затем `Router.cutPass` срезает вершины пути хордами в два прохода. Хорда держит отступ с запасом 0,2 м, как буфер узлов графа до упрощения, не пересекает спецобъектов и не оставляет подотрезков короче 1,05 м; срезы кэшируются по тройке вершин. Узлы графа стоят на вершинах буферов, и путь по ним обходит угол здания шире нужного. Хорда короче 10 м даёт два поворота подряд, и следующий шаг возвращает на её место прежний угол, если он проходит проверку; срезка остаётся там, где хорда длиннее или угол не вернуть, а её вершины часто убираются совсем.

После срезки `Router.sharpen` доводит форму по разделу 5 правил: участки прямые с поворотами, без необоснованных изломов, зигзагов и ступенек. Поворот — вершина с отклонением от 3°. Шаги повторяются, пока форма меняется:

1. Вершина убирается, если её соседей по обычному участку можно соединить прямой. Сосед — соседняя вершина или граница специальной части на соседнем отрезке: там сборка ставит технический узел, граница становится вершиной, а спецпроход остаётся прежним прямым участком. Так уходят и вершины рядом с техническим узлом: узел графа для пересечения дороги стоит в `margin_m` от полигона поперёк границы, а спецучасток кончается в `margin_m` вдоль трассы, ближе к дороге. Сосед, у которого после этого излом меньше 3°, убирается вместе с вершиной. Первой убирается вершина, которая сильнее укорачивает трассу.
2. Так же одной прямой убираются две вершины со звеном короче 10 м между ними: это спрямляет зигзаг.
3. Повороты подряд в одну сторону со звеньями короче 10 м заменяются наименьшим числом поворотов. Прямые входа, выхода и части средних звеньев продолжаются до пересечения, поворот в пересечении равен сумме поворотов между ними. Варианты идут по числу поворотов, при равном числе — по длине. Два поворота подряд остаются, только если их сумма больше 89,9° или вершина пересечения не проходит проверку.
4. У готовых вариантов (`VariantEnumerator.bent`) два соседних поворота в одну сторону при звене любой длины заменяет одна вершина, если путь с ней не длиннее прежнего. Вершина стоит на пересечении лучей из соседей пары. Лучи по очереди поворачиваются от прежних отрезков к хорде между соседями, пока звенья проходят те же проверки, поэтому путь только укорачивается. Соседи внутри участка остаются поворотами от 3°. В поиске этого шага нет: на каждом маршруте и дереве он стоил бы времени, а трассу только укорачивает.

Вершины убираются раньше, чем заменяются повороты: удаление укорачивает трассу, замена удлиняет. Порога по величине отдельного поворота нет. Каждая замена проверяется как хорда срезки, но с меньшим запасом отступа: 0,15 м сверх нормы, без спецпрохода, не ближе 0,5 м к другим рёбрам дерева и к своей ломаной, в пределах области графа; поворот не круче 89,9°, звено не короче 1,05 м. Так толкуется п. 5: поворот обоснован, если без него трасса подошла бы к зоне ближе нормы плюс 0,15 м. `ObstacleSet.plain` отсчитывает запас от нормы: зона и так шире нормы на 0,05 м, и прежде форма держала 0,2 м, оставляя вершины с запасом прямой 0,15–0,2 м. Точка выхода из здания остаётся на месте. Прямая от врезки не должна идти вдоль трубы врезки. Если одна прямая заменяет всё ребро, она касается трубы врезки своим концом, и проверка от другого конца находит это касание всегда. Поэтому такая прямая считается идущей вдоль трубы, только если это видно от обоих концов: иначе ребро от врезки не спрямлялось в один отрезок и в нём оставалась лишняя вершина. Маршрут с доведённой формой кэшируется по пути графа: маршрут между теми же точками строится за расчёт десятки раз.

### 5. Дерево одной врезки

<img src="../docs/assets/tree-growth.svg" alt="Рост дерева: ветка к первому ОКС, камера ветвления для второго, диаметры по расходу" width="100%">

`TreeBuilder` растит дерево от врезки эвристикой Такахаши–Мацуямы: на каждом шаге присоединяется ОКС с самым лёгким маршрутом до уже построенного дерева. Маршрут обрезается в первой точке касания дерева, там ставится камера ветвления.

- **Только новые цели.** Дерево на шаге только растёт, и цели, оставшиеся с той же надбавкой, дают прежние веса. Если прежняя лучшая цель ОКС на месте, `Router.choose` сравнивает её с лучшей из новых целей шага и не перебирает остальные; при равных весах выбор зависит от порядка целей, и тогда цели перебираются все. Датасет организаторов с этим считается 3,7 с вместо 4,4.
- **Место в камере.** Если у камеры нет свободного места — больше трёх ответвлений нельзя, — ответвление переносится на соседнюю точку ствола.
- **Надбавки.** Точка посреди ребра платит стоимость новой камеры, второй и следующий луч из существующей камеры врезки — стоимость врезки. Рубли переводятся в метры по весам формулы S, поэтому ветка предпочитает свободный луч, пока крюк до него короче цены камеры.
- **Повороты.** Ветка с поворотом круче 90° отбрасывается, и пробуется следующее место присоединения; сборка проверяет повороты ещё раз, включая технические узлы.
- **Звено после выхода.** Маршрут ищется от точки выхода без учёта направления финального участка и часто уходит вдоль своей стены назад, круче 90° к финальному участку: на датасете организаторов так отбраковывалось около 40 % попыток присоединения. Тогда после выхода вставляется звено 1,5 м (если не проходит — 3 и 6 м): поворот в выходе 80°, затем второй поворот к следующей вершине маршрута. Финальный участок от ближайшей границы остаётся прежним (п. 2.1, 2.2), звено проверяется вместе с веткой. Форму дерева со звеном, как и любого другого, доводит `TreeBuilder.cut` с теми же запасами: точка выхода остаётся на месте, повороты не круче 89,9°. Одиночный ОКС присоединяется со звеном сразу. В дереве нескольких ОКС звено сразу не пробуется: иначе в общее дерево попадали точки, которые дешевле подключить отдельно, и на «густо-200» поиск находил черновики хуже на 1,2. Такая точка, как раньше, уходит в `tree.unconnected`, а дерево помечается `turnStuck`.
- **Без маршрута.** ОКС, до которых маршрута нет, остаются в `tree.unconnected`. Для одиночного ОКС есть три повторные попытки: с диаметром по расходу самого ОКС вместо диаметра ствола, затем на широкой области, затем точным поиском `Router.routeExact` на широкой области. Точный поиск ведёт состояние «узел и откуда в него пришли», поэтому находит путь, в который нужно войти с другой стороны, и держит поворот не круче 90° уже в точке выхода из здания. Он дороже обычного, поэтому включается только там, где точка иначе остаётся без сети: штраф за неподключение от 100 млн (п. 2.1, 2.5). Нужны ли повторные попытки и поиск врезки дальше по той же сети, решается по деревьям без звена после выхода: дальнее дерево со звеном иначе отменяло попытку, которая дала бы дерево лучше.

### 6. Варианты и локальный поиск

`VariantEnumerator.run` собирает черновики (`Draft`) по разбиениям ОКС:

| Разбиение | С лучшей врезкой | С другой врезкой |
|---|---|---|
| каждый ОКС отдельно | да | да |
| группы близких ОКС | да, если есть группа больше одного ОКС | да |
| группы от трёх ОКС, разбитые k-means на две | да, если такие группы есть | нет |

Внутри черновика подмножества идут по убыванию размера. Каждое берёт лучшее дерево, которое не пересекается с уже принятыми. Если в этом дереве точки остались без сети из-за поворота у выхода (`turnStuck`), для той же врезки строится дерево со звеном после выхода, и черновик берёт его, когда его S меньше, чем у прежнего дерева вместе с лучшими одиночными деревьями оставшихся точек. Деревья строятся не на всех кандидатах врезки, а на шести лучших по грубой оценке: прямые от точек подключения по цене трубы плюс новая камера, если врезка в трубу. Деревья кандидатов и сторон выхода одного подмножества считаются параллельно (`heatnet.search.parallel`): граф и кэш маршрутов общие и потокобезопасны, результаты складываются в порядке кандидатов, поэтому выход не зависит от расписания нитей. Проверка отступов дерева берёт зоны из кэша области, а не строит их на каждое дерево. Вне районов города деревья всех ещё не посчитанных подмножеств разбиения строятся заранее и параллельно в своём пуле: черновик берёт подмножества по одному, а ядер больше.

Из каждого дерева собираются формы, и в черновик идёт лучшая по S из тех, что собрались:

- дерево как построено; вне районов города — только если перенос врезки к вершине ствола его не изменил или ни одна форма с перенесённой врезкой не собралась;
- срезанное: вершины рёбер срезаются хордой не ближе 0,5 м к другим рёбрам, форма доводится `Router.sharpen`, точка выхода из здания остаётся на месте (`TreeBuilder.cut`). Ребро проверяется по зонам Ду расхода точек ниже него, если этот Ду меньше Ду графа: проверка сдаваемых участков меряет отступы по Ду участка, и вершина не должна остаться лишней из-за зон ствола. Такое дерево сборка проверяет по Ду участков. Если срезанное не собралось, пробуется несрезанное с доведённой формой и только потом дерево как построено. Если срезка не изменила ни одного ребра, доводка отдельно не пробуется: она уже прошла с теми же рёбрами;
- с врезкой, перенесённой к вершине ствола (`slid`): у каждой вершины ствола пробуется проекция на трубу врезки и кандидаты врезки самой вершины — три ближайшие камеры и проекции на три ближайших участка; перенос берётся, если ствол с ценой узла врезки короче хотя бы на 1 м;
- со стволом, проложенным заново от первой камеры ветвления к ближайшим к ней кандидатам врезки (`rerooted`), затем тот же перенос вдоль новой трубы.

Лучшая из собранных форм пробуется ещё и без первой камеры ветвления (`absorbed`). К новой камере на трубе примыкают две части разрезанной трубы, и места в ней хватает ещё на два новых участка. Поэтому, если от врезки идёт один участок к камере ветвления с двумя ветками, обе ветки можно провести прямо из врезки, а камеру ветвления не строить. Врезка ставится на той же трубе у проекции камеры ветвления или со сдвигом вдоль оси на 2, 4, 8 и 16 м в обе стороны; врезку в существующую камеру заменяет новая камера на ближайших к камере ветвления трубах. Ветка идёт прямой от врезки к одной из своих вершин и дальше прежним путём, финальный участок к точке подключения не меняется. Прямая проверяется так же, как у `slid`. Прямые из врезки — новая геометрия, поэтому форму такого дерева доводит `TreeBuilder.cut` с теми же запасами, что и у остальных форм: сначала срезанное, затем несрезанное с доведённой формой. Без доводки дерево берётся, только если `Router.sharpen` в нём нечего менять. Такая форма собирается, если по цене метра Ду расхода, камер и врезки она дешевле лучшей, и заменяет лучшую, если её S меньше. На датасете организаторов так точка 7 получила свой участок из камеры врезки, а камера ветвления в 23 м от врезки ушла: S 13,020 вместо 13,057. Поверх прокладки рёбер по графу своего Ду, переноса и сдвига камер вариант 1 датасета — 12,747 вместо 12,785.

В районах города перенос идёт только вдоль своей трубы, а новый ствол не строится и камера ветвления не снимается: поиск кандидатов у каждой вершины перебирает все камеры. Если все деревья пересекаются, `merged` пробует снять мешающее дерево той же группы и построить одно общее. Черновик, который не собирается `NetworkAssembler`, отбрасывается.

От лучшего черновика идёт локальный поиск по разбиениям ОКС (`search`). Каждый ход на схеме выше — новый черновик той же процедурой.

1. Спуск принимает первое улучшение.
2. Из локального оптимума он шагает на наименее плохого ещё не посещённого соседа, если тот хуже текущего не больше чем на 0,5 S, и спускается снова.
3. Когда и такого соседа нет, спуск перезапускается от лучшего найденного черновика по его наименее плохому непосещённому соседу уже без порога.
4. Возвращается лучший найденный черновик.

> [!TIP]
> Поиск ограничен только числом сборок (`heatnet.search.budget`, 1000) и остановкой после 100 сборок без улучшения (`heatnet.search.stall`), предела по стенным часам нет. Результат на любой машине один и тот же. Остановка по застою действует только после того, как перебраны все соседи начального черновика: с переносом врезки к стволу поиск иначе останавливался на первых соседях. Датасет организаторов останавливается на 100 сборках, «густо» 100 и 200 — на 740 и 776. В районах города застой прежний, 50 сборок (`heatnet.city.stall`), и бюджет 60.

Выигрыш дают слияния: одна камера врезки и общий ствол вместо нескольких. Черновик, где без сети осталось больше точек, чем в лучшем, не выдаётся: намеренное неподключение запрещено (п. 2.5). Для вариантов 2 и 3 от лучшего черновика строятся ещё черновики с другой врезкой у каждого из восьми крупнейших блоков (до трёх отличных врезок) и с разбиением блока пополам. Перенос врезки к стволу сводит другие врезки блока на ту же трубу, и их трассы совпадают с первыми вариантами. Поэтому, если набралось два варианта, вне районов города такие же черновики строятся ещё от блоков второго варианта с врезками без переноса. Черновики сортируются по S. Вариант берётся, если он не совпадает по трассе ни с одним уже выбранным (раздел 6 технического приложения): совпадением считается, когда у каждого из двух больше 90 % длины меньшего лежит в полосе 1 м от другого. Другая врезка или другое разбиение ОКС без такого расхождения отличием не считаются, поэтому вариантов бывает меньше трёх. На датасете организаторов все черновики с тем же числом подключённых точек совпадают с первым по трассе, и вариант один. Доля сначала оценивается снизу и сверху без буфера JTS (`RouteBand`: полоса 0,95 м за вычетом допустимых наложений рёбер и 1,05 м), буфер строится, только если оценки не решают. Собранные варианты проверяются так же по своим участкам: перенос и сдвиг камер и прокладка заново двигают трассу после отбора. Вариант, совпавший с лучшим, не выдаётся, номера остальных идут подряд.

**Перенос камер ветвления.** Ветка присоединяется к дереву в первой точке касания, поэтому камера ветвления стоит буквой Т, а не там, где рёбрам выгоднее всего сойтись. В выбранных вариантах `JunctionMover` переносит каждую камеру. Он пробует точки на рёбрах камеры и вокруг неё в сторону равнодействующей рёбер (вес ребра — цена метра трубы по Ду его расхода плюс цена метра длины в S) и перекладывает каждое ребро из новой точки прямой к самой дальней своей вершине, до которой прямая допустима по зонам графа дерева. Одно ребро может пройти через прежнюю точку камеры. Финальный участок к точке внутри здания не меняется, поворот у выхода проверяется как у ветки. Дерево после каждого переноса снова проходит `TreeBuilder.cut` без срезки углов: `Router.sharpen` с теми же запасами убирает у новых отрезков лишние вершины, двойные повороты и зигзаги (п. 5). Точки перебираются по оценке выигрыша с отсечением по нижней границе. Сначала все камеры дерева переносятся в лучшие по оценке точки, и дерево собирается один раз; если сборка не удалась или вышла не лучше, каждая камера пробуется отдельно, до трёх точек. Перенос берётся, если точный S варианта меньше, а деревья не касаются друг друга, и не берётся, если из-за него вариант совпал бы по трассе с уже выбранным. Варианты переносятся параллельно, свойство `heatnet.relay=false` выключает перенос. Поверх строгой формы и прокладки рёбер по графу своего Ду вариант 1 датасета — 12,785 вместо 13,019.

После переноса камеры ветвления сдвигаются вдоль своих рёбер (`TreeBuilder.slides`, свойство `heatnet.slide.junctions`). Жадное дерево ставит камеру там, где удобно присоединить очередную ветку, и не видит ни веток, присоединённых позже, ни разницы Ду на рёбрах камеры. Камера пробует места на входящем и на каждом исходящем ребре: в 1–50 м от прежнего места и в вершинах ребра. Ребро сдвига и продолжающее его ребро меняют только длину, остальные ветки камеры идут от нового места прямой к одной из своих вершин. Прямая не пересекает спецобъекты, излом в вершине — от 3 до 90°, точка выхода из здания остаётся на месте. Сначала сдвиг оценивается по цене метра рёбер: труба по расходу ниже ребра и метр длины по весам S. Старое место камеры и новые прямые меняют изломы рёбер и расстояния до соседних рёбер, поэтому лучший по оценке сдвиг сначала доводится до строгой формы через `TreeBuilder.cut` без срезки углов: `Router.sharpen` с теми же запасами по зонам Ду ветки, точка выхода из здания остаётся на месте. Затем дерево собирается тем же `option`, что и дерево подмножества, и сдвиг принимается, если score дерева снизился; после этого сдвиги ищутся на новом дереве снова. У камер, чьи рёбра не менялись, сдвиг берётся из кэша, камеры и черновики считаются параллельно. Черновик заменяется, если собирается целиком и его S ниже. Сдвиги снижают S вариантов по-разному, поэтому варианты заново сортируются по S: на датасете организаторов бывший третий вариант после сдвигов стал первым, S 13,140 вместо 13,230. Без переноса, поверх строгой формы и прокладки рёбер по графу своего Ду, сдвиг давал варианту 1 датасета 12,943 вместо 13,019. Дерево с перенесёнными камерами сдвигается тем же графом и сборкой, что и дерево из перебора. После переноса на восьми наборах сдвигу не остаётся мест дешевле по оценке, и выход тот же, что с одним переносом. Сдвиг до переноса дал бы в сумме S по восьми наборам хуже, датасет 12,793.

Выбранные до трёх вариантов собираются заново с рангами 1, 2, 3.

Перед этой сборкой `rerouted` прокладывает рёбра выбранных вариантов заново. Дерево строилось по графу Ду ствола со ступенью запаса, и ветка Ду 100 обходила здания с отступом трубы Ду 400. Теперь маршрут каждого ребра между теми же узлами ищется по графу фактического Ду ребра, а если такого графа в области нет, то по графу ближайшего большего Ду из уже построенных: новые графы здесь не строятся. Выход из здания ставится по зонам того же Ду и оказывается ближе к стене. Прямые рёбра не меняются, а новое ребро от врезки не должно идти вдоль её трубы. Новое ребро доводится до строгой формы, как в `TreeBuilder.cut`: `Router.sharpen` с теми же запасами по зонам фактического Ду ребра (проверщик меряет отступы по Ду участка), новые куски не ближе 0,5 м к другим рёбрам дерева, точка выхода из здания остаётся на месте. Если после этого в ребре осталась вершина, которую можно убрать одну, но тогда излом соседа меньше 3°, а без обеих прямая не проходит по отступам (`Router.loose`), замена отбрасывается: проверщик формы считает такую вершину лишней. Рёбра дерева заменяются все сразу, а если так узел врезки не собирается, то по одному. Замена принимается, если S узла врезки снизился, новые рёбра не ближе 0,5 м к другим деревьям и Ду ни одного ребра не вырос: тогда маршрут держит отступы графа, по которому проложен. Если вариант целиком не собрался, он выдаётся таким, каким его нашёл поиск. На датасете организаторов вариант 1 стал 13,126 вместо 13,230 (13 рёбер короче, длина 1872 м вместо 1890), а поверх строгой формы и звена после выхода — 13,019 вместо 13,057: 15 рёбер проложены заново, длина 1781 м вместо 1787. Отключается свойством `heatnet.search.reroute=false`.

После `rerouted` и `turned` (о нём ниже) метод `unkinked` снимает изломы, зигзаги и ступеньки у камер ветвления (п. 5). Камера переносится туда, откуда у её рёбер меньше вершин (`TreeBuilder.unkinks`). Места — узлы сетки ±6 м с шагом 0,5 м вокруг камеры, первые вершины её рёбер, проекции камеры на прямые вторых звеньев и пересечения прямых первых и вторых звеньев. Из нового места каждое ребро идёт прямой к первой или второй своей вершине; если прямая ломается в вершине меньше чем на 3°, уходит и она: такой излом сборка не пропускает. Ребро со специальной частью меняется только до её начала, а камеру ближе 0,08 м к специальной части проход не трогает. Новые звенья проверяются по зонам фактического Ду ребра с запасами строгой формы: отступ плюс 0,15 м, не ближе 0,5 м к другим рёбрам, поворот до 89,9°, звено от 1,05 м. Повороты в камере от ребра к родителю и в дальнем узле ребра, к которому теперь идёт одно звено, тоже не круче 89,9°. Камера не встаёт у объектов специального прохода и в зону запрета, финальный участок к точке внутри здания остаётся на своей прямой. Места перебираются по возрастанию цены рёбер, и первые три годных переноса проверяются по S узла врезки. Соседние места упираются в одну и ту же зону, поэтому `ObstacleSet.plain` сначала проверяет зону, в которую упёрлась прошлая прямая ребра. Рёбра камеры доводятся до строгой формы, как в `rerouted`, но вершина, без которой поворот в камере стал бы круче 89,9°, остаётся. Перенос берётся, если S узла врезки вырос не больше чем на 0,002, Ду рёбер не выросли, а дерево не касается других; дальше изломы ищутся на новом дереве, а камера, у которой перенос не взят, с теми же рёбрами не пробуется снова. Проход идёт после `turned`: правка поворота в камере может поставить вершину у камеры, а перенос поворотов круче 89,9° в камере не создаёт. На датасете организаторов так выпрямились ветки у камер v1_ch_7 (излом 4,81° в 1,17 м от камеры на ветке к ОКС 13), v1_ch_13 и v1_ch_14, ушли зигзаг у v1_ch_11 и лишняя вершина у v1_ch_4, вариант 1 — 12,744 вместо 12,746. Такие места check18 ловит категорией B21: места переноса и проверки у него те же.

Тот же проход сдвигает новую камеру врезки на трубе, если первая вершина её ребра не нужна для отступов: прямая от врезки к следующей вершине проходит по зонам фактического Ду ребра с запасом 0,15 м (`VariantEnumerator.retied`). Вершина остаётся ради поворота: без неё поворот в следующей вершине круче 89,9°. Камера пробует места вдоль трубы до 5 м в обе стороны с шагом 0,1 м, ребро идёт от нового места прямой ко второй вершине, остальные рёбра врезки — к первой (`TreeBuilder.retie`). Новые звенья проверяются так же, как у камеры ветвления, и ещё уходят от сети у новой врезки. Место врезки даёт `TieInFinder.shifted`: у концов трубы и у существующей камеры не дальше 10 м оно другое, и такой сдвиг не берётся. Сдвиг пробуется, если узел врезки держит одно дерево; места перебираются по возрастанию цены рёбер, и берётся первое, при котором S не вырос. На датасете организаторов так ушла вершина ветки к ОКС 17 (10,3° и 80° через 1,5 м): камера v1_ch_3 сдвинулась по трубе 129 на 0,4 м, в точке выхода остался один поворот 89,9°, вариант 1 — 12,745 вместо 12,746.

Перед `unkinked` по готовым деревьям варианта идёт `turned`: он правит повороты круче 89,9° в камерах ветвления на пути точки к врезке (п. 2.1, разъяснение 5). Путь точки проходит камеру от первого звена ветки к последнему звену ребра к родителю, и угол между ними — такой же поворот, как в вершине. Поиск этого не проверяет: встроенное в него правило стоило 60 % времени на датасете и S на плотных сценах. Проход пробует две правки у каждой такой камеры. Первая — сдвиг камеры вдоль первого звена любого её ребра шагом 0,1 м до 10 м (`TreeBuilder.turnSlides`), с теми же проверками, что у `unkinks`. Вторая — излом звена одного ребра у камеры (`TreeBuilder.bends`): звено поворачивается на наименьший угол от 3,5° с шагом 0,5°, при котором все повороты в камере не круче 89,9°, ребро идёт до новой вершины в 1,05·2^k м от камеры и оттуда к прежней первой вершине. Финальный участок прямо от камеры в здание не меняется. Изменённые рёбра доводятся до строгой формы, где `Router.sharpen` не убирает вершину, если без неё поворот в камере на концах ребра стал бы круче 89,9°. Правка берётся, если таких поворотов в дереве стало меньше, S узла врезки вырос не больше чем на 0,002, Ду рёбер не выросли, а дерево не касается других. На датасете организаторов так снят поворот 97,9° у камеры v1_ch_11 (ветка к ОКС 2), вариант 1 — 12,746 вместо 12,745. Из восьми наборов проход не снял одно место: камеру v3_ch_67 в третьем варианте dense-100, где три ветки расходятся шире 180°, и ни одно направление к врезке не даёт всем поворотов до 90°. Такие повороты check18 ловит категорией B20: в техническом узле это нарушение, в камере — нарушение, если его снимает одна из тех же правок, иначе справочная строка с причиной.

Затем идёт `bent`. Рёбра готовых деревьев, где есть два соседних поворота в одну сторону, доводятся `Router.sharpen` с шагом 4 по зонам фактического Ду ребра, поворот в камере на пути точки остаётся не круче 89,9°. Сначала пробуются все такие рёбра дерева сразу, а если так не выходит, по одному. Замена берётся, если S узла врезки не вырос, Ду рёбер не выросли, а дерево не касается других. На датасете организаторов так ушёл двойной поворот v1_seg_2: +10,5° и через 11,3 м ещё +29,5° заменила одна вершина 38,5° с запасом 0,15 м, трасса короче на 0,13 м, вариант 1 — 12,743 вместо 12,744. Такие места check18 ловит категорией B17: одну вершину он ищет сеткой в эллипсе с фокусами в соседях пары и спуском по длине.

Последним идёт `entered`: он ставит вход финального участка у ближайшей допустимой точки контура здания (п. 2.2). Поиск берёт выход у ближней открытой стороны по ближайшим точкам сторон, а на изрезанном фасаде ближе бывает точка посреди стороны. Если вход дальше ближайшей точки контура больше чем на 5 см, `TreeBuilder.entered` перебирает точки контура через 5 см по возрастанию расстояния. Точка годится, если луч через неё выходит из здания один раз, в зоне отступа не подходит к другой стене, а на луче за зоной есть выход, от которого звено до прежней вершины ребра держит запасы строгой формы: отступ плюс 0,15 м, поворот до 89,9°, звено от 1,05 м, 0,5 м до других рёбер. Ребро доводится до строгой формы, как в `rerouted`. Правка берётся, если узел врезки собирается, Ду рёбер не выросли, а дерево не касается других; S не сравнивается, вход задаёт правило. Вход, от которого трасса пошла бы в обход здания, так не требуется. Часть луча за зоной для каждой точки входа считается один раз (`TreeBuilder.window`), а лучи, которые снова входят в здание раньше, чем могли бы выйти из зоны, отсеиваются по пересечениям со сторонами без JTS. На датасете организаторов вход ОКС 10 перенесён с 8,18 м на 7,50 м, вариант 1 — 12,751 вместо 12,743; синтетические наборы не изменились. Проход идёт после `unkinked` и `bent`: если ставить вход раньше, вариант 1 — 12,748, но у камеры v1_ch_4 остаётся S-излом (−63,6° и −25,8° через 2,04 м), а перенос камеры, который его снимает, при новом входе стоит 0,003 S, больше допуска `unkinked`. Такие входы check18 ловит категорией B8.

### Большой вход: прямые подключения и районы

Перебор из раздела 6 рассчитан на десятки ОКС: граф области квадратичен по числу узлов, а черновики и поиск растут быстрее n². Если перспективных ОКС больше 500 (`heatnet.city.min`), `VariantEnumerator.city` считает вход иначе.

1. **Прямые подключения.** `DirectTies` для каждой точки подключения по порядку берёт три ближайшие существующие камеры со свободным местом, три ближайшие трубы (проекция, а в 10 м от камеры — камера) и уже поставленные новые камеры в 300 м (`heatnet.city.reach`) с местом ещё для одного участка; у камеры на трубе места на два участка меньше за каждую проходящую трубу, на дублях труб места нет. Для каждого кандидата строится прямой участок от врезки к точке: один отрезок, если врезка внутри здания точки или в его зоне отступа, иначе два — через точку выхода на луче к ближайшей точке контура. Следующие по расстоянию стороны берутся, только если ближняя закрыта: выхода на луче нет, луч снова входит в своё здание или его зону отступа (`TreeBuilder.leavesOnce`) или проходит ближе отступа к чужому зданию или запретному объекту (с допуском 0,01 м, как у `check18.py`). Если от выхода к врезке поворот круче 90°, после выхода ставится звено, как у ветки дерева (`TreeBuilder.exitLink`); если поворот меньше 3°, участок идёт одним отрезком: вершину с таким изломом сборка не пропускает и отбросила бы весь узел врезки. Если участок от выхода у ближней открытой стороны недопустим, точка не переходит на дальнюю сторону (п. 2.2), а идёт в районы. Один отрезок от врезки в зоне отступа берётся, только если он входит в здание у ближайшей к точке границы (внутри здания он длиннее расстояния до неё не больше чем на 0,9 м, у `check18.py` предел 1 м) или ближняя сторона закрыта; врезка на трубе внутри самого здания — толкование из раздела 19 `CONSTRAINTS.md`, для неё этой проверки нет. Участок проверяется на отступы к зданиям, запретным ограничениям и сети; дорогу, пути и линии он может пересечь спецпроходом под допустимым углом. Берётся самый дешёвый по длине, Ду и узлу из участков, которые не ближе 0,5 м к уже поставленным участкам других врезок, а у общей врезки не касаются её участков вне круга 0,15 м, как деревья районов: сборка по узлам врезки участки разных узлов между собой не сверяет. Место в новой камере на трубе проверяется и тогда, когда она кандидат самой точки, а не только поставленная раньше камера; второй вариант города берёт второго по стоимости кандидата, оба набора деревьев строятся за один обход точек с раздельным учётом мест в камерах. Точка вне рамки сети с запасом 300 м кандидатов не получает: любой из них дальше 300 м. Кандидаты ближних точек и допустимость участков к ним считаются параллельно, выход из здания — один раз на точку, участки к уже поставленным новым камерам — пачкой на 32 точки вперёд; места в камерах и новые камеры распределяются последовательно в прежнем порядке точек, поэтому выход тот же, что при расчёте в одну нить. Если у точки нет ни одного прямого подключения, а труба ближе 3 м (в синтетическом городе труба проходит через здание точки), врезка сдвигается вдоль трубы на 0,5–15 м в обе стороны, пока остаётся в зоне своего здания; участок от неё может пересечь чужую трубу спецпроходом, и такое дерево сначала собирается пробно. Точки без допустимого прямого участка идут в районы, а точки дальше предельной длины наибольшего Ду (11 276 м) от сети остаются без маршрута сразу: ни один путь к ним не уложится в предел ни при каком диаметре; расстояния до сети считаются параллельно.
2. **Районы.** Оставшиеся ОКС делятся на группы близких ОКС, как в разделе 2. Крупные группы режутся пополам (k-means или по длинной стороне рамки), пока в районе не останется не больше 16 ОКС (`heatnet.city.block`).
3. **Расчёт районов.** Каждый район считается тем же перебором из раздела 6 на своих ОКС. Сеть, препятствия и их индексы общие, кэш маршрутов у района свой. Районы идут параллельно по числу ядер (`heatnet.city.threads`), ближние к сети первыми: их графы меньше. Районы, не начатые за `heatnet.city.deadline` секунд от старта городского расчёта (300), не считаются, их точки остаются без сети; на синтетическом городе десятки тысяч точек лежат в 5–11 км от сети, и их графы считались бы часами. Районы ближних точек досчитываются за ~110 с, последний район, давший дерево, — за ~230 с; срок 900 с даёт тот же выход. В районе действуют упрощения: кандидаты врезки дальше ближайшего больше чем на 150 м отбрасываются, область графа — не прямоугольник, а полоса вдоль прямых от точек к кандидатам врезки шириной 25 % длины, но не уже 60 м (`heatnet.city.corridor`), у графа один диаметр на район и нет широкой области, поиск тратит 60 сборок вместо 600. Дерево района не касается прямых подключений обоих наборов так же, как деревьев своего района, и не занимает в их камерах больше места, чем осталось в наборе с наибольшим числом участков в этой камере.
4. **Сборка.** Прямые подключения собираются по узлам врезки параллельно с общими счётчиками ID, деревья районов — одной сборкой; дерево района, задевающее прямое подключение или уже принятое дерево соседа или переполняющее общую с ними камеру, не берётся. Сводка складывается из частей, ранг кандидату даёт S всего варианта.

### 7. Сборка сети

`NetworkAssembler` превращает деревья варианта в объекты результата. Деревья с общей точкой врезки собираются в один узел. При врезке в существующую камеру участки начинаются в ней (ссылка на её входной `id`), и каждый такой участок — врезка за 5 млн руб. При врезке в трубу узел врезки — новая камера `heat_chamber`, её стоимость включает присоединение.

```mermaid
flowchart TD
    trees[Деревья варианта] --> flows[FlowCalculator:<br/>расход ребра = сумма ОКС ниже]
    flows --> dn[DiameterPlanner:<br/>минимальный DN ребра по расходу,<br/>ДУ детей и предельной длине пути]
    dn --> cut[Разрезка рёбер на участки<br/>по спецзонам и смене их набора]
    cut --> checks{Проверки:<br/>отступы, повороты, форма}
    checks -->|нарушение| reject[IllegalStateException:<br/>вариант отбрасывается]
    checks -->|ок| chambers[Камеры ветвления<br/>и камеры врезки]
    chambers --> cost[CostCalculator:<br/>стоимость и S]
    cost --> variant[Variant + VariantSummary]
```

| Этап | Что делает |
|---|---|
| **Расходы** | `FlowCalculator` обходит дерево от листьев к корню: расход ребра равен сумме расходов ОКС ниже по дереву |
| **Диаметры** | `DiameterPlanner` идёт от листьев к корню: ДУ ребра — наименьший, который проходит по расходу, не меньше ДУ дочерних рёбер и укладывает в предельную длину самый длинный путь одного ДУ через ребро; на ребре ДУ один, узел без смены ДУ отсчёт не начинает |
| **Разрезка** | участок делится техническим узлом на границах спецзон и на каждой смене их набора (разъяснение 8), Kспец части — наибольший в наборе. Зона линии — `margin_m` вдоль трассы от пересечения. Зона дороги — часть трассы в полигоне и `margin_m` вдоль трассы за границей, а если обычный участок там ближе нормы отступа, то до точки, где норма держится. Специальный участок с вершиной внутри отбрасывается: спецпроход — один прямой участок. Если за границей спецчасти ближе 0,08 м лежит вершина ребра, узел ставится в неё: у узла не остаётся звена в сантиметры |
| **Проверки** | отступы от объектов специального прохода, поворот не круче 90° в вершинах и технических узлах, форма участков; нарушение отбрасывает вариант |
| **Проверки с запасом к валидатору** | валидатор считает узлы ближе 0,05 м одним узлом, а координаты выхода округлены до 9 знаков. `checkApart` и проверка при разрезке отбрасывают дерево, если узлы разных участков ближе 0,06 м, участки касаются вне общих узлов или сами себя, спецкусок не длиннее 0,12 м, обычный и специальный участки ближе 0,06 м без общего узла или расходятся из узла под углом меньше 30,5°, обычный кусок перекрывает зону больше чем на 0,1 м. Такие деревья получались на плотной застройке у самых труб; на датасете организаторов проверки не срабатывают |
| **Стоимость** | новые участки (`длина × цена за метр DN × Kспец`), новые камеры, врезки в существующие камеры, штраф за неподключённые точки; суммы до копеек, S до трёх знаков; реконструкции по редакции 18.09 нет |

### 8. Запись результата

`GeoJsonStreamWriter` переводит геометрию обратно в EPSG:4326 и пишет результат потоком, по фиче на строку. В файле лежат объекты всех вариантов: новые участки, новые камеры, технические узлы и `variant_summary` на каждый вариант; ссылки на объекты входа с числовым `id` записаны числом. Глубины `depth_start` и `depth_end` всегда `null`: расчёт идёт только в плане.

## Правила и проверка

Все таблицы и коэффициенты кейса лежат в `rules/rules.json`. Java-сервис и Python-инструменты читают только этот файл, поэтому числа в коде не дублируются.

```mermaid
flowchart LR
    constraints[CONSTRAINTS.md] -->|RulesMatchConstraintsTest| rulesjson[rules/rules.json]
    rulesjson --> service[Сервис]
    rulesjson --> check18[check18.py]
    input[Вход: датасет или heatsynth] --> service
    service -->|выход| check18
    input -->|вход| check18
    check18 --> verdict[CHECK18 OK / CHECK18 VIOLATIONS]
```

Что числа в `rules/rules.json` совпадают с таблицами CONSTRAINTS.md, проверяет Java-тест `RulesMatchConstraintsTest`.

Валидатор `tools/validator/check18.py` не использует код сервиса. Он читает вход и выход и проверяет выход по техническому приложению и разъяснениям от 18.09.2026: состав объектов и ссылки узлов, геометрию и отступы, расходы и ДУ, камеры и врезки, стоимость и сводку. Отдельно он проверяет, что финальный участок идёт от ближайшего допустимого входа в здание, не возвращается в зону отступа своего здания и не подходит в ней к другой стене, углы и полосы спецпроходов, камеры врезки в полосе дороги, звенья короче метра у узлов спецпрохода, пересечение существующей сети только спецпроходом и касания новых участков вне общих узлов. Ограничение типа, которого нет в `rules.json`, он считает запретом с отступом `_fallback`, как сервис. Нарушения он печатает по категориям и заканчивает строкой `CHECK18 OK`, если их нет. Этим же валидатором `PipelineSampleIT` проверяет выход на `data/samples/small-1.geojson`.

Часть допусков в сервисе подобрана под то, как считает валидатор: узлы ближе 0,05 м он считает одним узлом, координаты выхода округлены до 9 знаков. Такие места помечены комментариями в `TieInFinder`, `TreeBuilder`, `Router` и `ObstacleSet`.
