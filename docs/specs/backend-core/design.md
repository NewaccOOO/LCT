# Дизайн: бекенд трассировки тепловых сетей

## Контекст и масштаб

Кода нет, репозиторий пустой, кроме CONSTRAINTS.md и этого пакета. Стек зафиксирован организатором (C-1). Вход до 3 ГБ, поэтому файл нельзя держать в памяти целиком (C-1, R-3). Геометрия считается в JTS в памяти, база хранит только задачи (NG-4, R-4). Алгоритм трассировки выбран по R-7…R-12 и описан в [ADR-0001](adr/0001-routing-approach.md).

## Решение

Один Maven-модуль в корне репозитория. Внутри три слоя без Spring-зависимостей в первых двух: `io` читает и пишет файлы, `core` считает, `api` принимает задачи и отдаёт результат. Рядом в `tools/` два Python-пакета: генератор синтетики и валидатор. Все числа кейса лежат в одном файле `rules/rules.json`, который читают и Java, и Python.

- **D-1** Структура репозитория и пакетов — закрывает AC-5.2, C-3, C-4.

    core/      Pipeline (интерфейс: InputData → Result), PipelineImpl

  Пакет `core` это `rules`, `graph`, `plan`, `calc` вместе; в них нет импортов Spring.

- **D-2** Правила кейса в одном файле `rules/rules.json`, Maven подключает `rules/` как ресурс, Python читает тот же путь — закрывает C-3, AC-3.3. Схема:

  Полный список из 18 диаметров и четырёх ценовых диапазонов камер берётся из разделов 6 и 9 CONSTRAINTS.md. Тест `RulesMatchConstraintsTest` (Java) и `test_rules_match_constraints.py` (Python) парсят таблицы CONSTRAINTS.md и сверяют с `rules.json`.

- **D-3** Потоковое чтение входа: Jackson `JsonParser` (2.13.1 из BOM Boot) идёт по массиву `features`, каждую фичу через `ObjectMapper.readTree(parser)` превращает в JTS-геометрию и объект `InputModel`, затем сразу репроецирует в EPSG:32637 через proj4j (R-2). В памяти остаются только объекты, не текст файла — закрывает NFR-2. Атрибуты, включая `id`, читаются из `properties`. Ориентация LineString не предполагается: конец участка, обращённый к источнику, это конец, ближайший к геометрии объекта `upstream_object_id`, совпадение точек с допуском 0,5 м (A-9). Фичи без обязательных атрибутов (раздел 12 CONSTRAINTS.md), с дублями `id` или висячими ссылками копятся в список диагностик, а не роняют парсер; при непустом списке задача завершается `FAILED` с этим списком — закрывает AC-1.4.

- **D-4** Загрузка сырым телом запроса, не multipart: `POST /api/v1/jobs` с `Content-Type: application/json` или `application/geo+json`, тело копируется `Files.copy(request.getInputStream(), path)` в `data/jobs/<id>/input.geojson` (R-3). Ограничений размера в Spring не остаётся, файл на диск пишется один раз — закрывает AC-1.1, NFR-2.

- **D-5** Задачи: таблица `jobs` в PostgreSQL через Spring Data JPA, схема из `schema.sql` (`spring.sql.init.mode=always`), без Flyway. Поля: `id uuid`, `status` (`QUEUED`, `RUNNING`, `DONE`, `FAILED`), `created_at`, `started_at`, `finished_at`, `error jsonb`, `summary jsonb`, `input_path`, `output_path`. `JobWorker` это `ThreadPoolTaskExecutor` на 2 потока с очередью; статусы меняются в отдельных транзакциях — закрывает AC-1.2, NFR-3.

- **D-6** Область расчёта. Из всего входа в граф попадают только объекты в прямоугольнике вокруг ОКС и кандидатов врезки с запасом 500 м; поиск через `STRtree`. Так вход в сотни мегабайт с далёкими объектами не раздувает граф — закрывает NFR-1, NFR-2.

- **D-7** Препятствия и буферы (`graph/ObstacleSet`). Для каждого ограничения с правилом `forbid` строится буфер `clearance + width/2` для текущего расчётного диаметра, `join=mitre`, затем `simplify(0.05)`. Вершины буферов, у которых внутренний угол больше 180°, становятся узлами графа (R-8). Для `oks_existing` отступ зависит от диаметра новой сети по таблице `clearance_m`. Для линейных объектов с полушириной буфер строится от оси с учётом `half_width_m`. Диаметр на момент построения неизвестен, поэтому: первый проход с диаметром по суммарному расходу всех ОКС кластера, после расчёта диаметров проверка отступов и при нарушении повтор с фактическими диаметрами, не больше трёх итераций — закрывает AC-2.7.

- **D-8** Visibility graph и путь (`graph/VisibilityGraph`, `graph/Router`). Узлы: точки подключения ОКС, существующие камеры, вершины существующей сети, кандидаты врезки, рефлексные вершины буферов. Ребро между двумя узлами существует, если отрезок не пересекает ни один буфер запрета. Для каждого ребра при построении считаются пересечения с объектами `special`: для `road` и `tram_tracks` угол между отрезком и пересекаемой стороной полигона меньше `min_angle_deg` → ребро удаляется; иначе вес = длина + `(k_special − 1)` × длина части отрезка внутри специального участка. Специальный участок для полигонов это часть внутри полигона плюс `margin_m` за границей с каждой стороны; для линий это `margin_m` в каждую сторону от точки пересечения. Кратчайшие пути через `DijkstraShortestPath` из JGraphT 1.5.3 (R-6). Пересечение существующей сети без врезки трактуется как `special` с `k_special` 1.05 — закрывает AC-2.7, AC-2.13.

- **D-9** Кандидаты врезки (`plan/TieInFinder`). Для каждого ОКС и для центроида каждого кластера ОКС: ближайшие 3 существующие камеры и перпендикулярные проекции на 3 ближайших участка сети. Кандидат, лежащий не дальше `max_dist_m` от существующей камеры, у которой после подключения будет не больше `max_segments` участков, становится врезкой в камеру; иначе врезкой в трубу с новой камерой — закрывает AC-2.2.

- **D-10** Дерево (`plan/TreeBuilder`). От выбранной врезки эвристика Такахаши–Мацуямы: дерево растёт из врезки, на каждом шаге присоединяется ОКС с кратчайшим путём от текущего дерева (R-9). После первого дерева добавляются узлы-проекции неприсоединённых ОКС на построенные стволы и дерево пересчитывается. Затем 3 итерации переоценки весов: по дереву считается расход ветвей → диаметр → цена за метр по `rules.json` → вес ребра = длина × цена → повтор (R-10). Постобработка: спрямление (вершина удаляется, если отрезок между соседями свободен), ветвления только в узлах-камерах, у камеры не больше `max_branches` ответвлений, лишнее ответвление переносится на ближайшую соседнюю точку ствола с новой камерой — закрывает AC-2.3, AC-2.13.

- **D-11** Варианты (`plan/VariantEnumerator`). Перебор: (3 лучших кандидата врезки для кластера) × (все ОКС общим деревом; каждый ОКС отдельной врезкой; ОКС разбиты на два кластера по k-means с k=2). Для каждого варианта полная сборка и стоимость. Два варианта считаются одинаковыми, если общая длина совпадающих участков больше 80 % длины меньшего (R-11). Выдаются до 3 лучших по S, не меньше 2, если есть хотя бы два разных — закрывает AC-2.12.

- **D-12** Сборка (`plan/NetworkAssembler`). Дерево режется на участки в точках: врезка, камера, точка подключения ОКС, смена диаметра, граница специального участка. В точках смены диаметра и границах специальных участков ставятся `technical_node`. У каждого участка `start_node_id` ближе к источнику. Расчёт по `calc/*`: расход участка = сумма расходов ОКС ниже по дереву; диаметр минимальный по `capacity_tph`; проверка `max_length_m` по непрерывной цепочке одного диаметра, при превышении диаметр цепочки поднимается на одну ступень и проверка повторяется; реконструкция по цепочке `upstream_object_id` от участка врезки до `source`, для врезки внутри участка только часть от точки врезки к источнику; реконструкция камеры врезки по наибольшему примыкающему диаметру; стоимость по разделу 9 CONSTRAINTS.md; S по разделу 10 — закрывает AC-2.4…AC-2.11.

- **D-13** Запись выхода (`io/GeoJsonStreamWriter`): Jackson `JsonGenerator` пишет `features` по одному объекту, геометрия репроецируется обратно в EPSG:4326, у каждого типа только свой набор полей, `depth_start` и `depth_end` всегда `null` (NG-2). Числа длин и стоимостей округляются до 2 знаков, `score` до 3 — закрывает AC-1.3, AC-2.10.

- **D-14** Валидатор `tools/validator` (пакет `heatcheck`). Вход: входной и выходной GeoJSON. Репроекция pyproj в EPSG:32637, геометрия shapely 2. Каждое правило это функция `check_<rule>(inp, out, rules) -> list[Violation]`. Отчёт: таблица «правило → число нарушений → первые 5 примеров с ID», в конце `VALIDATION PASSED` или `VALIDATION FAILED: <список правил>`, код выхода 0 или 1. Правила и их ID:

  | ID правила | Что проверяет |
  |---|---|
  | `schema` | типы объектов, обязательные поля, отсутствие чужих полей, одна сводная запись на вариант |
  | `topology` | дерево: от каждой врезки один путь до каждого ОКС, нет циклов, новые участки не пересекаются вне общих узлов, у камеры ≤ 4 участков и ≤ 3 ответвлений |
  | `tie_in` | врезка в камеру только если ≤ 10 м и ≤ 4 участков; иначе новая камера в точке врезки |
  | `flow` | расход участка = сумма расходов ОКС ниже по дереву |
  | `diameter` | минимальный диаметр с `capacity_tph` ≥ расход; на ступень выше допустимо только если цепочка на минимальном нарушила бы `length_limit` |
  | `length_limit` | непрерывная цепочка одного диаметра не длиннее `max_length_m` |
  | `forbid` | новые участки не пересекают запрещённые полигоны и держат отступ `clearance + width/2` |
  | `special` | пересечения `special`-объектов только участками `laying_method=special`, специальный участок это трасса внутри объекта, буферизованного на `margin_m`, угол между трассой и стороной полигона на входе и выходе ≥ 45° для дорог и трамвая; отступ `clearance` от `special`-объекта только для обычных участков, не смежных со специальным через этот объект |
  | `reconstruction` | добавленный расход прокинут по `upstream_object_id`, требуемые диаметры и длины частей верны, лишних реконструкций нет |
  | `chamber_recon` | реконструкция камеры врезки только при превышении исходного диаметра, стоимость по шкале |
  | `cost` | каждое `cost` пересчитано по формулам с расхождением ≤ 1 руб., сводные суммы сходятся |
  | `score` | S по формуле, `rank` по возрастанию S |
  | `coverage` | каждый ОКС либо подключён, либо в `unconnected_oks_ids`; штраф посчитан |
  | `variants` | не меньше 2 вариантов, любые два различаются набором врезок (другой `existing_object_id` или точка дальше 20 м от всех врезок другого) или разбиением ОКС по деревьям |
  | `geometry` | нет вершин с отклонением меньше 3° и подотрезков короче 1 м, кроме смежных со специальным участком; число поворотов (вершин с отклонением ≥ 3°, включая камеры и узлы) на пути врезка → ОКС не больше 3k + 4, где k число полигонов «запрещено» плюс дорог и трамвайных путей, которые пересекает прямая между ними |

  Каждое правило печатает `checked=<n>` — число проверенных объектов (участков, врезок, пересечений, частей реконструкции). Путь к правилам задаётся флагом `--rules`, по умолчанию `rules/rules.json` от текущего каталога.

  Закрывает AC-3.1, AC-3.2 и все критерии US-2.

- **D-15** Генератор `tools/synth` (пакет `heatsynth`). Всё строится в метрах в EPSG:32637 и в конце переводится в EPSG:4326. Источник в центре; существующая сеть как случайное дерево из 3–5 магистралей с ветвлениями в камерах; расходы растут к источнику, диаметр по таблице, `upstream_object_id` заполнен; ОКС как прямоугольники 30–80 м на расстоянии 50–400 м от сети с точкой подключения на стороне, обращённой к сети; ограничения всех 10 типов: полигоны для `forbid`, полосы 8–20 м для `road` и `tram_tracks`, линии для `gas_pipeline`, `power_cable`; не меньше чем у половины ОКС на прямой к ближайшему участку сети стоит запрещённый полигон. Полигоны ограничений со стороной не меньше 20 м. Ветка сети, ближайшая к каждому ОКС, загружена не меньше чем на 80 % пропускной способности, у каждого ОКС не меньше двух камер в радиусе 500 м, у пяти и более ОКС на прямой к сети лежит дорога или трамвайные пути. Координаты участков сети пишутся от конца, обращённого к источнику, но читатель на это не полагается (A-9). Пресеты: `small` (3 ОКС, 20 ограничений, 30 участков), `medium` (20, 200, 300), `large` (100, 2000, 3000). Флаг `--pad-mb N` добавляет далёкие полигоны `park` до нужного размера файла — закрывает AC-4.1…AC-4.3, NFR-2.

- **D-16** Режим CLI для гейтов и отладки: `java -jar target/heatnet.jar --cli <input> <output>` запускает приложение с профилем `cli` (`spring.main.web-application-type=none`, автоконфигурация DataSource и JPA исключена), прогоняет `GeoJsonStreamReader → Pipeline → GeoJsonStreamWriter` и печатает `PIPELINE DONE variants=<n> elapsed=<s>s`; при диагностиках входа печатает их и завершается кодом 2. Тот же `Pipeline` вызывает `JobWorker` — закрывает NFR-1 и все критерии US-2.

## Интерфейсы и данные

REST, префикс `/api/v1`, все ответы JSON в UTF-8, ошибки в формате `{"message": "…", "errors": [{"featureId": "…", "field": "…", "problem": "…"}]}`.

| Метод и путь | Запрос | Ответ |
|---|---|---|
| `POST /jobs` | тело: GeoJSON, `Content-Type: application/json` или `application/geo+json` | `202 {"id": "<uuid>", "status": "QUEUED"}`; `400` при пустом теле или первом байте не `{` |
| `GET /jobs` | — | `200 [ {id, status, createdAt, finishedAt} ]`, новые первыми |
| `GET /jobs/{id}` | — | `200 {id, status, createdAt, startedAt, finishedAt, error, summary}`; `summary` это массив `variant_summary` без геометрии после `DONE`; `404` |
| `GET /jobs/{id}/result` | — | `200` файл `application/geo+json`, `Content-Disposition: attachment`; `409` пока не `DONE`; `404` |
| `GET /jobs/{id}/input` | — | `200` исходный файл; `404` |
| `GET /v3/api-docs`, `GET /swagger-ui/index.html` | — | springdoc 1.7.0 |

Swagger описывает все пять операций с примерами.

Команды Python из корня репозитория:

```bash
uv run --project tools python -m heatsynth --preset medium --seed 1 --out data/synth/medium-1.geojson
uv run --project tools python -m heatcheck data/synth/medium-1.geojson data/out/medium-1.geojson
```

Идентификаторы выходных объектов: `v<variant>_seg_<n>`, `v<variant>_tie_<n>`, `v<variant>_ch_<n>`, `v<variant>_node_<n>`, `v<variant>_recon_<n>`, `v<variant>_chrecon_<n>`, `summary_<variant>`; `variant_id` это `"1"`, `"2"`, `"3"` в порядке ранга.

## Альтернативы

- Сеточный A* или Theta* — отклонены: ступенчатые трассы и невозможность честно проверить угол 45° без состояния направления (R-7, ADR-0001).
- MILP-модели уровня THERMOS и DHNx — отклонены: нужен солвер и дни на модель, а трассировка там идёт по уличному графу, не по свободной геометрии (R-12).
- Multipart-загрузка — отклонена: двойная запись 3 ГБ на диск и лимиты Tomcat (R-3).
- PostGIS — отклонён, NG-4.
- GeoTools для GeoJSON и репроекции — отклонён: тяжёлые транзитивные зависимости, а нужные операции есть в JTS и proj4j (R-1, R-2).

## Выкатка, откат, наблюдаемость

- **Включение и выключение:** `docker-compose up -d`, `docker-compose down`. Переменные `DATA_DIR`, `SPRING_DATASOURCE_URL`, `JOB_WORKERS` (по умолчанию 2).
- **Откат:** удалить контейнеры и том базы; файлы задач в `data/` можно удалить целиком, других данных нет.
- **Сигналы отката:** задачи зависают в `RUNNING` дольше 10 минут; `/actuator/health` отвечает не `UP`.
- **Отказ зависимости:** без PostgreSQL приложение не стартует; `depends_on` и `healthcheck` в compose ждут базу.

## Где можно застрять

- Visibility graph на среднем наборе строится дольше 30 секунд → сначала ограничить область (D-6) и число рефлексных вершин радиусом 300 м от прямой между врезкой и ОКС; порог NFR-1 проверяется гейтом.
- Буфер зависит от диаметра, а диаметр от маршрута → итерация D-7, не больше трёх проходов; при третьем нарушении диаметр берётся с запасом на ступень выше.
- Ограничение «не больше 3 ответвлений» ломает дерево после переноса → консервативный вариант: лишний ОКС подключается отдельной врезкой, это допустимо по правилам.
- proj4j использует старый `tmerc` → в пределах зоны 37N ошибка меньше миллиметра (R-2), для Москвы это нормально.
- Python 3.12+ и shapely: версии зафиксированы в `tools/pyproject.toml` (R-17).
- `brew install openjdk@11` кладёт keg-only JDK → в `scripts/gates/env.sh` экспортируется `JAVA_HOME=$(brew --prefix openjdk@11)` и `PATH`, все гейты подключают этот файл.
